01 · Docker 与 K8s

这一域的五道题里四道和容器有关。好消息是：只要把几个"关系"说对，就不会扣分—— 这一域考的是"够用"，而不是让你讲实现原理。

读之前

这一页不需要你搭过集群。但需要你知道"程序跑在服务器上"这件事大概是怎么回事。完全没接触过容器也没关系，这页从"它解决什么问题"讲起。术语不熟先看 00 · 先认识这几个词。

第一遍（5 分钟）只看主图，把 Docker 和 K8s 的关系记住。
第二遍（12 分钟）读第 2、3 节，那两节最容易被追问。
第三遍做页尾回忆卡，然后说清你自己项目里做到了哪一步。

0. 先看一个场景

对方问：「Docker 和 K8s 是什么关系？」

最常见的错误答法

「K8s 是 Docker 的升级版，现在都用 K8s 不用 Docker 了。」

这句话把两个不同层次的东西说成了替代关系——是本组题里最容易踩的坑，而且一说出口对方就知道你没用过。

正确的关系是：它们解决的是两个不同的问题。Docker 解决"这个应用怎么打包成一个能到处跑的东西"，K8s 解决"一堆这样的东西怎么在多台机器上管起来"。没有谁替代谁。

主图 · 它们不在一个层次上

Docker 管"一个"，K8s 管"一堆"

这张图在说什么：Docker 管"一个"，K8s 管"一堆"，它们是上下层关系，不是新旧版本。答这道题的关键就是把这句关系说对。

顺带说一句：业界确实有过"K8s 弃用 Docker"的新闻，但那说的是底层换成通用的容器运行时，不是"容器不用了"。能主动澄清这个误解，会显得你真的关注过。

颜色含义： 单机打包与运行 集群编排 两者关系 常见误解

1. 镜像和容器，还有挂载（KJ-6）

这题问三件事：镜像和容器的关系、怎么挂载、以及隐含的"数据怎么持久化"。

概念一句话说清类比
镜像 一个只读的模板，里面装着应用代码、依赖、运行时。它本身不会运行。 像一张光盘——内容固定，可以复制很多份。
容器 镜像运行起来的实例。同一个镜像可以起很多个容器，各自独立。 像把光盘放进播放器跑起来——同一张盘可以同时在很多台机器上放。
容器的可写层 容器里的改动写在镜像之上的一层，容器删掉这层就没了。 这解释了为什么容器一删，里面的数据就丢——那是本题的核心。
「怎么挂载」怎么答

挂载（把宿主机的目录或文件映射到容器里）解决的是两件事：

  • 数据要留住：数据库文件、上传的文件、日志——这些不能跟着容器一起消失。所以挂到外面去。
  • 配置要能改：不想为了改一个配置项就重新做镜像，就把配置文件挂进去。

答的时候补一句实际影响，比只讲概念有用：「这个在项目里的直接影响是——我们上线新版本时会重建容器，但数据不会丢，因为数据卷是独立于容器存在的。」

2. 多个服务之间怎么通信（KJ-7）

这题在集群里问，但答案要分层说——不同范围的通信用的东西不一样。

① 同一个容器组内部的几个容器

走本机地址同一组里的容器共享网络，互相访问就像同一台机器上的不同端口。

② 集群内部，服务之间互相调用

靠服务名，不靠 IP给一组容器配一个固定的访问名，请求会自动分给组里健康的实例。
为什么不能用 IP容器挂掉重建之后IP 就变了。用 IP 调用等于每次重启都要改配置——这是最常见的坑。

③ 从集群外访问进来

统一入口对外暴露一个入口，按域名或路径把流量分到不同服务。证书、限流通常也放在这一层。
这题的加分点

说清"别用 IP 互调"这条实际约束，比背概念有用：

「我印象最深的一条是服务之间绝对不要写死 IP。因为容器重启之后 IP 会变，你本地测着好好的，一上线就有一半请求打不通。正确做法是用服务名——它背后是一组实例，而且会自动跳过不健康的那些。」

3. 多租户怎么部署（JR-16）

这道题问得很具体（"一个租户一个 pod 吗"），但它没有唯一答案——正确答法是按隔离要求和成本分层说。

方案怎么做什么时候用 / 代价
共享集群，逻辑隔离 所有租户跑在同一个集群里，用命名空间隔开；资源配额和权限按命名空间限制。 成本最低、最常用。适合租户多、数据敏感度一般的场景。代价是隔离不算彻底，底层资源还是共享的。
按租户分组隔离 把租户分成几组，重要客户单独一组，普通客户共享一组。每组有独立的资源池。 折中方案。适合客户之间重要程度差异大的场景——把资源花在真正的重点客户上。
一租户一集群 每个租户一套独立集群。 隔离最彻底，成本也最高。只有合规要求很严（比如数据必须物理隔离）时才这么做。
「一个租户一个 pod 吗」——这个问法本身有个前提要澄清

"一个租户一个 pod"通常是不够的，因为一个租户往往需要多个服务（前端、后端、数据库连接等），一个 pod 装不下。

更准确的说法是：一个租户对应一组资源——可能是几个 pod 加配置加存储，共享集群但逻辑隔离。

答的时候把这一点指出来，会显得你想过实际部署，而不是背了个概念。

这题的加分点

把技术选择挂到业务约束上：

「所以我的判断顺序是：先看合规要求有多严——要求物理隔离就只能独立集群；再看租户数量和成本——几百个租户一集群根本不现实；最后看租户之间的重要程度差异，差异大就分组。技术上都能做，关键是别为了隔离而隔离。」

4. 「日常用到什么程度」（YF-13）

这题是自我盘点，而且是这一域里最需要诚实的一题——说自己"很熟"，接下来就会被追问深水区。

层次能做到什么
会写配置 能写部署配置、服务配置、配置项和密钥的挂载；能看日志和事件排查为什么起不来。
会用和排障 能滚动更新、回滚、扩缩容；服务起不来时能顺着事件和日志定位到原因。
会设计和运维 能规划集群、做资源配额、设计多环境隔离和网络策略、调优调度。
套出来的样子（按你的实际填）

「我在"会写配置和排障"这个层次。项目里的部署配置是我写的，服务起不来我能看事件和日志定位原因——这类问题我处理过几次。

但集群本身的规划和运维不是我做的，那是运维同事在管。所以资源配额怎么定、网络策略怎么设计这些，我只知道有这回事，没实际做过决定。」

这个答法既说清了能力，又主动划了边界——比含糊说"会用一点"安全得多。

对方追问：「那你说说 K8s 的架构？」

这题明显是在往下探。如果你只到"会写配置"，别硬编——但也不是只能说"不知道"。

好的答法是说清你知道的那一层，并明确说出边界：

「我知道大概的分工：有一组组件负责做决策（决定该把服务放哪台机器、发现服务挂了要怎么处理），每台机器上还有一组组件负责执行（真正把容器跑起来、把状态报回去）。但具体每个组件叫什么、内部怎么交互，我没有深入看过——我平时接触的是用它的那一层。」

这个答法的好处：说对了框架（决策层 + 执行层），但明确承认没深入到组件级。比含糊其辞或者背一堆名词安全得多。

对方追问：「服务起不来，你怎么排查？」

这题很实际，答得出细节就说明你真处理过。给一个固定顺序：

  1. 先看状态和事件：是不是在反复重启、还是一直起不来、还是根本没被调度上去。事件里通常直接写着原因（镜像拉不到、资源不够、配置缺了）。
  2. 再看日志：分了"上一次挂掉之前的日志"和"当前的日志"——反复重启的情况一定要看前者，那是崩溃现场。
  3. 然后进到容器里看：有时候是应用起来了但连不上数据库、或者配置读不到，这时候要看环境变量和网络能不能通。
  4. 最后怀疑资源：内存不够被杀掉（表现是没有任何报错就重启）——这种情况日志里看不到异常，要看是不是被系统干掉的。

最后一条特别能体现经验：「最坑的是内存不够被杀——它不报错，就是安静地重启，第一次遇到会完全找不到方向。」

5. 讲解骨架（看懂之后再背）

「Docker 和 K8s 的关系 / 镜像和容器 / 服务怎么通信 / 多租户怎么部署」

【关系】它们不在一个层次，是上下层关系，不是新旧版本。Docker 解决"一个应用怎么打包成能到处跑的标准单元"，K8s 解决"一堆这样的单元怎么在多台机器上管起来"。K8s 调度的对象就是容器，没有容器这个标准单元，它也 orchestrate 不起来。

【澄清一个误解】业界有过"K8s 弃用 Docker"的说法，那说的是底层换成通用的容器运行时，不是容器不用了。容器这个形态一直都在。

【镜像和容器】镜像是只读模板，容器是它运行起来的实例，改动的部分写在镜像之上的一层——所以容器一删，里面的数据就没了。这就引出挂载：把宿主机的目录映射进去，数据卷独立于容器存在，上线重建容器时数据不丢；配置文件也可以挂进去，改配置不用重做镜像。

【服务通信】分三层：同一组容器内部走本机地址；集群内服务之间用服务名互相调用，不写死 IP（因为重启后 IP 会变，本地测着好好的上线就打不通），服务名背后是一组实例并会自动跳过不健康的；对外用统一入口，按域名或路径分流，证书和限流也放在这一层。

【多租户】这题没有唯一答案，按隔离要求和成本分三档：共享集群用命名空间做逻辑隔离——成本最低最常用，但隔离不彻底；按租户分组、重要客户单独一组；一租户一集群——隔离最彻底也最贵，只在合规要求严的时候用。

【一个要澄清的前提】"一个租户一个 pod"通常不够——一个租户往往要多个服务，一个 pod 装不下。准确说法是"一个租户对应一组资源"。

【我的程度】我在会写配置和排障这一层：部署配置是我写的，服务起不来能顺着事件和日志定位。但集群规划和运维不是我做的——资源配额、网络策略这些我知道有这回事，没实际做过决定。

【权衡】这一域的定位是"够用即可"。我不会去背组件级的细节，因为那对我的实际工作没有帮助；我更愿意把时间花在保证服务能正常部署和可排查上。

回忆卡 1 · 合上材料，用自己的话讲一遍

用一个类比说清 Docker 和 K8s 的关系，并指出一个常见误解。

讲完了，展开对照

类比可以有很多种，关键是把"一个 vs 一堆"这层关系表达出来。比如：

  • Docker 像是把家具做成标准尺寸的箱子，搬到哪都能用；K8s 像是物流调度中心，决定这些箱子放哪个仓库、坏了怎么补、怎么分配。
  • 或者：Docker 是"怎么把一个东西装好"，K8s 是"一堆装好的东西怎么管"。

然后指出那个误解："现在都用 K8s 不用 Docker 了"是错的——它们是上下层，不是新旧版。业界那次"弃用"说的是底层换成通用容器运行时，容器本身一直都在。

如果还能补一句：「K8s 调度的对象就是容器，所以严格说不是"用不用 Docker"的问题，是"用什么来跑容器"的问题。」那这道题就答满了。

回忆卡 2 · 合上材料，用自己的话讲一遍

服务起不来，你的排查顺序是什么？

讲完了，展开对照
  1. 看状态和事件：反复重启？起不来？还是没被调度上去？事件里通常直接写着原因。
  2. 看日志：注意区分"上一次挂掉前的日志"和"当前的日志"——反复重启的要先看前者，那是崩溃现场。
  3. 进容器里看：应用起来了但连不上数据库、读不到配置，要查环境变量和网络连通性。
  4. 怀疑资源：内存不够被杀掉的表现是"不报错、安静重启"——这种情况日志里看不到异常，要看是不是被系统干掉的。

最后那条是这道题里最值钱的一句——它是个"不看就找不到"的原因，说出来就证明你真踩过。

如果没实际排查过，就诚实说"我遇到过的都是配置写错这类，看事件就定位到了；更复杂的情况没处理过"。比背一个排查流程安全。
