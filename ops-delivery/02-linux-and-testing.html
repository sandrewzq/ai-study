02 · 日志排查与测试

两道题看着不相关，其实共同点是同一个：没有专职的人时，你自己怎么兜住。 一条日志命令、一套没有测试岗的质量方案。

YF-14HJ-11
读之前

这两题都需要你真做过。"我会用 grep"这种答法等于没答——对方要听的是具体的命令和顺序。术语不熟先看 00 · 先认识这几个词。

第一遍（4 分钟）只看主图，记住排查的四步顺序。
第二遍（12 分钟）读第 1、2 节，把常用命令的组合记下来。
第三遍做页尾回忆卡，把质量那套按你的项目讲一遍。

0. 先看一个场景

对方问：「线上报了一批异常，日志文件很大，你怎么查？」

两种答法

「我会用 grep 把错误的那几行找出来看看。」
——方向对，但太粗。日志几十万行、错误几千条，"看看"是看不过来的。

「我会分四步：先确认有没有——筛出错误行看有多少；再看分布——把错误信息按内容统计排序，看是不是集中在某一类；然后看规律——这些错误是不是集中在某个时间段、某个接口；最后定位到具体请求——拿一个具体的请求标识，把那一次调用的完整链路捞出来。」
——四步都在收窄范围，而不是"看"。

这道题（YF-14）的关键不在你会不会 grep，而在你有没有一个"从大到小"的排查顺序。

主图 · 查日志的四步，每一步都在缩小范围

别一上来就看具体某一条

这张图在说什么：查日志的顺序是从整体到具体——先数总量，再做分布统计找出"主要矛盾"，然后看规律，最后才捞一次完整的调用链路。

这一步的价值：日志几十万行，你不可能一条条看。做一次分布统计，往往几千条错误会收敛成三四个原因——然后你只需要看那三四个。

颜色含义： 收窄范围 定位到具体 命令示例

1. 日志怎么查（YF-14）

答这题要说出具体命令——只说"用 grep"和说出完整的统计组合，可信度差一个量级。

要做什么命令写法
实时跟踪 tail -f app.log——一边跑一边看新的输出。复现问题时用这个。
按关键字筛 grep ERROR app.log；要看前后几行就加 -A / -B，光看错误行往往看不出上下文。
按时间范围筛 用 sed -n '/起始时间/,/结束时间/p' 截一段出来。直接 grep 时间戳也行，但截区间更直观。
做分布统计 ... | awk '{print $某列}' | sort | uniq -c | sort -rn | head——这是最有价值的一条：把几万条错误按内容归类计数，排出前几名。
捞一次完整调用 用请求标识 grep 某个请求id app.log，把一个请求从进来到出错的所有日志捞出来。
这题的加分点

说清"日志本身设计得好不好，决定了排查快不快"：

「工具只解决一半问题。另一半是日志里有没有关键信息——比如每个请求有没有一个贯穿全链路的标识，出错时有没有把关键的入参和上下文打出来。

我踩过的坑就是日志里没打请求标识，结果出了问题只能靠时间戳去猜哪几条是同一个请求的，排查时间翻了好几倍。后来加上了这个标识，同样的排查几分钟就能定位。」

2. 没有测试岗怎么保证质量（HJ-11）

这题的潜台词是："没人帮你测，你怎么保证上线不出事。"答案不是"我会仔细测"，而是一套分层的机制。

① 提交前自测
固定动作：自己跑一遍主流程 + 想一遍边界情况。这一步靠清单，不靠记性——因为赶时间的时候最容易漏。
→
② 自动化测试
接口测试覆盖核心链路，单测覆盖容易写错的逻辑。这是没有人帮你测时唯一能长期依赖的东西——人会疲劳，脚本不会。
→
③ 交叉验证
让同事跑一遍，或者让别人看代码逻辑。没有测试岗不等于没人看——换个人就很容易发现你自己看不到的问题。
→
④ 上线观察
发布后盯着错误率和核心指标。出问题能在几分钟内回滚，比"保证不出问题"现实得多。
这题最该说的一句

「没有测试岗，意味着开发要为质量负全责——那就不能靠"小心"，得靠机制。」

因为"小心"是不可持续的：赶进度的时候第一个被牺牲的就是它。而自动化测试和回滚能力不会因为赶进度而消失。

另外补一句体现分寸的话：「但我也知道这套覆盖不到全部——有些交互和体验问题只能靠人试。所以关键版本上线前我会找几个同事实际用一遍，不完全依赖自动化。」

对方追问：「那你们有自动化测试吗？覆盖多少？」

这题在核实你说的"靠自动化"是不是真的。诚实回答，而且要说清"覆盖在哪"：

  • 如果有：说清覆盖的是哪部分——通常是"核心业务链路的接口测试"，而不是"全部代码"。报一个大概的比例，并说明统计口径。
  • 如果很少：「覆盖得不算多，主要是几条核心链路。剩下的靠自测和上线观察兜。」——诚实说，然后补一句你知道该往哪补。
  • 补一句判断：「我的优先级是先覆盖"出错代价最大"和"最常改动"的那两条链路——因为这两类最容易出问题，收益也最直接。」
对方追问：「那你有没有漏测过？后来怎么改的？」

这题几乎一定会被问到，而且是个加分机会——承认漏过、并说清怎么改的，比说"我基本没漏过"可信得多。

好的结构是现象 → 原因 → 改了什么：

「漏过。有一次改了一个共用的工具函数，本地测了主流程没问题，但没测到一个只在特定条件下才走的分支——上线后有个低频功能报错了。

原因不是粗心，是那个分支平时没人走，我压根没想到。后来我改了两件事：一是改共用代码时会搜一下有哪些地方在用它，把调用点都过一遍；二是给这类共用函数补了测试。」

最后补一句认知：「这件事让我意识到，漏测往往不是"没测仔细"，而是"没想到还有这种情况"——所以靠清单和测试比靠小心有用。」

3. 讲解骨架（看懂之后再背）

这一段就是答案：按顺序把这几件事讲一遍，讲不下去的地方回上面正文补。再往下的「回忆卡」是自测（先合上材料讲，再展开对照），「动手清单」是怎么落到自己项目里。

「Linux 熟不熟 / 日志怎么查 / 没有测试岗怎么保证质量」

【Linux】日常够用。用得最多的就是查日志和看进程、看磁盘和内存——这些是我自己排查问题时要用的。

【查日志的顺序】我按从整体到具体四步走：先确认有多少（grep -c 数一下）；再做分布统计——把错误按内容归类计数排序（awk 取列 + sort | uniq -c | sort -rn | head），这一步最有价值，几千条错误往往收敛成三四个原因；然后看规律，是不是集中在某个时间段或某个接口；最后用请求标识捞一次完整调用，看那一次到底发生了什么。

【一个经验】工具只解决一半问题，另一半是日志里有没有关键信息。我踩过的坑是日志里没打请求标识，出了问题只能靠时间戳猜哪几条是同一个请求，排查时间翻了好几倍；加上标识之后几分钟就能定位。

【质量：结论】没有测试岗意味着开发要为质量负全责，那就不能靠"小心"，得靠机制——因为赶进度的时候第一个被牺牲的就是小心。

【四层机制】提交前自测（按清单跑主流程 + 想边界，不靠记性）；自动化测试（接口测试覆盖核心链路、单测覆盖易错逻辑，这是唯一能长期依赖的）；交叉验证（让同事跑一遍或者看代码逻辑，换个人容易发现你自己看不到的）；上线观察（盯错误率和核心指标，出问题几分钟内能回滚，比"保证不出问题"现实）。

【漏测经历】漏过。改了一个共用的工具函数，本地测了主流程，但没测到一个特定条件下才走的分支，上线后低频功能报错。原因不是粗心，是那个分支平时没人走，我压根没想到。后来改了两件事：改共用代码时先搜有哪些调用点、都过一遍；给这类函数补上测试。

【认知】这件事让我意识到，漏测往往不是"没测仔细"，而是"没想到还有这种情况"——所以靠清单和自动化比靠小心有用。

【权衡】但我也知道这套覆盖不到全部。有些交互和体验问题只能靠人试，所以关键版本上线前我会找几个同事实际用一遍。

回忆卡 1 · 合上材料，用自己的话讲一遍

「日志文件很大，你怎么查？」——说出你的顺序和每一步的命令。

讲完了，展开对照
  1. 先数总量：grep -c ERROR app.log——先知道规模。
  2. 做分布统计：grep ERROR app.log | awk '{print $列}' | sort | uniq -c | sort -rn | head——这是最关键的一步，几千条错误会收敛成几个原因。
  3. 看规律：集中在哪个时间段、哪个接口、哪个用户。把范围从"某个错误"缩到"某个场景"。
  4. 捞一次完整调用：用请求标识把那一次的所有日志捞出来，看完整链路。

加分句：「排查快不快，一半取决于工具，另一半取决于日志里有没有打请求标识和关键上下文。」——这句话说明你从"被日志坑过"的角度想过问题。

如果只用过 tail 和 grep，就诚实说这两种，然后讲一个你真用它们定位到问题的例子。有例子比会更多命令有用。

回忆卡 2 · 合上材料，用自己的话讲一遍

「没有测试岗，你们怎么保证质量？」——说出你的四层机制，并指出哪一层最重要。

讲完了，展开对照
  1. 提交前自测：按清单跑主流程、想边界。靠清单不靠记性。
  2. 自动化测试：覆盖核心链路和易错逻辑。
  3. 交叉验证：让同事跑一遍或看代码。换个人容易发现你自己看不到的。
  4. 上线观察：盯指标、能快速回滚。

最重要的是第二层——因为它是唯一不依赖"当时状态好不好"的一层。人会疲劳、会赶进度、会想当然，脚本不会。

核心那句话："没有测试岗意味着开发要为质量负全责，那就不能靠小心，得靠机制。"

最后别忘了主动说边界：「不过这套覆盖不到全部，有些体验问题只能靠人试，所以关键版本上线前我会找同事实际用一遍。」
