05 · Canvas 与动效实战

这一组题表面在问"你会不会 Canvas"，实际在问两件事：你知道什么时候该用它吗， 以及那些效果你到底是自己写的，还是只知道有这么回事。

读之前

需要知道 DOM 是什么、元素是怎么画到页面上的。Canvas 完全没碰过也没关系——这一页的重点是选型判断，不是 API 细节。术语不熟先看 00 · 先认识这几个词。

第一遍（4 分钟）只看主图，记住"元素少用 DOM、元素多用 Canvas"。

第三遍做页尾回忆卡，然后挑一个你做过的动效，说清它每一层是怎么实现的。

0. 先看一个场景

要做一个"新年红包雨"的活动页：屏幕上飘落几百个金币，用户点一下金币有爆开效果。

你第一反应可能是用 DOM：给每个金币建一个 div，用 CSS 动画让它往下飘。

几十个还行，几百个就开始卡了。手机上一测，掉帧掉得厉害。

换成 Canvas 之后，同样的视觉效果，几百个元素照样流畅——因为这时候页面上只有一个元素，其他的都是画上去的像素。

这一页讲的就是这类判断：什么时候该用 DOM，什么时候该用 Canvas。

主图 · 选型的唯一标准：元素数量和交互复杂度

DOM 是「每个元素都是一个对象」，Canvas 是「一张画布，自己往上画」

这张图在说什么：DOM 把每个东西都变成一个有身份的对象——能单独绑事件、能被搜索、能被读屏；Canvas 只在页面上放一张画布，里面全是像素，画什么、画在哪、谁被点到了，全得你自己算。

所以选型不是"哪个更高级"，而是你要不要那些"身份"：需要就给 DOM，不需要又量大，就上 Canvas。

颜色含义： DOM 路线 Canvas 路线 判断维度 各自的代价

1. 「Canvas 做过什么场景」（SH-5、SH-6）

这两题是一组。答的时候不要只报项目名，要说清"为什么这里非用 Canvas 不可"——那才是对方想听的。

场景为什么用 Canvas如果改用 DOM 会怎样
活动动效
金币雨、粒子、烟花		 元素数量极大且彼此独立，用 Canvas 一次画完，只有一次绘制开销。 几百上千个节点，浏览器要维护、要参与布局计算，直接掉帧。
数据图表
折线、热力图		 需要像素级控制和精细的坐标计算，元素数量也随数据量增长。 数据点多的时候，节点数量同样爆炸；而且画斜线、曲线很别扭。
图片处理
裁剪、滤镜、加水印		 直接操作像素，可以把结果导出成图片。 DOM 根本做不了像素级操作。
白板 / 无限画布
见第 4 节		 画布可以无限大，但只渲染视口内的部分。 无限大的 DOM 区域放不下那么多节点。
不要这样说

❌ "Canvas 性能比 DOM 好，所以我们用了 Canvas。"

这句话听起来就不像真做过——因为 Canvas 有明确的功能代价（不能绑事件、不能被读屏、不能被搜索）。真实项目里没人会为了性能把整个页面都换成 Canvas。

✅ 应该这样说："这个模块是纯装饰性的，用户不需要点它里面的东西，也不需要被搜索到，所以我们把它放进了 Canvas；外面的按钮和文字仍然是 DOM。"

2. 「红包动画是怎么做的」（SH-7、SH-8）

这两题几乎是绑在一起问的：先问整体怎么做，再追一句"打开那个动作是画出来的还是图片"。第二问才是关键——它在探你是不是真做过。

先给结论：绝大多数商业项目的红包打开动效，用的是设计给的序列帧或矢量动画文件，不是前端用代码画出来的。

原因是成本：手绘级别的动效（红包撕开、金币迸射、绸带飘动）如果用代码画，工作量极大且还原不了设计稿。前端在这里的角色是"播放器"，不是"画家"。

做法怎么实现什么时候用它
纯 CSS 变换 + 关键帧：缩放、旋转、抖动、阴影变化 简单反馈：按钮按下缩小、卡片抖动、悬停浮起。这是自己写的那部分。
序列帧 设计输出一组连续图片，前端按固定帧率一张张切换 手绘感强的连续动作（撕开、爆破）。缺点是要下载一堆图，体积大。
矢量动画文件
设计工具直接导出		 播放一个 JSON 描述，前端用播放器渲染，可以缩放不失真 目前最主流的做法。体积小、能动态换色改文案，设计改稿也方便。
Canvas 粒子 自己算每个粒子的位置、速度、生命周期，逐帧重画 数量大、规则简单的部分：金币雨、星光。这部分是自己写的。
这题的加分点

答清"分工"，可信度立刻不一样：

「红包的打开动作是设计给的一版矢量动画，我们用播放器渲染——因为手绘质感的连续动作用代码画不现实，而且还原不了设计稿。周围的氛围（飘落的金币、点击迸射的粒子）是我们用 Canvas 写的，这部分规则简单、数量大，自己写反而更好控制。另外按钮的按下反馈就是普通的 CSS 变换。」

这一句同时交代了三层：设计资产、Canvas 粒子、CSS 反馈——一听就是真做过的人。

对方追问：「那序列帧和矢量动画文件，你怎么选？」

给两三条实际标准就够，不用背参数：

  • 体积：序列帧是一堆图片，动辄几兆；矢量动画就是一个文本文件，通常几十到几百 KB。移动端和弱网下这一点往往是决定性的。
  • 能不能改：矢量动画可以运行时换颜色、换文案，不用重新找设计出图；序列帧改一个像素都得重新导一遍。
  • 还原度：如果设计效果特别写实（复杂的光影、纹理），矢量格式可能还原不了，这时候只能用序列帧。

一句话：「默认用矢量动画，只有矢量还原不了才退到序列帧，同时算好体积预算。」

3. 「打开 / 抖动 / 浮动 / 阴影 / 缩放做过吗」（SH-9）

这题列了五类效果，它其实在给你递梯子——你只要挑做过的说，说清怎么实现就行。这五类全部可以用 CSS 变换和关键帧搞定，正好接上上一份。

效果怎么实现要注意什么
缩放 改 transform: scale()，配合过渡 便宜属性，不会影响旁边元素位置。按下反馈最常用。
抖动 关键帧里让位移在左右（或上下）之间来回几次，最后归零 抖动幅度要小、要快，并且一定要有终点——不然会看起来像卡住了。
浮动 关键帧里做小幅上下位移，设置成无限循环 + 来回交替 循环动画要避免所有元素同步，否则几十个东西一起动会很假；给每个加一点随机延迟。
阴影 改 box-shadow，或者配合缩放做"浮起来"的感觉 box-shadow 属于需要重新绘制的属性，比变换贵。元素多的时候慎用，可以用伪元素 + 透明度代替。
打开 简单的是旋转+缩放组合；复杂的手绘动作见上一节 要区分"简单开盖"和"手绘爆破"——前者能自己写，后者得用设计资产。

4. 无限画布怎么实现（KJ-3）

这道题是这一组里最能拉开差距的。它不考 API，考的是你脑子里有没有坐标系这个概念。

先说清楚"无限"是什么意思：画布并不是真的无限大，而是"你永远走不到边"——因为只有视口里能看到的部分会被真正渲染出来。

① 两套坐标系
世界坐标是元素在画布里的真实位置，固定不变；屏幕坐标是它此刻显示在屏幕哪里。两者之间靠平移量和缩放倍数换算。
→
② 平移靠改偏移
拖拽时不去动每个元素，只改整个画布的偏移。所有元素的位置关系不变——这就是"视口移动"而不是"元素移动"。
→
③ 缩放要绕指针
滚轮缩放时，要让鼠标指着的那个点保持不动，否则用户会觉得画面在乱跑。做法是先算出指针在世界坐标里的位置，缩放后反推需要补偿多少偏移。
→
④ 只渲染看得见的
这是"无限"的关键：先算出当前视口覆盖的世界坐标范围，只渲染范围内的元素。缩放很小时，上万个元素里可能只有几十个需要画。
这题的加分点

答完上面四步已经不错了，再补一句性能上的进阶做法就很完整：

「元素特别多的时候，遍历全部元素来判断"谁在视口里"本身就很慢。这时会用空间索引——比如把画布切成网格，或者用树形结构按区域组织元素，这样就能直接查出视口覆盖的那几块，不用逐个判断。」

再补一句实现选型：「DOM 方案是把所有元素放进一个容器、整体做变换，配合虚拟化只挂载可见的；Canvas 方案是自己算坐标逐帧重画。前者省事、能复用 DOM 的交互，后者能扛更大的数量。」

对方追问：「缩放的时候画面为什么会飘？怎么解决？」

这是真实做过的才会遇到的问题，答对了非常加分。

现象：直接改缩放倍数，画面会以画布左上角为中心缩放——你鼠标在右下角，结果右下角的东西跑掉了。

原因：缩放默认围绕原点。用户的心理预期是"以我指着的点为中心"，两者不一致。

解决：分三步算——先把鼠标的屏幕坐标换算成世界坐标（记住这个点）；改完缩放后，再把它换算回去，看它偏移了多少；把这个偏移补回平移量。这样那个点在屏幕上就没动过。

对方追问：「画布上的元素怎么知道被点中了？」

这是 Canvas 的固有代价——元素不是节点，浏览器不提供"点击检测"。两种做法：

  • 自己算碰撞：把点击的屏幕坐标换算成世界坐标，然后遍历元素判断点是否落在它的范围内。元素多时要配合空间索引，否则很慢。
  • 用现成的库：成熟的 Canvas 绘图库都内置了"图形对象 + 命中检测"，你按对象的方式用，它内部帮你算。项目里通常直接用库，不自己造。

如果能补一句曲线救国的做法就更完整："有些交互复杂的场景，会把可交互的部分用 DOM 叠在 Canvas 上层——Canvas 负责画，DOM 负责接事件。"

5. 讲解骨架（看懂之后再背）

这一段就是答案：按顺序把这几件事讲一遍，讲不下去的地方回上面正文补。再往下的「回忆卡」是自测（先合上材料讲，再展开对照），「动手清单」是怎么落到自己项目里。

「Canvas 用过吗 / 做过什么场景 / 无限画布怎么实现」

【结论】用过。选型标准我一般看两点：元素数量和要不要单独交互。数量大、又不需要逐个响应事件、也不需要被搜索和读屏的，用 Canvas。

【场景】主要用在纯装饰性的大批量动效上，比如活动页的飘落物和点击迸射的粒子——几百个元素用 DOM 会掉帧，用 Canvas 只有一次绘制开销。页面上的按钮和文字仍然是 DOM，因为它们需要能被点击、被搜索。

【红包这类动效】要分三层说：手绘质感的打开动作用设计给的矢量动画文件播放，我们只做播放器；氛围粒子用 Canvas 自己写；按钮反馈就是普通的 CSS 变换。做不出来的不是技术问题，是美术资产问题。

【无限画布】核心是两套坐标系：世界坐标固定、屏幕坐标随视口变，中间靠平移量和缩放倍数换算。拖拽改的是整个画布的偏移；缩放要绕指针做，否则画面会飘；渲染时只画视口范围内的元素，元素极多时再配合空间索引来加速查询。

【权衡】Canvas 的代价是失去 DOM 的那些能力——不能单独绑事件、不能被读屏、不能被搜索，命中检测也得自己算。所以我的原则是：能用 DOM 就用 DOM，只有数量和像素级控制这两个理由成立时才上 Canvas。

回忆卡 1 · 合上材料，用自己的话讲一遍

要做"页面上飘落 300 个雪花"，你选 DOM 还是 Canvas？说出你的判断过程。

讲完了，展开对照
  1. 先看数量：300 个已经超出 DOM 舒服的范围了。经验上几十个以内 DOM 没问题，几百个就要警惕。
  2. 再看交互：雪花需要被单独点击吗？如果只是装饰，答案就明确了。如果要做"点雪花得分"，那要么自己算命中检测，要么给其中少数可交互的元素单独叠 DOM。
  3. 再看无障碍和搜索：雪花需要被搜索或被读屏识别吗？不需要。
  4. 结论：用 Canvas，元素数量是决定性因素。

如果再加一句就更完整："雪花是不规则图形、还要各自旋转，用 Canvas 画反而比用图片更省——不用下载 300 张图，也不用为每个元素创建节点。"

回忆卡 2 · 合上材料，用自己的话讲一遍

有人问你"无限画布是不是真的无限大"，你怎么解释？

讲完了，展开对照

不是真的无限，是"感觉不到边界"。

关键在渲染策略：任何时刻只有视口里那一片会被真正画出来。你把画布拖到很远的地方，之前那一片就不渲染了，新的那一片才开始渲染。所以内存和性能只和"当前看得见多少"有关，和"总共能走多远"无关。

实现上要三样东西配合：

  • 坐标系换算：元素存在世界坐标里（固定），显示时换算成屏幕坐标。
  • 视口裁剪：只渲染落在视口范围内的元素。
  • 空间索引：元素很多时，用网格或树形结构快速查出"视口里有谁"，避免每次遍历全部。

一句话："无限"是效果，实现上是"只画看得见的那一块"。
