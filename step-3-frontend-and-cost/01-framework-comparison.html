01 · 框架选型：Vue 与 React

这一页解决一个问题：被问"Vue 和 React 有什么区别"时，怎么答得不像背的。 这道题不难，但答成"一个是模板一个是 JSX"就浪费了——它其实是道设计哲学题。

FN-1FN-2FN-3HQ-1SH-33
读之前

这一页假设你写过 Vue 或 React 中的至少一个。如果两个都只跟着教程写过 todo list，先补 00 · 先认识这几个词，再回来看。

第一遍（4 分钟）只看主图，抓住"谁在替你做决定"这一条。
第二遍（12 分钟）读第 2、3 节——区别和性能上限是真正会被追问的。
第三遍做页尾回忆卡，用你自己的项目举例讲一遍。

0. 先看一个场景

对方翻着你的项目，随口问了一句：「你 React 用得多，还是 Vue 用得多？」

这是个送分题，也是个陷阱题。

答「Vue 多」结束了——对方只能接着问下一个。但如果你的项目写的是 Vue，你又答「React 多」，那就等于自己给对方递了把刀：那你项目里那套东西是怎么写的？

正确的答法是：先说清楚你的主战场，再用一句话讲明白两者的本质区别，最后落到"所以我当时为什么选它"。这样一句话就把话题从"你熟不熟"引到了"你会不会做技术决策"。

主图 · 两者的真正区别只有一条

框架替你做的决定，多还是少

这张图在说什么：Vue 是「响应式」的——你改数据，它自动知道哪里变了，只更新那一小块；React 是「快照」的——你重新描述整个界面，它自己比对出哪里不一样。

这个底层差异往下推，就带出了模板 vs JSX、官方全家桶 vs 自己选生态、编译时优化 vs 运行时调度这一整串区别。别去背那一串，记住源头就够了。

颜色含义： Vue 路线 React 路线 由底层差异推出的结果

1. 回答这道题的三句话结构

被问区别时，不要一口气列十条。用这个结构，三句话就够，而且每句都能接追问：

顺序说什么为什么这么说
先说结论 本质区别是「谁负责知道哪里变了」：Vue 靠响应式自动追踪，React 靠你重新描述、它来比对。 一句话把话题从"背知识点"抬到"讲设计取向"，后面所有细节都能挂在这句话上。
再说表现 这个差异带来的直接结果是：Vue 写得少，React 管得多。Vue 语法更收敛、上手快；React 更自由、但要自己做更多决策。 把抽象差异翻译成"写代码时的体感"，对方一听就知道你真用过。
最后落到自己 结合你的项目：我当时用 X，是因为 Y（团队已有基础 / 需要服务端渲染 / 只是做个中后台）。 这一句是把话题引向"你会做技术决策"的关键，不要省。
「写得少」具体少在哪

举两个能立刻说出口的例子，比空讲"更简单"有说服力：

  • 表单双向绑定：Vue 写 v-model 一行；React 要写 value + onChange 两个属性，还要自己处理取值。
  • 依赖收集：Vue 里把数据放进模板或 computed，它自动就追踪了；React 里你得理解"闭包捕获的是哪一次渲染的值"，否则会踩到「拿到旧值」的坑。

反过来说，React 的"自由"也不是空话：状态放哪、什么时候重渲染、要不要手动 memo，这些都是你来定。定得好性能上限更高，定不好就一卡一卡的。

2. 「谁性能上限更高」——这是道送命题

这道题（FN-2）没有标准答案，但有三种答法，只有一种不扣分：

❌ 「Vue 更快」/「React 更快」

直接给结论不管说哪个，对方只要追一句"为什么"就接不下去了。而且这个结论本身就是错的——两者在常见场景下都够快。

⚠️ 「都差不多」

和稀泥不算错，但等于没答。对方会觉得你没有判断。

✅ 「看场景，而且取决于优化能力」

常见场景Vue 的编译时优化让它默认就快：模板在编译阶段就能标记出"哪块是静态的、哪块会变"，运行时跳过大量比对。不动手优化的情况下，Vue 通常更容易跑到好成绩。
极端场景React 的运行时调度能力强——它能把一次大更新拆成很多小片，穿插着响应用户输入（就是所谓的"并发渲染"）。数据量极大、又必须保证输入不卡时，React 有更大的优化空间。
更重要的半句"但真正决定性能的，是有没有人认真优化——列表有没有做虚拟滚动、有没有乱重建对象导致全量重渲染。这些做不好，用哪个框架都慢。"
这题的加分点

"这个问题的答案取决于你在哪个层面比。如果比'不优化能跑多快'，Vue 因为编译期做了静态分析，通常更占优；如果比'优化后的天花板'，React 的调度能力给了更大的空间。"

把"性能"拆成"默认表现"和"优化上限"两个维度——这一下就把一道没有答案的题，答成了一道有结构的题。

3. 「最新版本在做什么」（FN-3）

这题考的是你有没有持续跟进，不是考你背版本号。所以说方向比说版本号重要——版本号说错很尴尬，方向说错才是真问题。

框架大方向怎么说得像真在用
Vue 继续压榨编译时的能力 "Vue 这几年的主线一直是把更多工作放到编译阶段——静态提升、补丁标记都是这个思路。再往前是探索不依赖虚拟 DOM 的编译模式，官方叫 Vapor Mode，思路是把响应式直接编译成精确的 DOM 操作。"
React 继续强化运行时调度 + 把优化自动化 "React 这边最近两块：一是服务端组件，把一部分渲染放回服务端，减少传到浏览器的 JS；二是编译器，目标是让你不用手写那些 memo 优化，它自动帮你加。方向都是'让开发者少操心性能'。"
说错版本号的代价

版本号记不准就模糊着说："大概从 3.4 之后"「最近一两个大版本」——没人会揪这个。

但不要说反方向。比如把 Vue 说成"也在搞并发渲染"，或者把 React 说成"主要靠编译优化"——这会让对方判断你只是看了两篇公众号。

4. 剩下两道零散的题

题怎么答
你哪个用得多（SH-33） 如实说，然后补半句另外一个的情况。例："Vue 是我的主战场，项目从 2 到 3 都是我做的；React 我写过一些，主要用来做独立的小工具，所以生态那套（路由、状态管理怎么选）我知道大概但不常做决策。"
不要硬撑两边都精通——追两个细节就露了，而且显得不稳。
NextJS 用得多吗（HQ-1） 如果用过，就讲你用它解决了什么："我们的文档站要做 SEO，纯前端渲染抓不到内容，所以用了它的服务端渲染。"
如果没用过，别硬编，说："我目前项目是纯前端渲染，没有 SEO 需求所以没上；我知道它主要解决首屏和 SEO，也支持把一部分渲染放服务端。"
关键是说清"解决什么问题"，而不是背特性列表。

5. 讲解骨架（看懂之后再背）

「Vue 和 React 有什么区别 / 你更熟哪个」

【结论】我两个都用过，主力是 Vue。它们的本质区别是"谁负责知道哪里变了"——Vue 靠响应式自动追踪依赖，React 靠你重新描述界面、它来比对差异。

【展开】这个差异往下推，就是模板对 JSX、官方全家桶对自由选生态、编译时优化对运行时调度。

【性能】比性能要看层面：不优化的情况下 Vue 通常更占优，因为它在编译阶段就能标出静态内容；优化上限上 React 空间更大，它的调度能把大更新拆片。但真正决定性能的是有没有做虚拟滚动、有没有避免无谓的重渲染。

【自己的项目】我项目用 Vue 3，选它是因为团队已有基础、而且主要是中后台场景，开发效率比极致性能更重要。响应式那套我用得比较熟，包括 2 和 3 的实现差异。

【权衡】如果重来一次、且要做 SEO 或需要服务端渲染，我会认真考虑 React 那一套。选型不是选"更好的框架"，是选更匹配当前约束的。

对方追问：「那 React 的 hooks 你了解吗？」

这多半是在验证你刚才说的"写过一些"是不是真的。诚实回答，但要把你知道的那部分说实：

  • 说清它的目的：让函数组件也能有状态和副作用，替代了以前的 class 组件写法。
  • 说出最常用的一两个：useState 管状态、useEffect 管副作用，以及依赖数组决定它什么时候重跑。
  • 如果能说出一个真实的坑，可信度会陡增：比如"useEffect 依赖数组漏了一项会导致拿到旧值，早期踩过"。

不要不懂装懂。被追问到"手写一个 useDebounce"这种程度，硬编会翻车得很难看；直接说"这类自定义 hook 我写过简单的，复杂的不敢说熟"反而安全。

对方追问：「那你觉得新项目该选哪个？」

这是一道没有正确答案、但能看出判断力的题。答的时候围绕三条约束展开：

  • 团队：现有成员熟哪个？招人好不好招？这一条通常权重最高。
  • 场景：要不要 SEO / 服务端渲染（偏 React 生态成熟）、是不是中后台（偏 Vue 上手快）、要不要跨端。
  • 生态：Vue 官方把路由和状态管理都给了，省选型；React 每样都要自己挑，灵活但费决策。

一句话收尾："没有更好的框架，只有更匹配当前约束的。"

对方追问：「虚拟 DOM 到底快不快？」

这是个反直觉的点，能答对很加分：

虚拟 DOM 不是因为它比直接操作 DOM 快——直接操作理论上更快。它的价值是"让你不用自己算哪里变了"：你重新描述整个界面，它比对出最小改动，然后只改那些地方。

比对手写的 DOM 操作，它多了一层比对开销，但比"整块重新渲染"快得多，而且把"什么时候该更新"这个难题从人手里拿走了。

再补一句就完整了：Vue 3 的思路是"能编译出来的就别留到运行时比对"——静态内容直接提升出去，动态部分打标记，等于把一部分虚拟 DOM 的开销省掉了。

回忆卡 1 · 合上材料，用自己的话讲一遍

用一个具体例子，说明 Vue 和 React 在「数据变了之后」的处理有什么不同。

讲完了，展开对照

假设页面上有个计数器，点了按钮要 +1：

  • Vue：你直接写 this.count++。这个 count 是被追踪过的，它一变，框架就知道"模板里用到它的那几处"需要更新，只改那几处。
  • React：你调 setCount(count + 1)。整个组件函数重新执行一遍，生成一份新的界面描述，框架拿新的和旧的比对，找出差异再去改 DOM。

一句话概括：Vue 是"数据活着，框架盯着它"；React 是"你重新描述，框架帮你比"。

顺带能说出代价就更好了：Vue 的代价是数据要经过处理才能被追踪（所以有那些"数据变了视图没变"的坑）；React 的代价是你要理解"每次渲染都是一个快照"，否则会踩到闭包拿旧值的问题。

回忆卡 2 · 合上材料，用自己的话讲一遍

「Vue 和 React 谁性能更好？」——列出你的答法结构。

讲完了，展开对照
  1. 先否掉二选一："这个问题要看在哪个层面比，不能直接给结论。"
  2. 默认表现：Vue 的编译时优化（静态提升、补丁标记）让它不额外优化就更容易快。
  3. 优化上限：React 的调度能把一次大更新拆成小片、保证输入不卡，极端场景空间更大。
  4. 落到真正决定因素：列表有没有虚拟滚动、有没有避免无谓重渲染、有没有乱建对象——这些做不好，用哪个都慢。
  5. 收尾：所以选型时性能通常不是第一权重，团队熟练度和场景匹配更重要。

关键在第四步：把话题从"框架之争"拉回"工程实践"，这是拉分的地方。
