03 · 响应式失效与排查

「数据改了但页面没变」是前端最常见的 bug，也是能直接看出你有没有真做过项目的题。 这一页给的不是知识点，是一套能照着走的排查顺序。

SH-37SH-38SH-39
读之前

这一页建立在上一份（Vue 响应式原理）之上。如果还不清楚 defineProperty 和 Proxy 的区别，先回去看那份，否则这页的排查顺序你只能背下来、理解不了。

第一遍（4 分钟）只看下面那棵树，记住排查的顺序。
第二遍（12 分钟）读每一层"为什么"，把顺序变成理解。
第三遍回忆卡里有一个真实场景，先自己走一遍排查再展开。

0. 先看一个场景

用户反馈："点了已读，红点没消失。"

你打开代码，找到那行：this.list[0].read = true;。加了 console.log，确认执行到了，值也确实变成 true 了。

于是卡住了——数据明明变了，为什么页面不动？

这时候大多数人的做法是开始猜：是不是要加 $forceUpdate？是不是 key 写错了？然后一个个试过去，试到某个能用了就收工——但并不知道为什么。下次遇到换个样子，还是不会。

这道题（SH-39）真正想看的，是你有没有一套固定顺序，而不是你能不能猜对。

主图 · 照着这个顺序走，不要跳步

四层往下筛：每一层排除掉一半可能

这张图在说什么：这四层是按"发生的先后顺序"排的——先确认数据变了没，再看改的方式对不对，再看模板有没有依赖，最后才怀疑渲染和样式。

大部分人卡住是因为直接从第四层开始猜（试 $forceUpdate、改 key），跳过了前三层。按顺序走，通常两分钟就能定位。

颜色含义： 排查步骤 最常见的失效原因 结论

1. 第 ② 层：什么算「响应式地改」

这是绝大多数 bug 的所在层，也是 SH-38 那道题问的东西。判断标准只有一条：这次修改有没有经过框架能感知的路径。

写法Vue 2Vue 3说明
obj.key = 1
改已有属性		 ✅ 响应 ✅ 响应 两者都支持，这是最常见的写法。
obj.newKey = 1
新增属性		 ❌ 不响应 ✅ 响应 Vue 2 要在初始化时就装好监听器，事后新增的没有；得用 $set。
delete obj.key
删除属性		 ❌ 不响应 ✅ 响应 同上。
list[0] = 'x'
数组下标赋值		 ❌ 不响应 ✅ 响应 Vue 2 靠重写数组方法来感知变化，下标赋值不经过任何方法；要用 splice 或 $set。
list.length = 0
改数组长度		 ❌ 不响应 ✅ 响应 同理。Vue 2 里清空数组要用 splice(0)。
this.list = [...]
整体替换		 ✅ 响应 ✅ 响应 前提是这个字段本身是响应式的。很多人以为"整体替换最保险"，其实它和上面几条是两个维度。
Vue 3 里还有一类坑：解构

Vue 3 用 reactive 包了对象，然后解构取值：

看起来没问题

const { count } = state;　→　之后改 count 不影响 state.count

原因是：解构拿到的是某一刻的普通值，不是代理。代理那层被丢掉了，后面的修改自然和框架无关。

解法是用 toRefs 把每个字段转成"保持连接的引用"，或者干脆不解构、始终写 state.count。

2. 第 ③ 层：模板没用到，就永远不更新

这一层容易被忽略，但很好判断：你改的那个数据，在当前模板（或计算属性、侦听器）里被读到了吗？

响应式的工作方式是"读到才记一笔"。如果某个字段从没被渲染逻辑读过，它变了也不会触发任何更新——这不是 bug，是设计如此。

常见的三种踩法：

场景为什么会这样
数据放在组件里，但渲染用的是另一份拷贝 你改了 A，模板读的是 B。常见于"初始化时把接口数据复制了一份"。要么直接用响应式那份，要么改完记得同步。
数据在子组件里改，但父组件没监听 子组件改了 prop 对应的副本，父组件那份没动。正确做法是通知父组件改，而不是自己改副本。
只在mounted里读了一次，之后靠 JS 直接改 DOM 绕过框架改 DOM，框架不知道，下次渲染会把它覆盖回去。这是"改了闪一下又变回来"的典型原因。

3. 第 ④ 层：渲染了但你看不见

走到这一层说明响应式是好的，问题在别处。常见四类：

条件渲染挡住了
外面套着 v-if，条件没成立，整个块根本没渲染。改了里面的数据当然没反应。
→
被缓存了
列表用了 key 做复用，或者组件被 keep-alive 缓存。数据换了但复用了旧节点。key 用下标是经典错误——删掉中间一项后，后面的项全都错位复用。
→
样式把它藏了
DOM 确实更新了，但被别的元素盖住、透明度为 0、或者高度为 0。用调试面板看一眼节点内容就知道。
→
第三方库接管了这块 DOM
图表库、富文本编辑器这类会自己管理 DOM。它们渲染过之后，框架的更新可能被覆盖。解法是让它们跟着数据重绘，而不是指望框架改它们。

4. Vue 3 做了哪些优化（SH-37）

这道题问的是整条链路，不只是响应式。分两层答，条理立刻就出来了：

层面做了什么解决了什么
数据层 用 Proxy，并且用到哪一层才代理哪一层 初始化时不用把所有层级都递归处理一遍，大对象启动更快；同时把上一节那批"改不到的写法"全都覆盖了。
渲染层
编译阶段完成		 静态提升：模板里不变的部分只创建一次，之后复用 不用每次渲染都重新创建这些节点。
补丁标记：编译时就标出"这个节点会变、变的是文字还是属性" 更新时跳过静态节点的比对，直奔该改的地方，省掉大量比对开销。
事件缓存：绑定的事件函数缓存复用，不每次重建 减少无谓的函数创建和比对。
打包层 功能拆成按需引入的模块，没用到的会被摇掉 运行时体积更小，首屏更快。
这题的加分点

大多数人的答案是"用了 Proxy，所以更快"——这个答案只对了一小半。

更好的答法：「Vue 3 的提速主要来自编译阶段：静态提升和补丁标记让它在编译期就知道哪里会变，运行时可以跳过大量比对。Proxy 解决的是"能不能感知变化"的问题，不是"快不快"的问题——反倒是它在单次读写上多了一层拦截开销。」

5. 讲解骨架（看懂之后再背）

「数据变了视图没更新，你怎么排查」

【结论】我会按四层顺序查，不跳步：数据变没变 → 改的方式对不对 → 模板有没有用到 → 渲染了是不是被挡住。每往下一层，可能性就少一半。

【第一层】先确认数据真的改了。很多人卡在这里——以为是响应式问题，其实是赋值那行根本没执行（异步没回来、条件没进）。

【第二层】这是绝大多数问题的所在。判断标准是"这次修改有没有经过框架能感知的路径"。Vue 2 里下标赋值、改长度、增删属性都绕开了监听；Vue 3 里这几种基本没了，但多了解构丢响应性这个坑。

【第三层】数据改了、改的方式也对，但模板从没读过它，依赖没收集，自然不更新。常见于"渲染用的是另一份拷贝"。

【第四层】如果 DOM 确实更新了只是看不见，那就和响应式无关了：条件渲染、`key` 复用、样式遮挡、或者第三方库接管了这块 DOM。

【数字/经验】实际项目里我遇到最多的是第二层——Vue 2 老代码里给列表项补字段，直接点上去，红点不消失；换成 $set 就好了。定位花了不到两分钟，因为按顺序走的，没有靠猜。

【权衡】不建议一上来就用强制刷新那种粗暴手段——它能"修好"现象，但会掩盖真正的依赖问题，而且让后续渲染变慢。先定位，再决定要不要绕。

对方追问：「为什么会设计成这样？不能一开始就把所有情况都覆盖吗？」

这是个好问题，答好了能显出你理解取舍：

  • 能力所限：Vue 2 用的那个 API 只能对已存在的属性定义读写拦截，它没有"监听对象结构变化"的能力。这不是设计者偷懒，是当时语言层面只有这个工具。
  • 代价问题：就算能，也未必值得。遍历得越深、初始化越慢。Vue 2 对深层次的大对象启动慢，就是这个原因。
  • 所以 Vue 3 换了工具：新工具能在对象这一层拦截，结构变化自然就覆盖了，而且能做成"用到才代理"。

收尾："框架的很多限制，都是它诞生那个年代的技术约束留下的痕迹。"这句话能显出你不是只会用 API。

对方追问：「那 React 有类似的问题吗？」

有，但形态不同，能说清区别很加分：

  • React 没有"监听数据"这回事，它靠你主动调更新函数触发重渲染。所以不存在"改了但框架不知道"——你改的如果是普通变量，它压根不会重渲染，这反而是更直白的表现。
  • React 的经典坑是另一个：直接改原对象/数组（list.push(x)、obj.a = 1）之后调更新函数，因为引用没变，比对时被认为"没变"，可能跳过更新。所以 React 里要返回新对象（展开运算符那套）。

一句话对比：Vue 的问题是"改的方式框架看不见"，React 的问题是"引用没变所以框架认为没改"。

回忆卡 1 · 合上材料，用自己的话讲一遍

同事说"我改了 this.userInfo.name，页面没变"，但你看了代码，userInfo 是 data 里定义的、name 也是初始化时就有的。这时候你怎么查？

讲完了，展开对照

注意：这个场景已经排除了第二层最典型的那批原因（不是新增属性、不是下标赋值），所以更要按顺序走：

  1. 先确认数据真变了：打印一下 userInfo.name。有可能代码根本没执行到，或者异步还没回来。
  2. 看改的是不是同一份数据：经常是 userInfo 被整体替换过，或者模板里绑的是父组件传进来的那份，你改的是本地那份。这一层最容易中招。
  3. 看模板读到了没：模板里是不是写了 userInfo.name？如果只在某个 v-if 分支里、而那个分支没渲染，那它压根没被读到。
  4. 看是不是渲染了但看不见：节点内容变了但被样式或兄弟元素盖住。

如果四层都不是，再考虑异步更新队列的问题——数据改了但渲染还没轮到，此时立刻去读 DOM 会拿到旧值，要用等待更新完成之后再读。

回忆卡 2 · 合上材料，用自己的话讲一遍

Vue 2 里清空一个列表，下面三种写法哪种能触发更新？为什么？
list = []　/　list.length = 0　/　list.splice(0)

讲完了，展开对照
  • list = [] —— ✅ 可以。这是给 list 这个字段本身赋值，而这个字段是初始化时就定义好的响应式属性，所以能被感知。注意：前提是它得是 data 里的字段。
  • list.length = 0 —— ❌ 不行。改长度不经过任何被重写的数组方法，框架收不到通知。
  • list.splice(0) —— ✅ 可以。splice 是被重写的 7 个方法之一，调用后框架会收到通知。

这题的关键区分是："改字段本身"和"改数组内部"是两条不同的路径。前者天然响应，后者要看有没有走那几个被重写的方法。
