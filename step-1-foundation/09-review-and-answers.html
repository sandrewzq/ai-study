1. 口述模板：五段式

绝大多数技术题都能套这个结构，能套住 80% 的题：

【结论】    一句话给出核心判断（先给答案，别铺垫）
【做法】    你项目里具体怎么做的（要有技术名词和流程）
【数字】    量化的结果（数据量、延迟、命中率、成本降幅）
【坑】      你踩过的一个真实的坑（这是可信度的来源）
【权衡】    为什么这么选、代价是什么、边界在哪（这是分差的来源）
三档话术的区别
  • 60 分：只说得出【结论】——"因为要分工，每个 Agent 负责一个职能。"
  • 80 分：能说【结论 + 做法 + 数字 + 坑】——"我们拆了三个 Agent，拆之前上下文混着调研笔记，越到后面想法越飘……"
  • 100 分：还能说【权衡】——"但拆不是免费的，通信成本和状态一致性都是代价，所以只在子任务需要不同上下文或可并行时才拆。"

2. 自查题 · RAG 部分（10 题）

每题先自己讲 1~2 分钟并录音，讲完再展开。

① RAG 解决哪三个问题？它和微调怎么分工？

三个问题：模型不知道（私有知识）、模型记不住（知识过时）、模型会瞎编（幻觉）。第三个在严肃场景里最关键，因为 RAG 天然带出处、可溯源。

分工：RAG 教它"说什么"（知识），微调教它"怎么说"（格式、风格、术语习惯）。两者不冲突、可叠加。常见误区是拿微调灌知识——更新要重训、还照样会编。

② chunk 切太大和太小各会出什么问题？

太大：向量语义被稀释（关键信息占比小、相似度算不准、召不回）；侥幸召回了也是噪声干扰生成；浪费上下文和成本。

太小：指代关系断裂（"左边那条"指哪条）；条件丢失（"初次入职"的"初次"被切走）；需要召回更多片段才能还原原意。

判断标准：切出来的每一段，单独拿出来读，意思是否完整。

③ 稠密向量和稀疏向量各擅长什么？为什么需要混合检索？

稠密（embedding 模型）擅长语义相近：问"能打包吗"能召回写着"不提供外带打包服务"的段落。

稀疏（BM25）擅长精确命中：产品型号、条款号、人名——这些词在语义空间里没有"相近"的概念。

为什么混合：用户的提问两种成分都有。只做向量，型号搜不准；只做关键词，口语化提问搜不到。

④ HNSW 和 IVF 的区别？线上想提升召回率调什么参数？

HNSW：多层图，像多层公路，从上层大步跳到下层精确定位。快、准，但吃内存（图结构要常驻）。

IVF：先聚类分"班"，查询时只搜最近的几个班。省内存、建索引快，但可能漏召回。

调参：HNSW 调 efSearch，IVF 调 nprobe。这两个都是运行时可调、不需要重建索引——这正是它们相对于 M / efConstruction / nlist 的关键优势。

⑤ 混合检索为什么用 RRF，而不是把两路分数直接相加？

因为两路分数量纲不同、不可比：BM25 通常在 0~20 这个量级，向量相似度是 0~1。直接相加，关键词分会单方面主导，融合就退化成"只看关键词"。

归一化能缓解，但对异常值敏感。RRF 只看名次不看分数，天然可比、对异常值免疫、几乎不需要调参。

⑥ 已经排序去重了，为什么还要 rerank？粗排和精排的本质区别是什么？

本质区别在技术：粗排是双塔——问题和文档分别编码、比向量距离，所以文档向量能离线预计算、快；精排是交叉编码——两者拼在一起送进模型，能逐词对齐，所以准，但每对都要现场推理。

为什么需要：向量检索找的是"语义相似"，不等于"能回答问题"。两个段落都在讲餐厅，一个是"环境介绍"（相似的）、一个是"不提供外带打包"（用户要的），向量分不出来。

⑦ 用户反馈"答得不准"，你按什么顺序排查？

从上游到下游，不要乱试：

  1. 数据层：解析对了吗？切分合理吗？入库了吗？权限过滤掉了吗？
  2. 检索层：正确片段在召回的那 50 条里出现了吗？
  3. 精排层：精排把正确的排到后面去了吗？
  4. 生成层：证据给对了还答错 → 提示词组装问题或模型能力问题。

最值钱的判断：如果召回的 50 条里根本没有正确答案，那怎么调提示词都没用。多数人的第一反应是改提示词——那是最下游的地方。

⑧ 怎么向对方证明你们的召回是准的？

四层证据：

  • 评测集：人工标注几百个「问题 → 正确片段」对，这是黄金标准。
  • 指标：Recall@K（漏没漏）、MRR（排得靠不靠前）、命中率。
  • 人工抽检：定期抽样真实问答，严肃场景不能省。
  • 线上反馈：点踩率、追问率、引用点击率。

政策文件场景加分项：按生效日期过滤（防止拿旧版回答新问题）+ 引用可核对（每条结论能点回原文条款）。

⑨ 为什么结构化输出常选 Markdown 而不是 JSON？

① 流式友好：JSON 没写完就是非法结构，前端没法边收边渲染；Markdown 可以边收边渲染，用户体感快。

② 生成稳定：长 JSON 容易出错（少括号、多逗号），一出错整个结构就废了；Markdown 容错性好。

③ 模型顺手：训练语料里 Markdown 极多，输出它格式漂移最少。

什么时候用 JSON：需要严格结构时，用结构化输出约束让接口层保证格式，而不是让模型自由发挥写 JSON。

⑩ 微调、RAG、私有化部署分别该在什么情况下用？
  • RAG：知识类需求的首选——更新快、可溯源、成本低。
  • 微调：格式/风格/术语类需求；或把大模型能力蒸馏到小模型省钱。不要用它灌知识。
  • 私有化：数据不能出内网（政府、金融、医疗），或者调用量大到自建更便宜。

加分回答：模型分级路由——简单任务走小模型，复杂生成走大模型，整体成本能降一大截而效果几乎不损失。

3. 自查题 · Agent 部分（10 题）

⑪ Agent 和 Workflow 的区别？什么时候不该用 Agent？

区别在路径由谁决定：Workflow 是人写死的流程图；Agent 是模型现场判断下一步。

不该用 Agent 的场景：结果要求 100% 确定（转账、改权限）；延迟要求极严（多轮循环天然慢）；成本敏感（每轮带完整历史）；流程完全固定。

加分点：能用 Workflow 就别上 Agent，真实项目大多是混合——主流程固定，关键判断点放 Agent。

⑫ 完整讲一遍 Agent 主循环，并说明怎么防止死循环。

主循环：组装上下文 → 模型决策（直接答 or 调工具）→ 解析调用 → 执行工具 → 结果回灌 → 回到第一步。

刹车机制：轮次上限、token 预算（轮次限制挡不住"一轮塞十万 token"）、时间上限、重复调用检测、无进展检测、错误熔断、接近上限时升级给人。

加分点：到上限时不是硬报错，而是把已拿到的部分结果总结给用户并说明还差什么。

⑬ Function Call、MCP、Skill 三者的区别？（必须一次说清）

Function Call 是模型的能力——告诉它有哪些函数、参数长什么样，它能输出规范的结构化调用请求，解决"能不能调"。

MCP 是工具的接口标准——像 USB-C，把 M 个模型 × N 个工具的适配从 M×N 变成 M+N，解决"接起来太麻烦"。

Skill 是做事的流程知识——像操作手册，打包提示词、脚本、参考资料，解决"知不知道该怎么做"。

补充：Skill 用渐进式披露（先给名字和一句话描述，需要时再加载详情），本质是对上下文的 RAG。

⑭ 工具调用失败了怎么处理？举三种失败类型。

按类型处理，不能只答"重试"：

  • 参数写错 → 把报错信息原样告诉模型让它自己改（最有效的一招）。
  • 工具自己坏了（超时/500/限流）→ 指数退避重试，并区分可重试与不可重试。
  • 工具选错 → 优化工具描述（写清使用边界）、减少工具数量、给示例。
  • 查到是空的 → 让模型换关键词或换工具再试。
  • 反复调同一个 → 重复调用检测 + 轮次上限。

兜底原则：重试 N 次不行就降级（返回部分结果 / 转人工），绝不让 Agent 烧钱空转。

⑮ 多 Agent 解决的核心问题是什么？拆的代价是什么？

核心问题：上下文污染 + 角色冲突（自己评审自己不客观），顺带拿到并行能力。

代价：信息在传递中丢失、状态一致性、责任边界模糊（排查链路变长）、互相踢皮球、延迟和成本上升、调试难度大增。

核心判断：决定 Agent 上限的不是模型有多强，而是上下文有多干净。

⑯ 什么时候该拆多 Agent？什么时候不该拆？

该拆：子任务需要独立上下文；能并行；需要不同工具集或权限；需要独立评审；提示词里有互相冲突的指令。

不该拆：上下文本来就一样；必须串行且强依赖全部细节；工具集重合；只是"想让架构好看"。

现实观察（说出来很务实）：两三个通常就够，那些七八个 Agent 互相讨论的架构多半演示好看、上线痛苦。

⑰ 动态路由怎么实现？要注意什么？

实现：模型分类（把候选分支和适用条件写进提示词）→ 函数调用（把"选分支"做成函数）→ 规则 + 模型兜底（生产最实用）→ 向量相似度。

三个坑：① 必须有兜底分支，否则这一步失败整条链路就崩；② 必须限制跳转次数，否则 Agent 之间互相踢皮球；③ 路由日志要留全（模型判断理由 + 可选分支 + 上下文摘要），没有它动态路由没法调试。

⑱ claude code 的核心循环是什么？它体现了哪些设计原则？

核心循环：主循环——模型判断该做什么 → 调用工具（读代码、搜代码、改代码、跑测试）→ 结果回灌上下文 → 进入下一轮，直到解决。本质就是 Agent 主循环，只是工具集换成了代码相关的。

四条设计原则：① 检索优于全量（先搜索定位，只带相关片段进上下文）；② 工具结果要裁剪（读文件只读需要的行区间）；③ 子任务隔离（探索类工作交给子 Agent，只回传结论）；④ 提示词可缓存（稳定部分放最前面）。

落点：所有设计都指向同一件事——管住每一个 session 的上下文。决定 Agent 表现的不是模型上限，而是上下文质量。

⑲ Harness 是什么？为什么它比换模型还重要？

Harness = 把裸模型包装成能干活的系统所需要的整套东西：系统提示词、工具定义与执行、上下文管理、循环控制、错误处理、可观测性、权限沙箱、人机协作。

为什么重要：同一个模型装在不同 Harness 里效果能差好几倍（同一个发动机装不同车架）；更关键的是模型半年才更新一次，Harness 你每天都能改——改它的投入产出比往往高于等更强的模型。

⑳ 讲一个你设计过的 Agent（五段式）。

没做过真实项目就自己搭一个，然后照下面的结构讲（完整示范见 08 第 6 节）：

  • 结论：一句话说清职责边界（"检索 Agent，负责把口语问题变成精准查询，只读不写"）。
  • 做法：几步流程 + 工具集（工具越少越好说清）。
  • 数字：命中率、延迟、占比。
  • 坑：工具粒度的真实教训。
  • 权衡：拆细了灵活但轮次多，最后怎么折中的。

4. 完整参考回答（3 份）

示范一：简单介绍一下 RAG 的流程

【结论】RAG 是检索增强生成，核心是先从外部知识库取相关信息，再让模型基于这些信息生成答案。它主要解决模型不知道私有知识、知识会过时、容易幻觉这三个问题。

【做法】我们分两条链路。离线链路把文档解析、切分、向量化后入库，同时把原文和元数据存进 ES。在线链路拿到问题后先做查询改写，然后并行走两路召回——ES 做关键词、向量库做语义，用 RRF 融合成 Top 50，再用交叉编码器精排到 Top 5，组装进提示词让模型基于证据回答，并要求标注出处。

【数字】知识库目前 XX 万段，单次问答检索加精排的 P95 是 X 秒；加了混合检索之后，专有名词类问题的命中率从 X% 提到 Y%。

【坑】最开始只做了向量召回，结果用户搜产品型号和条款编号经常搜不到——向量擅长语义、不擅长精确匹配。加了关键词那一路才解决。

【权衡】精排提升了准确率但增加了延迟，所以我把候选从 100 缩到 30，并对高频问题做了结果缓存，把延迟控制在可接受范围。

示范二：Function Call、MCP、Skill 的区别

【结论】三者解决的是不同层次的问题。

【Function Call】是模型的能力——你告诉它有哪些函数、参数长什么样，它能输出一个规范的结构化调用请求。它解决"模型能不能调工具"，是模型自带的。

【MCP】是工具的接口标准，可以理解成 USB-C。以前每个工具要对接每个 AI 客户端，M 个模型 × N 个工具就是 M×N 份适配代码；有了统一协议就变成 M+N。它解决"接起来太麻烦"。

【Skill】是做事的流程知识，像一份操作手册，打包了提示词、脚本和参考资料。它解决"知不知道这类任务该怎么做"，而不只是"能调什么工具"。

【补充】Skill 通常用渐进式披露——上下文里只放名字和一句话描述，模型觉得需要时再加载详情。这样挂几百个 Skill 也不会撑爆上下文，本质上是对上下文的 RAG。而一个 Skill 内部可以调用多个工具，模型是靠 Function Call 能力真正发起调用的。

示范三：为什么需要多 Agent？（含 100 分档的权衡）

【结论】多 Agent 主要解决两个问题：上下文污染和角色冲突，顺带拿到并行能力。

【做法】我们拆了检索和评审两个 Agent。检索 Agent 的上下文里只有查询和结果，不会被后续写作过程污染；评审 Agent 拿到的只有"待评审对象 + 评审维度"，没有历史包袱，判断更客观。两个各配独立的工具集，主 Agent 只负责分派和汇总。

【数字】拆分之后评审结论的一致性明显提升；检索和评审可以并行，总耗时下降约 X%。

【坑】一开始让两个 Agent 共用一份对话历史，结果评审者被前面的讨论带偏，永远说"还能改进"。改成上下文隔离之后才有收敛。

【权衡】但拆不是免费的：多 Agent 有通信成本和状态一致性成本——信息在传递中会丢失，责任边界会模糊，还会互相踢皮球。我的判断标准是——只有当子任务需要不同的上下文、或者可以并行时才拆，纯粹为了让架构"看起来更专业"而拆是负收益。

从"大模型只会说话"开始，一路讲到"Agent 会做事"。中间要经过哪几步？每一步解决什么问题？

讲完了，展开对照

① 大模型只会说话：能对话、能写代码，但不知道你们的私有资料，不知道最新消息，不知道的时候还会编。

② 加 RAG 让它"会查"：离线把文档解析、切分、向量化后入库；在线把问题改写后两路召回、融合、精排，再把证据塞进上下文让它照着答。解决了"不知道"和"会编"。

③ 加工具和循环让它"会做"：工具让它能真的去搜、去算（注意是程序在动手，模型只负责说要干什么）；循环让它做完一步看结果、不够再来一轮。加上刹车机制防止它烧钱空转。

④ 拆成多 Agent 解决上下文污染：每个 Agent 只看自己那摊，上下文更干净。代价是通信成本和状态一致性。

⑤ 最后靠 Harness 把它做成能上线的系统：提示词、工具、上下文管理、刹车、错误处理、日志、权限——同一模型装在不同 Harness 里，效果差好几倍。

下一步做什么

步骤 1 达标后进入步骤 2：做系统（C + D 域）。那一步没有预先阅读材料——C 域（上下文治理、流式输出）和 D 域（后端数据）的知识只能在项目里长出来，先看也是白看。
