01 · RAG 是什么

这一页讲一件事：怎么让模型回答它"没读过"的东西——比如你们公司的内部制度。 第一次读，先只看图和加粗句。

JR-5TK-8PY-5YU-17
读之前

这一页会用到「上下文」「向量」「幻觉」这些词。看着眼生的话，先花 5 分钟看 00 · 先认识这几个词。

第一遍（5 分钟）只看主图和加粗句，跳过表格。
第二遍（15 分钟）读正文和例子。
第三遍（5 分钟）做页尾回忆卡，自己讲一遍。

0. 先看一个场景

你把 AI 接进公司内部系统，员工问它：「我们公司的年假怎么算？」

如果只有大模型如果加上 RAG
它会答：「一般公司年假是 5 到 15 天，具体看工龄……」

——听起来很像那么回事，但它根本没读过你们的员工手册，这是它编的。		 它先去《员工手册》里翻出年假那一条，然后照着答：「入职满一年 5 天，满三年 10 天（来源：员工手册 4.2 节）」

——有依据，还标了出处，员工能自己去核对。
RAG 的全部思路就是这一句话

提问时，先把相关资料找出来放进上下文，再让模型照着资料回答。

这个"找资料"的动作就叫检索（Retrieval），找到资料后用来"增强"模型的回答能力，所以叫检索增强生成（Retrieval-Augmented Generation，缩写 RAG）。

主图 · RAG 的两条链路

离线把资料变"能查"，在线查完再回答

这张图在说什么：上半部分是"提前把文档处理好存进库"，用户看不见；下半部分是"用户提问时现场查、现场答"。中间的知识库把两条链路连起来。

一句话记住：离线管"存得进、查得到"，在线管"查得准、答得好"。两条链路的优化手段完全不同，出问题时要先判断是哪条链路的错。

颜色含义： 用户 模型 / 计算 工具 / 处理 产出 / 存储 数据 / 静态 风险 / 限制

1. 它到底解决哪三个问题

开头那个"年假"的例子，其实同时暴露了三个问题。这三个问题几乎每轮都会被问到：

问题具体表现RAG 怎么解决
模型不知道
私有知识缺失		 你们公司的制度、内部接口文档、客户资料——训练时它根本没读过 把这些文档处理成知识库，提问时检索出来喂给它
模型记不住
知识会过时		 它的知识停在训练那天。上个月刚改的报销标准，它不知道 知识库随时能更新，新文档入库后立刻生效，不用重新训练模型
模型会编
幻觉		 不知道的时候不承认，而是编一个"一般公司年假是 5 到 15 天" 强制它照着检索到的资料回答，并要求标注出处——用户能自己核对
第三个问题常被低估

在严肃场景（法律、医疗、政策、金融）里，"能溯源"往往比"答得准"更重要。用户要的不只是一个答案，而是"这个答案出自哪份文件第几条"。这类场景下 RAG 几乎是唯一选择，因为只有它天然带着出处。

2. 一个容易钻牛角尖的问题：RAG 是不是"文档问答"？

很多人对 RAG 的理解停在"文档切分 → 向量化 → 召回 Top-K"这一套流程。这是最常见的形态，但它不是 RAG 的本质。

RAG 的本质是一种更宽的说法，只要满足这三步就算：

① 先从外部取信息  →  ② 用它增强模型的上下文  →  ③ 再生成答案

按这个定义，下面这些全都是 RAG：

形态为什么算 RAG
Agent 调搜索引擎查资料检索发生在工具调用里，取回的内容塞进了上下文
代码助手用关键词搜索找代码从代码库里取信息来增强上下文；关键词搜索本身就是一种检索
Agent 的长期记忆把历史对话存起来，需要时取出来——取出来这一步就是检索
Skill 的按需加载先给一句话描述，需要时再取详细内容——对"做事方法"的 RAG

这个认知的用处很直接：当对方问"现在模型上下文都那么长了，RAG 是不是要死了"，你就能答：被淘汰的只是某种粗糙的实现方式，而不是这个思路——照这个定义，RAG 早就到处都是了。

3. RAG、微调、长上下文，该用哪个

这三个经常被拿来互相比较，其实它们解决的不是同一件事：

方案解决什么代价什么时候用
RAG 让模型"知道"新知识和私有资料 要搭一整套检索链路；检索质量决定上限 知识类需求的首选：更新快、可溯源、成本低
微调 改变模型"怎么说话"：输出格式、语气、术语习惯 要数据要算力；知识更新要重训；容易过拟合 格式 / 风格类需求；或把大模型能力蒸馏到小模型省钱
长上下文 一次能塞进更多材料 贵；塞得越多噪声越大，模型容易被无关内容带偏 材料总量很小时（几份文档）可以直接全塞；量大仍然要靠检索
私有化部署 数据不出内网、长期成本可控 要 GPU、要运维；模型能力通常弱于头部闭源 合规要求高（政府、金融、医疗），或调用量大到比自己部署还贵
一句话分工

RAG 教它"说什么"，微调教它"怎么说"，两者不冲突、可以叠加。

常见的错误是用微调去灌知识——知识更新要重训、还容易过拟合，而且模型照样会编。

4. 答错了，先分清是哪一类错

RAG 答错只可能是两种原因，而它们的修法完全相反。先分清，再动手：

这张图在说什么：先确认"正确答案在不在召回结果里"。在，问题出在后面；不在，问题出在前面。

这句话讲的时候很值钱

"如果召回的 50 条里根本没有正确答案，那怎么调提示词都没用。"

大多数人的第一反应是去改提示词——那是整条链路最下游的地方，方向就错了。先确认上游没坏，再动下游。

5. 讲解骨架（看懂之后再背）

「简单介绍一下 RAG 的流程」（约 3 分钟）

【结论】RAG 是检索增强生成，核心是先从外部知识库取相关信息，再让模型基于这些信息生成答案。它主要解决三个问题：模型不知道私有知识、知识会过时、以及容易产生幻觉。

【做法】我们分两条链路。离线链路把文档解析、切分、向量化后入库，同时把原文和元数据存进 ES。在线链路拿到问题后先做查询改写，然后并行走两路召回——ES 做关键词、向量库做语义，用 RRF 融合成 Top 50，再用交叉编码器精排到 Top 5，组装进提示词让模型基于证据回答，并要求标注出处。

【数字】知识库目前 XX 万段，单次问答检索加精排的 P95 是 X 秒；加了混合检索之后，专有名词类问题的命中率从 X% 提到 Y%。

【坑】最开始只做了向量召回，结果用户搜产品型号和条款编号经常搜不到——向量擅长语义、不擅长精确匹配。加了关键词那一路才解决。

【权衡】精排提升了准确率但增加了延迟，所以我把候选从 100 缩到 30，并对高频问题做了结果缓存，把延迟控制在可接受范围。

RAG 和微调怎么选？

按需求性质分：要它"知道"新知识 → RAG；要它"说话方式"改变 → 微调。

常见的误区是拿微调去灌知识——那样知识更新要重训、还容易过拟合，而且模型仍然可能编。正确做法是 RAG 负责知识、微调负责格式和风格，两者叠加。

"RAG 已死"的说法怎么看？

先承认现象：确实每隔一阵就有这类文章，拿关键词搜索、长上下文、模型自身的知识来论证。

再指出问题：这些论证把 RAG 狭隘地定义成"外部文档充当上下文"，是以偏概全。关键词搜索本身就是一种检索，Agent 的长期记忆就是把历史取出来，Skill 的按需加载就是对"做事方法"的检索——用本质是 RAG 的东西去证明 RAG 死了，是自我反驳。

结论：会过时的是某些粗糙实现，不是这个思路。

你怎么衡量一个 RAG 系统做得好不好？

分两层看，别只盯最终答案：

  • 检索层：Recall@K（正确片段有没有进前 K）、MRR（排得靠不靠前）——需要人工标注评测集。
  • 生成层：答案正确率、引用准确率（引用是不是真的支持结论）、拒答率（该说不知道时有没有说）。
  • 线上：点踩率、追问率、引用点击率、平均轮次（一轮解决 vs 反复追问）。

加分点：引用准确率是 RAG 特有的指标。很多团队只看答案对不对，忽略了"引用是不是真的支撑这句话"。

知识库的数据源一般有哪些？

按处理难度从低到高：

  • 结构化：数据库表、CSV——最好处理，但通常走 SQL 查询而不是向量检索
  • 半结构化：Markdown、HTML、语雀/Confluence 导出的文档——有结构，切分质量高
  • 办公文档：PDF、Word、PPT——要解析，表格和公式是难点
  • 非结构化：图片、扫描件、录音转写、视频字幕——要 OCR / 语音识别，质量最不稳定

回答时补一句工程细节会更可信：每条数据都要带元数据（来源、版本、生效时间、权限），否则后面做过滤、做引用、做权限控制都要返工。
