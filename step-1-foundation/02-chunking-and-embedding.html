02 · 索引：切分与向量化

这一页讲那件"用户看不见、但决定一切"的事：把文档变成能被检索的东西。 这一步做得糙，后面检索和生成再优化也救不回来——垃圾进，垃圾出。

读之前

0. 先看一个场景

你手上有一份 80 页的《员工手册》PDF，要把它变成可检索的知识库。

能不能整本存进去？不行——检索是按"段"匹配的，整本一个单位，等于什么都没匹配上。所以要加工：

解析
从 PDF 里把文字、表格、图片提取出来。这一步的坑最多，见第 4 节。
→
切分
切成一段一段的 chunk，每段意思要完整。切法决定检索上限，见第 1~2 节。
→
向量化
每段算成一个向量，让机器能"按意思找"。见第 6 节。
→
入库
向量存档，原文和元数据也一起存（要用来做引用和过滤）。见第 3 节。

这张图在说什么：这四步是"用户看不见的那一半"。用户只看到最后问答很快，但答得准不准，几乎全由这里决定。

主图 · 这一页最反直觉的一点

切得太大，关键信息会被"稀释"

《员工手册》里有一条："员工餐厅不提供外带打包服务"。假设员工问：「餐厅能打包吗？」

切得太大（一段 800 字，里面还混着考勤、报销、门禁的内容）

那一句话只占整段的 6%。整段算出来的向量，反映的其实是"考勤报销门禁"这些内容——员工问"打包"，根本匹配不上。

切得合适（一段 150 字，就讲餐厅规则）

同一句话占了 62%，向量能准确表达它——员工一问就能召回这一段。

这张图在说什么：向量是"整段的平均意思"。关键句在一段里占比越小，它就越容易被淹没。这就是切分粒度的核心矛盾。

颜色含义： 用户 模型 / 计算 工具 / 处理 产出 / 存储 数据 / 静态 风险 / 限制

1. 粒度：切太大和切太小，各出什么问题

切太大后果具体的坑
800 字一段 向量语义被稀释，召不回来 上面主图那个"餐厅打包"的例子
侥幸召回了，也干扰模型 一段里一半内容跟问题无关，模型容易被带偏
浪费上下文和成本 无关内容白占 token，还挤掉别的有用内容
切太小后果具体的坑
一句话一段 指代关系断裂 手册里写"请选择左边那条通道"——左边哪条？上一段被切走了
条件丢失 "初次入职的员工需提交体检报告"——"初次"这个前提被切丢了，变成所有人都要交
要召回更多段才能还原原意 检索开销变大，还容易召回不齐
判断标准就一条

随便抽一段出来单独读，意思完整吗？

读得懂就是合适的粒度；读不懂说明切坏了——要么切太碎，要么把别的主题混进来了。

2. 怎么切：三种策略

策略怎么做适合缺点
按长度硬切 每 500 字切一刀，相邻两段留一点重叠 快速起步、格式乱的文本 句子会被拦腰切断，语义容易碎
按结构切 按标题层级、段落、列表项切 结构规范的文档：手册、政策文件、文档站 文档本身没结构就用不了
按语义切 算相邻句子的向量相似度，在"意思跳变"的地方断开 长文、论文 慢、贵；切出来的长度不可控
实战组合（照这个答）

结构优先 → 结构内太长再按长度切 → 相邻块留 10~20% 重叠 → 每块头部拼上章节路径。

最后一步容易被忽略但很有效：给每段拼上它所属的章节，比如 第三章 财务制度 > 3.2 差旅报销。这样即使这一小段本身没提"报销"两个字，检索时也能匹配上。

3. 切完还要带上"身份证"：元数据

很多人只存了文字和向量，结果后面做引用、做过滤、做权限时全部返工。每一段都要带上这些字段：

字段后面用来干什么
doc_id / chunk_id溯源、去重、文档更新时定位旧内容
来源 / 标题答案里显示"出自哪份文件"
章节路径拼进 chunk 头部，提升检索质量
页码 / 位置引用能精确点到第几页
生效日期 / 版本政策类文档必备：防止拿 2019 年的文件回答 2025 年的问题
部门 / 权限标签多租户隔离。必须在检索时就过滤掉，不能"先检索再让模型别看"
权限这件事有个红线

没有权限的内容绝不能进上下文。因为一旦进去了，就已经是数据泄露了——而且模型完全可能把它说出来。所以过滤必须在检索之前或之内完成。

4. PDF 为什么最麻烦

关键认知：PDF 里没有"段落"这个概念，只有一堆带坐标的文字块。所谓段落、表格、分栏，全靠解析器去猜。

坑会发生什么
双栏排版被读串行左栏第一行接上右栏第一行，句子完全错乱
表格被拆散跨页表格、合并单元格读出来是一堆错位的文字
页眉页脚混进正文每页重复的页眉污染每一段
扫描件没有文字层必须先做 OCR，识别错字直接影响检索
公式变乱码普通解析器读不出公式结构
工具适用场景
PyMuPDF / pdfplumber版式简单、以文字为主，轻量快速
Unstructured / Marker / MinerU版式复杂、要保住表格和公式，能输出 Markdown 结构
云解析服务表格/公式精度要求高，且允许数据出内网
一个能加分的设计

解析时保留结构标记（标题层级、表格、列表），不要一上来就拍平成纯文本。结构化的 Markdown 让后面的切分和章节路径提取都简单得多。

这也是为什么很多团队会优先喂 Markdown / LaTeX 原文，而不是 PDF——能拿到源文件就别走 PDF。

5. 中文怎么切词（ES 分词）

关键词检索（ES）靠的是"把句子切成词，建一张词到文档的索引表"。切得好不好，直接决定搜不搜得到。

分词器"中华人民共和国" 会被切成效果
standard 中 / 华 / 人 / 民 / 共 / 和 / 国 中文被切成单字，几乎不可用
ik_smart 中华人民共和国 粗粒度：召回少、噪声小
ik_max_word 中华人民共和国 / 中华 / 人民 / 共和国 …… 细粒度：召回多、噪声大
标准做法：索引粗、查询细

建索引的时候用 ik_max_word（尽量多切），用户查询的时候用 ik_smart（尽量准）。

索引阶段多切，保证各种问法都能命中；查询阶段少切，避免把用户的问题切碎之后匹配到一堆无关内容。

另外两件常被忽略的事：自定义词典（把产品型号、内部缩写灌进去，防止被切碎）和同义词表（"社保" ↔ "社会保险"）。

6. 稠密 vs 稀疏：为什么两种都要

"找相似内容"有两种思路，它们擅长的事情完全不一样：

这张图在说什么：同一个知识库，两种检索各能覆盖对方漏掉的情况——所以生产系统通常两路都要走（这就是第 04 篇的"混合检索"）。

BM25 的三条直觉

关键词检索的打分公式叫 BM25。不用背公式，能说出这三条就够：

机制直觉
词越稀有越值钱 "的""是"这种满篇都有的词没有区分度；专业术语只在少数文档里出现，命中它就说明很相关
词频有上限 一个词出现 100 次和 100 万次，得分不该差一万倍。否则一篇疯狂重复"苹果手机"的灌水贴会排到真实评测前面
长文档要打折 文档越长，天然越容易命中各种关键词。不打折的话长文档会系统性占优

embedding 模型怎么选

场景选择思路
中文为主、要开源可控bge-m3 / bge-large-zh 系列；bge-m3 还能同时输出稠密和稀疏向量
走 API、省运维主流闭源接口，效果稳，但要考虑数据合规和成本
中英混排 / 多语言多语言版模型，或支持多语言的 bge-m3
选型时最容易被忽略的一点

换 embedding 模型 = 全库重新向量化。几十万上百万条重跑一遍，既费钱又费时间，还要平滑切换（新旧索引并存、逐批迁移）。所以这是个一次定好、别中途换的决定——讲的时候主动提这一点，说明你想过工程成本。

另外：查询和文档必须用同一个模型，混用不同模型的向量算出来的距离没有意义。

7. 为什么必须有人工审核

对方问这个，其实在问你对数据质量的态度。要讲清一条因果链：

解析和切分必然会出错 → 错误会一路传到答案里 → 而模型会用同样自信的语气把错误说给用户。

环节审什么
入库前审切分是否完整、表格公式是否读对、敏感内容是否要过滤、元数据是否齐全
上线后抽检定期抽样真实问答，看召回内容对不对、答案引用得对不对
一句话回答

"不是不信任 AI，而是错误的成本太高——一段错的数据会被模型自信地复述给用户，而且用户很难察觉。所以入库前设一道闸，上线后做定期抽检。"

8. 讲解骨架（看懂之后再背）

这一段就是答案：按顺序把这几件事讲一遍，讲不下去的地方回上面正文补。再往下的「回忆卡」是自测（先合上材料讲，再展开对照），「动手清单」是怎么落到自己项目里。文中的 X XX X% 不是没写完，是留给你填自己项目数字的槽位——换成真实数字，这段才立得住。

「文档是怎么切分、入库、审核的」

【结论】切分的标准不是长度，而是语义是否完整——切太大，关键信息在整段里的占比被稀释，向量就表达不准、召不回来；切太小，前提条件和指代关系会断裂。

【做法】我们是结构优先：先按文档标题层级切，某一节太长的再按句子边界二次切分，相邻块保留 15% 重叠。每个 chunk 头部会拼上章节路径，并带上来源、页码、生效日期、权限这些元数据。向量化之后，向量写进向量库，原文和元数据写进 ES。

【数字】一共 XX 万份文档、切成 XX 万个 chunk，平均每块 X 百字，重叠 15%。

【坑】最开始用固定长度硬切，结果规则类文本被拦腰截断——"在 X 情况下做 Y"被切成两半，模型只看到 Y，不知道怎么用。改成按结构切之后这类问题基本消失。

【权衡】语义切分效果最好但慢且贵、长度不可控，所以只在长文档上局部使用，绝大部分场景用结构切分就够了。

chunk 到底切多大？有没有标准值？

没有通用标准值，但有判断依据：

  • 看内容形态：问答对、规章制度适合小块（语义自洽）；叙述性长文适合大块。
  • 看检索粒度：要精确定位到条款就切小；要保留完整论证就切大。
  • 实用折中：用小 chunk 做检索，命中后把它所在的整段送给模型——兼顾准确率和完整性。

最好直接说"我们线上用的是 X 字左右，这个值是 A/B 对比之后定的"，比背一个数字可信得多。

ES 存原文、向量库存向量，两者怎么对应？

用同一个 chunk_id 关联。混合检索时两路各自返回 chunk_id 和分数，融合后再按 id 取回原文和元数据。

实践上有两种简化：把向量直接存进 ES（ES 支持向量字段，一套系统搞定，运维最省事）；或者向量库也存原文（省一次查询，但要处理数据一致性）。

知识库文档更新了怎么办？
  • 识别变更：用文件哈希或版本号判断哪些文档真的变了，别按修改时间瞎猜。
  • 先删后插：按 doc_id 删掉这个文档的所有旧 chunk 再插入新的——否则新旧内容同时在库里，答案会自相矛盾。
  • 注意旁路影响：被引用过的 chunk 删掉后历史答案的引用会失效，要么归档、要么标记"已失效"。
为什么不只用一个模型同时出稠密和稀疏向量？

可以，bge-m3 这类模型就同时输出两种向量，省一次推理。但有两点要注意：

  • 它的稀疏向量是"学出来的词权重"，和 BM25 那种纯统计的词权重不完全等价；型号、编号这类精确匹配场景，BM25 反而更稳。
  • 如果已经在用 ES，直接用 ES 自带的 BM25 更省事，不需要额外存一份稀疏向量。

为什么 chunk 切太大会"召不回来"？切太小又会出什么问题？

讲完了，展开对照

切太大：向量是整段的"平均意思"。关键句在一段里占比很小，整段向量反映的是别的内容，算相似度就算不准，于是召不回来。就算召回了，里面一半是无关内容，也会干扰模型。

切太小：指代关系断裂（"左边那条"指哪条）、条件丢失（"初次入职"的"初次"被切走）、要召回更多段才能还原原意。

判断标准：抽一段单独读，意思完整吗？

回忆卡 2 · 合上材料，用自己的话讲一遍

稠密向量和关键词检索各擅长什么？为什么两个都要？

讲完了，展开对照
  • 稠密向量擅长意思相近：问"能打包吗"，能找到写着"不提供外带打包服务"的段落。
  • 关键词（BM25）擅长词能对上：搜型号 XR-2000A、条款号、人名，这些词没有"意思相近"的说法，只能精确匹配。
  • 反过来各自的短板正好是对方的长处，所以两路都要走，再融合结果。

另一个必答点：换 embedding 模型等于全库重新向量化，所以选型要一次定好。
