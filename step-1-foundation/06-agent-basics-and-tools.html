06 · Agent 基础与工具协议

这一页讲一件事：怎么让一个只会聊天的模型，变成一个能自己干活的助手。 所有内容都是围绕这个问题的。第一次读，先只看图和加粗句。

0. 先看一个例子

你对 AI 说：「帮我调研一下 X 产品的竞品，写份报告。」

这件事大模型自己干不了——它没搜过，也不知道现在的市场是什么样，硬答就是在编。

加上 Agent 之后，它开始这么转：

轮次它判断……然后做了什么
第 1 轮 「我什么都不知道，得先搜资料」 调用网页搜索工具（这个工具是程序员提前写好、交给它的）→ 拿回 10 条结果
第 2 轮 「这 10 条全是官方宣传稿，没有真实评测」 换一组关键词再搜一次 → 这次拿到了评测文章
第 3 轮 「够了，可以动笔了」 直接输出报告（并说明依据来自哪几篇）
这个例子里最关键的一点

这三轮里"下一步做什么"，没有一步是程序员提前写死的——全是模型看着当前情况自己判断的。

这就是 Agent 和普通程序最本质的区别。普通程序你写死"第一步搜、第二步写"，它就只会这么干；哪怕第一轮搜出来的东西全是垃圾，它也会接着写。而 Agent 会停下来判断："这批结果不行，我换个词再搜。"

主图 · 把刚才那个过程画出来

主循环：想 → 做 → 看 → 再想

这张图在说什么：模型每一轮只做一件事——判断"现在能不能答"。能就直接输出答案，不能就调工具、把结果追加回上下文，然后带着新信息重新判断一次。中间那个虚线框是刹车机制：轮次、token 预算、时间上限，防止它无限循环下去。

图里的每个名字对应什么：

图上的名字实际指的是常听到的叫法
模型决策大模型看着当前情况，判断下一步做什么Reasoning（推理）
工具执行程序替它真的去搜、去算、去读文件Function Call / Tool Use
结果回灌把工具返回的内容塞回上下文，供它下一轮参考观察结果 / Observation
刹车机制防止它转个没完、把钱烧光循环控制 / 预算控制

讲的时候就说这四句：模型决定 → 工具执行 → 结果回灌 → 循环，外面必须套一层刹车。

（这个循环在论文里叫 ReAct，是 Reasoning + Acting 的缩写。讲的时候说"主循环"完全够用，能讲清"想→做→看→再想"比背这个词有用。）

颜色含义： 用户 模型 / 决策 工具 / 执行 产出 / 存储 数据 / 状态 风险 / 限制

1. Agent 和 Workflow 差在哪

先看一个更小的需求：「客户发来一封邮件，把里面的订单信息存进表格。」

这件事有两种做法：

做法怎么实现出问题时
A · Workflow
按固定流程走		 你写死四步：提取正文 → 抽取字段 → 校验格式 → 写入表格。程序照着跑，每次都一样 格式变了就报错，得你去改代码
B · Agent
让模型自己看着办		 把邮件丢给模型，它自己决定先看哪里、要不要拆附件、字段抽不出来要不要换个思路 它自己会调整；但也可能绕远路

两种都能用，那怎么选？就看这三个问题：

① 步骤能提前枚举完吗？（每次都是那几步）

能用 Workflow —— 更便宜、更快、出问题好查
不能继续看 ②

② 步骤是否依赖"跑起来才知道"的信息？（附件里有没有合同？要不要回邮件问一下？）

是用 Agent —— 这正是它的价值所在
否继续看 ③

③ 有没有承诺的响应时间？（比如接口必须 3 秒内返回）

没有可以用 Agent
有慎用 Agent —— 它要来回转好几轮，耗时不可控
讲解落点：主动说"能不用就别用"

Agent 更灵活，但代价是更不可控、更贵、更难调试——同一个任务，Workflow 的耗时和成本是可预测的，Agent 不是。

所以工程上的正确姿势是：能 Workflow 解决的就别上 Agent。真实项目大多是混合的——主流程用 Workflow 固定住，只在个别需要判断的节点上放 Agent。

2. 循环里每一步在做什么

回到第 0 节那个例子。点开任意一步，看它在实际运行中是干什么的。

组装上下文
把这几样拼在一起送给模型：系统提示（它的角色和规矩）+ 工具清单（它有哪些工具、各自怎么用）+ 之前的对话 + 当前目标。这一步每轮都要重做一遍。
→
模型决策
模型看着上面那一大坨，决定"我现在能直接回答了吗？还是要先调个工具？"。整个循环里只有这一步是它在"思考"。
→
解析调用
模型输出的是一段结构化的文字，比如"调用搜索，关键词=竞品评测"。程序把它解析成真正的函数调用。格式错了就走失败处理，见第 6 节。
→
执行工具
程序真的去搜网页、跑代码、读文件。注意：动手的永远是程序，模型只负责说要干什么。返回值要先裁剪再回灌——一整坨原始 JSON 直接塞进去会撑爆上下文。
→
结果回灌
把结果作为一条新消息追加进上下文，然后回到第一步。这就是为什么转的轮数越多，上下文越长、越贵。
一个能看出你做过系统的判断

Agent 失败的原因，几乎都能归到一件事上：上下文管理没做好。所以"结果回灌"这一步的关键不是"塞进去"，而是"裁干净再塞"。

为什么必须刹车：看上下文是怎么被撑爆的

还拿第 0 节那个调研任务举例。蓝色部分是"当前这一轮最需要看的信息"：

第 1 轮 —— 上下文很干净

当前目标占 34%，模型看得见重点，判断力最好。

第 8 轮 —— 前面几轮搜到的原始网页开始堆积

当前目标被稀释到 12%，它开始被无关内容干扰，比如反复去搜已经搜过的东西。

第 20 轮 —— 当前目标几乎被淹没

只剩 4%。失败的尝试、已经否掉的思路全都还留在上下文里，模型被自己的历史带着走，反复在同一个坑里打转。

这解释了那句很常见的话："AI 一直修不好一个 bug，不一定是它没能力，而是它的上下文被带偏了。"

四道刹车（缺一不可）

机制说明
最大轮次最多转几圈，到点强制收尾
token 预算累计消耗超过上限就停。光限制轮次没用——一轮塞十万字照样烧钱
时间上限总耗时超时停止，不让用户干等
重复调用检测同一个工具、同样的参数连着调 → 判定卡住了，强制换个策略

加分回答：到上限时不要直接报错，而是让它把已经查到的部分整理给用户，并说明还差什么——比一句"失败了"体验好得多。

3. 工具怎么设计

工具调用出错，很多时候不是模型笨，是工具没设计好。下面三条最常用，先讲透；后面三条列出来，知道有这回事就行。

最常用的三条

原则什么意思反例
描述比名字重要 模型主要靠描述判断什么时候该用这个工具。所以要写清"什么情况该用、什么情况不该用" 描述只写"搜索工具"——那它可能拿它去搜数据库里该用 SQL 的东西
结果要裁剪 工具返回的内容要先删减、摘要，只留模型用得上的字段 把接口返回的整坨 JSON（带几十个字段）原样塞回去，上下文一下就满了
错误信息要有用 出错时返回人能看懂、能照着改的提示 返回一个"500 服务器错误"——模型不知道该改什么，只能瞎试

另外三条（知道就行）

  • 参数少而清晰：参数越多、套得越深，模型传错的概率越高；能给默认值就给。
  • 工具数量要克制：几十个工具会让模型挑花眼，相似的工具应该合并或分组加载。
  • 幂等性：写操作类的工具（下单、扣款）要能安全重试，否则模型重试一次就多扣一次钱。

4. Function Call / MCP / Skill 的区别

这是整份清单里最高频的题之一（4 家公司问过）。先看图，再看下面的口诀。

这张图在说什么：这四个词经常被混着说，其实各自解决一个不同的问题——从上到下是「知不知道怎么做」（Skill）、「能不能做」（Tools）、「接起来顺不顺」（MCP）、「调得动调不动」（Function Call）。

它们是四个不同的层面，不是四个互相替代的方案。一个成熟的 agent 这四样都得有——所以这道题的重点不是分个高低，而是说清各自补的是哪块短板。

口诀（必须一次说清）

Function Call 是模型的能力，MCP 是工具的接口标准，Skill 是做事的流程知识。

  • Function Call 解决"能不能调"
  • MCP 解决"接起来太麻烦"
  • Skill 解决"知不知道该怎么做"

再说清它们怎么串起来：一个 Skill 内部可以调用好几个 Tools，这些 Tools 可能通过 MCP 接进来，而真正发起调用靠的是模型的 Function Call 能力。

用"新员工入职"打比方怎么讲？
  • Tools = 公司给他配的电脑、电话、门禁卡
  • Function Call = 他有能力看懂"这个按钮是干嘛的"，并按规范操作
  • MCP = 公司所有设备都用统一接口，不用为每个员工重新布线
  • Skill = 老员工留下的《报销怎么做》《客户投诉怎么处理》手册

渐进式披露：为什么挂几百个 Skill 也不撑爆上下文

如果每个 Skill 的内容（几百上千字）都塞进上下文，挂 50 个就是几万字——还没开始干活，桌面就已经堆满了。

第一层 · 常驻
上下文里只放每个 Skill 的名字 + 一句话描述。50 个 Skill 也就几百 token。
→
模型挑一个
它看着这些描述，判断"这个任务要用到 XX Skill"。
→
第二层 · 按需加载
这时才把这个 Skill 的详细步骤读进上下文。
→
第三层 · 再按需
执行中需要参考时，才加载它附带的脚本、模板、资料。
加分点：把它和 RAG 联系起来

"Skill 的渐进式披露本质上就是对上下文的 RAG：先给一个索引（名字 + 描述），需要时再取出详细内容。

所以它和 RAG 是同一个思想用在两种东西上——RAG 检索的是"知识"，这里检索的是"做事的方法"。"

这句话能把 RAG 那几页和 Agent 这几页打通，很体现理解深度。

5. 工具调用失败了怎么办

只答"重试"是不够的。先判断是哪一类失败，处理方式完全不同：

① 看报错内容，属于哪一类？

参数写错了把报错信息原样告诉模型，让它自己改——这是最有效的一招。比如告诉它"日期格式应该是 2026-09-14"，它下次就改对了
工具自己坏了超时 / 500 / 被限流 → 等一会儿再试（间隔逐次拉长），并且区分"值得重试"和"重试也没用"
工具选错了该用 A 却调了 B → 回去改工具描述、减少工具数量、给它几个例子
查到了但是空的让它换个关键词、或者换一个工具再试
反复调同一个重复调用检测触发 → 强制换策略，或者直接停

② 重试了好几次还是不行呢？

降级把已经拿到的部分结果给用户、转人工、或者老实说做不到。绝不能让 Agent 一直烧钱空转

为什么强调"降级"：用户等 3 分钟拿到一句"抱歉失败了"，比等 10 秒就被告知"这个我做不到，要不要转人工"体验差得多。

6. 通用 Agent 一般分几层

像 Manus 这类"什么都能干"的通用 Agent，从下往上可以拆成四层：

这张图在说什么：通用 Agent 从下往上是模型层 → 能力层 → 编排层 → 交互层。越往下越靠近"模型行不行"，越往上越靠近"用户用不用得上"。

外面看都是"什么都能干"，差距其实在中间两层——同样是接一个强模型，任务怎么拆、上下文怎么保持干净，这些工程细节才拉开距离。

回答时突出"难点在哪"

"从架构上分四层。但真正决定这类产品好不好用的不是模型层，而是编排层和上下文管理——同样是接一个强模型，任务怎么拆、上下文怎么保持干净、失败了怎么恢复，这些工程细节才拉开差距。

这也是为什么"换个更强的模型"往往不解决问题，而"改进外围这套东西"能带来明显提升。"

7. 讲解骨架（看懂之后再背）

这一段就是答案：按顺序把这几件事讲一遍，讲不下去的地方回上面正文补。再往下的「回忆卡」是自测（先合上材料讲，再展开对照），「动手清单」是怎么落到自己项目里。

「说说 MCP、Function Call、Skill 三者的区别」（必考）

【结论】三者解决的是不同层次的问题。

【Function Call】是模型的能力——你告诉它有哪些函数、参数长什么样，它能输出规范的结构化调用请求，解决"模型能不能调工具"。这是模型自带的。

【MCP】是工具的接口标准，可以理解成 USB-C。以前每个工具要对接每个 AI 客户端，M 个模型 × N 个工具就是 M×N 份适配代码；有了统一协议就变成 M+N。它解决"接起来太麻烦"。

【Skill】是做事的流程知识，像一份操作手册，打包了提示词、脚本和参考资料。它解决"知不知道这类任务该怎么做"，而不只是"能调什么工具"。

【补充】Skill 通常用渐进式披露——上下文里只放名字和一句话描述，模型觉得需要时再加载详情。这样挂几百个 Skill 也不会撑爆上下文，本质上是对上下文的 RAG。

Agent 和 Workflow 怎么选？

判断标准是路径能不能提前确定：步骤固定、情况可枚举 → Workflow（更便宜、更快、可预测、好调试）；要看运行时才知道的信息 → Agent。

再补一句成本视角会很专业："Agent 的成本和耗时是不可预测的，Workflow 是可预测的——在需要承诺响应时间的场景里，这一点往往比灵活性更重要。"

怎么调试一个表现不好的 Agent？
  • 把每一轮都记下来：这轮的输入是什么、模型说了什么、调了哪个工具、参数是什么、返回什么。
  • 常见病因：上下文太脏（历史结果堆太多）→ 裁剪或隔离；工具描述不清 → 改描述；轮次限制太紧 → 放宽；模型能力不够 → 换模型或拆任务。
  • 复现手段：把出问题的那一轮上下文原样存下来，离线反复重放，这是最快的定位方式。
什么样的任务不适合用 Agent？
  • 结果要求 100% 确定的：转账、改权限必须走确定性代码，Agent 只能做前置的信息收集和建议。
  • 延迟要求很严的：多轮循环天然慢，实时交互撑不住。
  • 成本敏感的：每轮都要带上全部历史，消耗是普通问答的好几倍。
  • 流程完全固定的：用 Workflow 更好，上 Agent 是自找麻烦。
回忆卡 1 · 合上材料，用自己的话讲一遍

讲一遍 Agent 的主循环。为什么"限制轮次"这一道刹车还不够？

讲完了，展开对照

循环是：组装上下文 → 模型决策（直接答还是调工具）→ 解析调用 → 执行工具 → 结果回灌 → 回到决策。四道刹车：最大轮次、token 预算、时间上限、重复调用检测。

光限制轮次不够，是因为它挡不住"一轮塞进去十万字"——转的圈数少，但每圈都巨大，照样烧钱，所以必须有 token 预算兜底。
