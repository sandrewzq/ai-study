05 · 生成侧与模型选型

检索把资料找回来了，剩下最后一公里：怎么把这些资料用好，以及用哪个模型来做这件事。 这一页的题不多，但都属于"答不好会显得没做过"的类型。

0. 先看一个场景

检索环节已经找回了 5 段资料，都跟"餐厅能不能打包"有关。接下来要做的只有一件事：把这 5 段资料组装成一段文字，连同用户的提问一起发给模型。

听起来很简单，但组装方式直接决定模型用不用得上这些资料——顺序不对、要求没写清，模型就会忽略资料、自己编。

主图 · 一个反直觉的现象

资料放在哪个位置，决定了模型用不用它

放在开头（系统提示后面紧跟着资料）

模型用得很好——开头的位置它最认真看。

放在中间（前面一堆历史、后面还有别的内容）

容易被忽略——夹在中间的内容模型常常"看漏"，业内把这个现象叫"迷失在中间"。它可能明明看到了却说"资料里没有"。

放在结尾（紧挨着用户提问）

用得也好——离问题最近，模型注意力集中。

这张图在说什么：模型对上下文的注意力不是均匀分布的，开头和结尾利用得最好，中间最容易被忽略。

两个实用推论：① 资料少的时候随便放；资料多（十几段）时把最相关的放前面。② 与其塞十段凑数的，不如留三段精准的——少而准比多而杂有效得多。

颜色含义： 用户 模型 / 计算 工具 / 处理 产出 / 存储 数据 / 静态 风险 / 限制

1. 怎么组装这一段提示词

要素要点
角色与任务 一句话说清身份和边界："你是公司内部制度助手，只回答制度相关的问题。"
证据区块 每段资料带编号和出处，比如 [1]（来源：员工手册 4.2 节）……——方便模型引用，也方便你事后核对引用对不对
约束 "只依据以上资料回答"、"资料里没有的要明说不知道"、"每个结论标注引用编号"
顺序 最相关的放开头或结尾，别埋中间（见主图）
历史对话 多轮场景要带上，但注意控制长度（具体手段是步骤 2 的 C 域内容）

2. 幻觉和"拒答"

RAG 最反直觉的一点：检索不到答案时，模型反而更容易编——因为它拿到了几段"看起来相关"的内容，会强行拼凑出一个答案。

手段说明
显式允许拒答 提示词里明确写："如果资料中没有相关信息，回答'根据现有资料无法回答'。"不给它台阶，它就不会承认不知道
强制引用 要求每个结论标注来源编号。编造的内容会因为"找不到引用"而暴露
检索前的门槛 如果最高相似度低于某个阈值，直接走兜底话术，不进模型——从源头避免硬答
生成后校验 用小模型或规则检查：引用是否真实存在、结论是否被引用内容支持
一个容易被忽略的指标

评估 RAG 时，除了"答对率"，一定要单独看两个指标：

  • 该拒答没拒答（幻觉）——最严重，会误导用户
  • 不该拒答却拒答（过度保守）——体验差，但比上面好得多

很多团队只优化"答对率"，结果把模型调成了"什么都敢答"，反而更危险。

3. 输出格式：Markdown 还是 JSON

先说为什么要纠结格式：因为系统要拿模型的输出做后续处理——渲染卡片、存库、调接口、驱动前端组件。不可解析的输出等于白给。

格式优点缺点
Markdown 流式友好（边生成边渲染）；模型生成稳定；前端渲染成本低 不是严格结构，程序解析要写规则
JSON 严格结构，程序直接反序列化；字段清晰 流式不友好（没写完就是非法 JSON）；内容长了容易出错（少括号、多逗号）；模型要为转义分心
结构化输出 / 函数调用 格式由接口层保证，最可靠 需要模型和 SDK 支持；只能表达有限结构
这道题的答法

【结论】原则是：要流式渲染给人看的用 Markdown；要喂给程序做后续处理的用 JSON 或结构化输出。

【为什么主用 Markdown】三个原因：

  • 流式：JSON 没生成完就是非法结构，前端没法边收边渲染；Markdown 可以边收边渲染，用户体感快很多。
  • 稳定：模型写 JSON 容易出错，尤其内容长了之后少个括号整个就废了；Markdown 容错性好，格式错了顶多渲染难看，不影响内容。
  • 顺手：模型训练语料里 Markdown 极多，输出它最自然，格式漂移最少。

【什么时候用 JSON】需要严格结构时（比如要生成一组表单字段、触发特定前端组件），用结构化输出约束让接口层保证格式，而不是让模型"自由发挥写 JSON"，同时做校验和失败重试。

流式输出下的那些坑（做过的人才知道）

难题解法
JSON 流式没法增量解析用支持增量解析的库，或者让模型输出"每行一个完整对象"，逐行解析
Markdown 表格渲染错乱流式时先按纯文本渲染，表格结构收完整了再切成表格组件
代码块没闭合前端容错：收到 ``` 但还没收到结束标记时，按"已开始的代码块"渲染
引用编号满天飞前端解析 [1] 这类标记，替换成可点击的角标，指向对应资料

4. 模型怎么选：六个维度

维度要问自己的问题
能力你的任务需要多强？简单分类抽取用小模型就够；复杂推理必须上大模型
成本输入输出分别多少钱/百万 token？能不能分级路由
延迟首字多快出来？流式场景用户对这个极敏感
合规数据能不能出内网/出境？政府、金融项目通常必须私有化
上下文长度要塞多长的资料？注意"标称长度"和"实际有效长度"不是一回事
稳定性与生态限流策略、可用性、工具调用能力、SDK 成熟度
别只答"我们用了最强的模型"

对方想听的是取舍逻辑。一个高分回答长这样：

"我们把任务分了级：意图识别、格式校验这种简单任务用便宜的小模型，成本和延迟都低；只有最终答案生成和复杂推理才用最强的模型。整体成本降了大概 X%，效果几乎没损失——因为简单任务本来就不需要大模型。"

5. 微调、API、私有化、蒸馏

方案什么时候用注意
调 API 默认选择。知识更新走 RAG，不靠微调 成本随量线性增长；数据合规要评估
微调 固定输出格式、特定语气风格、垂直领域术语；或把大模型能力蒸馏到小模型省钱 要数据要算力；用它灌知识是错的——知识更新要重训，还照样会编
私有化部署 数据不能出内网；或调用量大到自建更便宜 要 GPU 和运维；开源模型能力通常弱一些，要用工程手段补
蒸馏 用大模型生成高质量数据，训一个小模型专做某个任务（如意图分类、改写） 只适合任务边界清晰的场景，通用能力会退化
这道题的答法

【结论】我们没有做微调，走的是第三方 API + RAG。因为核心需求是"知道公司内部知识"，这属于知识问题，应该由 RAG 解决——微调灌知识既贵又难更新，还照样会编。

【做法】模型接入做了一层统一封装：超时重试、限流、失败自动切到备用模型；按任务难度分级路由——简单任务走小模型，复杂生成走大模型。

【什么时候会考虑微调】两个信号：一是输出格式始终不稳定，反复调提示词也压不住；二是某个高频任务用大模型太贵，想蒸馏到小模型。这两个才是微调的合理场景。

【合规】如果客户是政府单位、要求数据不出内网，API 路线就走不通，必须换私有化部署——这类项目要在选型阶段就当成硬约束，而不是事后改造。

6. 成本优化的四条路

这一节和后面"量化指标与成本"那一步直接相关，先建立框架：

方向手段
少调模型 缓存（问题级 / 语义级）；规则能解决的不用模型；合并多次调用为一次
用更便宜的模型 分级路由：简单任务小模型、复杂任务大模型；高频固定任务蒸馏到小模型
少送 token 提高检索精度（少送无用资料）；上下文压缩；提示词缓存（系统提示和工具定义复用）
少重复计算 幂等去重（同一个任务重试时不要重复调模型——这一点在步骤 2 的后端部分会展开）；批处理

7. 讲解骨架（看懂之后再背）

这一段就是答案：按顺序把这几件事讲一遍，讲不下去的地方回上面正文补。再往下的「回忆卡」是自测（先合上材料讲，再展开对照），「动手清单」是怎么落到自己项目里。文中的 X XX X% 不是没写完，是留给你填自己项目数字的槽位——换成真实数字，这段才立得住。

「大模型的选型逻辑是什么」

【结论】我们的选型不是"选最强的"，而是按任务分级 + 按约束过滤。

【做法】先用硬约束筛掉一批：数据能不能出境（决定用 API 还是私有化）、需不需要工具调用能力、上下文够不够长。然后在剩下的里按"能力 / 成本 / 延迟"权衡——意图识别、格式校验这类简单任务用便宜的小模型，最终答案生成用最强的。

【数字】分级路由之后，约 X% 的请求走了小模型，整体成本下降约 X%，P95 延迟下降 X 秒，效果指标基本持平。

【坑】一开始所有请求都用同一个大模型，成本很高但效果并没有更好——因为大部分请求是简单任务。分级之后才发现小模型完全够用。

【权衡】分级路由增加了系统复杂度（要维护两套提示词和评测），而且判断任务难度本身也有成本。所以只在请求量足够大、成本压力明显时才做。

怎么评估换个模型会不会变好？

不能靠感觉，要靠评测集：

  • 固定评测集：用之前建好的「问题 → 期望答案」集合，新模型跑一遍对比指标。
  • 用模型当裁判：让更强的模型给两个模型的输出打分（要有明确的评分维度和示例，否则不稳定）。
  • 人工盲评：关键场景抽样人工对比，注意打乱顺序、别告诉评审哪个是新模型。
  • 线上小流量对比：切一部分流量到新模型，看真实指标（点踩率、追问率、解决率）。

加分点：换模型要同时看效果、延迟、成本三个维度。只看效果容易选出一个"更准但贵一倍、慢两倍"的模型。

模型输出的引用编号是假的（引用不支持结论）怎么办？

这是 RAG 特有的失败模式，叫"引用幻觉"——编号是真的，但那一篇并不支持这句话。

  • 提示词层面：明确要求"引用必须是直接支持该结论的原文"，并给出正反例。
  • 校验层面：生成后用小模型判断"这段资料是否真的支持这句话"，不支持就打标记或重新生成。
  • 产品层面：把引用做成可点击的，让用户一键核对原文——这是最实用的一道防线。
提示词缓存是什么？有什么坑？

很多模型服务支持把不变的前缀（系统提示、工具定义、长文档）缓存起来，后续请求命中缓存的部分按更低价格计费、延迟也更低。

实践要点：把稳定不变的内容放在最前面，每次都变的内容（用户问题、检索结果）放后面。顺序反了就命中不了缓存——这是个很容易踩的坑。

为什么结构化输出常选 Markdown 而不是 JSON？什么时候反而该用 JSON？

讲完了，展开对照

三个原因：流式友好（JSON 没写完就是非法结构，没法边收边渲染）、生成稳定（长 JSON 容易少括号多逗号，一错就全废；Markdown 容错好）、模型顺手（训练语料里 Markdown 多，格式漂移最少）。

需要严格结构时（生成表单字段、触发前端组件）用 JSON，但要通过结构化输出约束让接口层保证格式，而不是让模型自由发挥，同时做校验和重试。

回忆卡 2 · 合上材料，用自己的话讲一遍

模型选型看哪六个维度？为什么"分级路由"是常见的省钱手段？

讲完了，展开对照

六个维度：能力、成本、延迟、合规、上下文长度、稳定性与生态。先用合规这种硬约束筛掉一批，再在剩下的里权衡。

分级路由省钱，是因为真实流量里大部分请求是简单任务（意图识别、格式校验），用小模型完全够用；只有少数复杂请求才需要最强的模型。整体成本能降一大截，而效果几乎不变。代价是系统复杂度上升——要维护两套提示词和评测。
