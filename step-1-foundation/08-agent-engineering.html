08 · Agent 工程化与选型

前面两页讲了 Agent 怎么运作、什么时候该拆。这一页收尾：怎么把它做成一个能上线、能维护、能选型的系统。 核心问题是——大家都用同一个模型，为什么做出来的 Agent 好用程度差好几倍？

读之前

这一页默认你看过 06 · Agent 基础与工具协议（主循环和工具协议）和 00 · 先认识这几个词（概念解释）。没看的话先看那两份。

第一遍（5 分钟）只看主图和加粗句。
第二遍（20 分钟）读正文，重点看第 2 节（Harness）和第 6 节（案例）。
第三遍（5 分钟）做页尾回忆卡。

0. 先看一个问题

你和别人用的是同一个模型，做的也是同一类任务，但人家的 Agent 就是更稳、更少跑偏、更省钱。差在哪？

差在模型外面包的那层东西：提示词怎么写、工具怎么定义、上下文怎么管、循环怎么刹车、出错了怎么办、日志记不记。这一整套，业内叫 Harness（外壳）。

主图 · 这一页的核心概念

模型只是发动机，Harness 才是整台车

这张图在说什么：上面那 8 个部件都不是模型自带的，是你要自己搭的工程。同一个模型，外壳搭得好不好，直接决定它稳不稳、贵不贵、好不好调。

为什么这个概念现在很火：模型半年才更新一次，外壳你每天都能改。所以改外壳的投入产出比，往往高于等一个更强的模型。

颜色含义： 用户 模型 工具 / 外壳 产出 / 存储 数据 / 静态 风险 / 限制

1. claude code 的核心循环与四条设计原则

先明确对方想听什么

问这个（JR-13 KJ-1）不是让你背源码。答"我逐行读过源码"却讲不出设计取舍，反而扣分。他要听的是：你理解它为什么这么设计。

核心循环就是 06 讲的 ReAct 循环，只是工具换成了代码相关的：

这张图在说什么：Agent 干活的节奏是「做一步 → 看结果 → 不对就再来一轮」。四个动作里三个是工具调用，只有"思考下一步"是模型在做——这也是它和普通脚本最本质的区别。

关键在那条回头的虚线：循环什么时候停，取决于"结果符不符合预期"这个判断，而不是跑完固定的步数。所以 agent 靠不靠谱，很大程度上取决于它怎么判断"这一步算不算成功"。

颜色含义： 工具调用 模型判断 判断节点 结束

真正有价值的是它围绕这个循环做的四条设计取舍——这些原则不依赖具体实现，自己写一个 agent loop 也能验证：

原则做法为什么
检索优于全量 不把整个代码库塞进上下文，先搜索定位，只把相关片段带进来 上下文装不下整个仓库；全塞进去噪声大、还贵
工具结果要裁剪 读文件只读需要的行区间，命令输出做截断 避免"读了一个 5000 行文件"直接占满上下文
子任务隔离 搜索、探索类工作交给子 Agent，只回传结论 探索过程又长又乱，不该污染主线上下文
提示词可缓存 稳定的系统提示和工具定义放最前面并缓存 降本提速，也减少上下文抖动
这题的落点

"claude code 的所有设计最终都指向同一件事——管住每一个 session 的上下文。因为决定 Agent 表现的往往不是模型上限，而是上下文质量。这也是为什么它宁可多调几次工具去精确定位，也不愿意把大块内容直接塞进上下文。"

关于"源码泄露"事件该怎么聊？

保持专业和克制，别表现出"我扒了人家的东西"的态度。可以这样答：

"我看过社区的讨论和基于它做的分析。有意思的不是某段实现细节，而是它印证了几个设计原则：检索优于全量、工具结果必须裁剪、子任务要隔离、提示词要能缓存。这些原则不依赖具体实现，自己实现一个 agent loop 也能验证。"

然后把话题引到自己的实践上——这比背源码细节有价值得多。

2. Harness 到底是什么

上一节主图里那 8 个部件，加上把它们串起来的逻辑，合起来就叫 Harness。换个说法：

类比

模型是发动机，Harness 是整台车。同一个发动机装在不同车架上，跑出来的性能、油耗、舒适度差很多。

而且更关键的一点：发动机半年才换一次，车架你自己随时能改。

部件不管它会发生什么
系统提示词模型不知道自己的角色和边界，什么都敢答
工具定义与执行模型只会说话，干不了活；工具描述写不清它就选错
上下文管理跑十几轮之后上下文被历史塞满，模型开始跑偏
循环控制死循环，一直烧钱不产出
错误处理工具一失败整个任务就崩
可观测性出问题完全没法查，只能"感觉最近变差了"
权限与沙箱模型可能删掉不该删的文件、调用不该调的接口
人机协作该停下来问人的时候它自作主张
Harness 和 Agent 框架（LangChain 之类）是什么关系？

有重叠但不完全等同：

  • 框架是给你用的代码库，你用它搭 Harness。
  • Harness 是最终跑起来的那个系统——框架只是其中一部分，还包括你写的提示词、工具实现、循环控制、日志、权限。

所以完全不用框架也能有 Harness（很多人手写 agent loop，反而更可控）；反过来，用了框架不等于 Harness 做得好。

3. LangChain 和 LangGraph 怎么选

LangChainLangGraph
定位 各种组件的工具箱：模型、向量库、工具、检索器的统一封装 用图来编排流程和 Agent
核心概念 链、提示词模板、检索器、工具 节点 + 边 + 状态
适合 简单线性流程、快速搭原型、需要现成的组件集成 多分支、循环、多 Agent、需要显式状态和人工介入

判断标准很简单：流程有没有分支和循环。线性流程（检索 → 拼提示词 → 生成）用 LangChain 就够，甚至不用框架也行；有分支、有循环、要多 Agent 协作，才需要 LangGraph 那种状态机。

版本变化（HQ-25 问的就是这个）

对方问"不同版本/模块的区别"，其实是在验证你是否真的用过：

模块职责
langchain-core核心抽象（提示词、消息类型、可组合的调用单元）
langchain-community社区维护的各种第三方集成
各家厂商的独立包模型适配，单独发版、单独升级
langgraph图编排，独立于 LangChain 演进

另一个变化是写法：早期用 LLMChain 这类类的方式，现在推荐用管道符把组件串起来，或者直接上 LangGraph。

选型怎么答（要说出取舍）

"选它是因为生态全、组件多、原型快。但有几个实际问题：抽象层厚，出问题不好排查——一层层封下去，报错信息很难定位到根因；而且版本迭代快，容易踩不兼容。

所以我们的做法是：框架只用在"胶水"部分——模型接入、工具封装用它省事；核心链路（检索、重排、上下文管理）自己写，避免被框架绑架。这样将来换框架的迁移成本也可控。"

4. 通用能力模块怎么抽象

对方问"你们抽象了哪些通用 AI 能力"（JR-3），实际在问你的工程化水平。

模块抽象了什么
模型接入层统一各家模型的调用接口；超时重试、限流、失败自动切到备用模型
提示词层模板管理、版本管理、变量注入（提示词是资产，要能迭代和回滚）
检索层统一的检索接口（向量 / 关键词 / 混合），上层不关心底层用的什么库
工具层工具注册、参数校验、权限控制、调用日志
上下文层会话管理、压缩、裁剪策略
可观测层token 统计、成本核算、调用链追踪、效果评估
一句话点出抽象的目的

"抽象的目的有两个：一是换模型、换向量库不用改业务代码——我们实际换过一次向量模型，只改了配置层；二是成本和效果可度量——每个模块的 token 消耗、延迟、命中率都能单独看到，不然优化就是盲猜。"

5. 意图识别与路由

用户的问题五花八门，不可能都走同一条路。所以需要先判断他想干什么，再决定送到哪里处理。

这张图在说什么：意图识别不是"一步判断准"，而是从便宜到贵逐层筛——先用规则挡掉大部分（零成本、可解释），剩下的交给小模型，只有复杂模糊的才动用大模型。

关键在每一层都要能说"我不确定"然后往下一层交。硬猜是最糟的处理：猜错了用户会遇到答非所问，体验比直接问"你是想问 X 还是 Y"差得多。

颜色含义： 用户 判断 / 决策 路由执行 往下一层的条件
方式优点缺点
关键词规则快、准、可解释、零成本覆盖窄，用户换个说法就失效
小模型分类成本低、延迟低、稳定要标注数据训练；意图变了要重训
大模型分类灵活、零样本可用、意图随时改慢、贵；结果有一定随机性
向量相似度意图多变时好维护（改描述即可）相似意图容易混
加分点：必须提置信度和兜底

"意图识别一定要有置信度机制和兜底路径。识别不出来的时候别硬猜——猜错了用户会遇到答非所问，体验比直接说'我没理解，你是想问 X 还是 Y'差得多。

我们的做法是分层过滤：规则先兜一层（明确的直接路由），剩下的交给模型；模型置信度低于阈值就走通用问答或者给澄清选项。这样既保证了大部分请求的低延迟，又保住了准确率。"

6. 完整案例：一个检索 Agent 的设计

这道题（YU-19「你自主设计过智能体吗」）用五段式准备一个具体例子。下面是完整示范。

参考回答

【结论】我设计过一个检索 Agent，职责是把用户的口语问题变成精准的知识库查询，并返回可靠的证据。

【做法】它有三步：先做查询改写（含多轮对话的指代消解），然后并行发两路检索——关键词和向量语义，用 RRF 融合，再用交叉编码器精排到 Top 5 返回。工具集就三个：改写、检索、精排。它只读不写，不碰任何业务数据。

【数字】上线后专有名词类问题的命中率从 X% 提到 Y%，检索环节 P95 约 X 毫秒，占整个问答链路耗时的 X%。

【坑】一开始我把三个步骤合成一个"大检索"工具，模型经常一次传错参数整条链路就失败。拆成三个小工具之后，模型可以单独重试某一步，鲁棒性明显变好。

【权衡】但拆细了轮次变多、延迟上升。最后的折中是"改写 + 检索"合并成一个工具，"精排"独立——因为精排失败率高且需要单独调参，值得单独一步。

这个例子为什么好
  • 有具体的职责边界（只读、不碰业务数据）
  • 有数字（命中率、延迟、占比）
  • 有真实的坑（工具粒度问题）
  • 有权衡和修正过程（一个大工具 → 三个小工具 → 折中方案）

对方听完能判断出：这个人真的设计过、跑过、改过。

7. 讲解骨架（看懂之后再背）

「claude code 的核心循环 / 多层架构是怎么做的」

【结论】它的核心是一个主循环：模型判断该做什么，调用工具（读代码、搜代码、改代码、跑测试），把结果回灌到上下文，再进入下一轮，直到问题解决。

【做法】真正值得说的是它围绕这个循环做的工程取舍，有四条原则：检索优于全量（先用搜索精确定位，不把整个仓库塞进去）；工具结果要裁剪（读文件只读需要的行区间）；子任务隔离（探索类工作交给子 Agent，只回传结论）；提示词可缓存（稳定部分放最前面）。

【坑】我自己实现 agent loop 时踩过反例：一开始把整个文件内容都塞进上下文，跑几轮就爆了，而且模型被无关代码干扰、改错地方。改成先搜索定位、只读相关行区间之后，效果立刻不一样。

【权衡】这些设计都有代价——检索多花一次工具调用、裁剪可能导致信息不全、子 Agent 有通信开销。所以判断标准是：只有当信息明显超出上下文预算时才做这些取舍，小任务不值得。

【落点】所有设计最终指向同一件事：管住每一个 session 的上下文。决定 Agent 表现的不是模型上限，而是上下文质量。

为什么说"抽象层太厚不好排查"？

因为出问题时你要一层层往下找：框架封装了重试逻辑，你看到的报错是"链执行失败"，但根因可能是底层网络超时、也可能是提示词变量没注入、还可能是输出格式解析失败。

实践上两条应对：① 把关键链路自己写，框架只用在边缘；② 强行打开详细日志，确保每一层的输入输出都能看到。第二条在排查线上问题时是救命的。

怎么评估 Harness 改得好不好？

不能在线上凭感觉，要有一套离线评测：

  • 固定一批任务（含成功案例和已知的困难案例），每次改动都跑一遍。
  • 看三类指标：任务成功率、平均轮次 / token 消耗、失败类型的分布（是工具选错变少了，还是死循环变少了）。
  • 改动的收益要大于它带来的复杂度——Harness 越复杂，出问题的面也越大。
你们为什么用 / 不用 Agent 框架？

两种回答都有说服力，关键是给出理由：

  • 用："生态全、原型快，尤其是模型接入和工具封装这些重复劳动能省掉。"
  • 不用："我们的链路不复杂，直接手写 agent loop 更可控、更好调试，也避免被框架的版本升级绑架。"

通用建议：框架用在边缘（接入、封装），核心链路（检索、重排、上下文管理）自己掌控。

Harness = 把裸模型包装成能干活的系统所需要的整套东西：系统提示词、工具定义与执行、上下文管理、循环控制、错误处理、可观测性、权限沙箱、人机协作。
