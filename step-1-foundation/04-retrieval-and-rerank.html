04 · 检索优化与重排

库里存好了，接下来是怎么查得准。这一页是 A 域分差最大的一页——这里的题几乎都会连着追问三层， 答得出第一层的人很多，答得出第三层的人很少。

0. 先看一个场景

员工问：「餐厅能打包吗？」——知识库里明明有"员工餐厅不提供外带打包服务"这一条，但系统没把它找出来。

查了一下召回结果，里面是"餐厅环境介绍""员工福利概览"这些。为什么？

原因怎么办
用户的说法和文档对不上
用户说"打包"，文档写"外带打包服务"		 查询优化：先改写、扩写出几种说法再去查
只做了语义匹配
短查询里没几个词，向量算出来很"糊"		 混合检索：再加一路关键词匹配
捞回来一堆，但排前面的不是最相关的 精排：从候选里挑出真正能回答问题的

这三件事就是这一页的全部内容：查询优化 → 混合召回 → 精排。

主图 · 这一页最核心的一个认知

「语义相似」不等于「能回答问题」

这张图在说什么：找相似内容有两种技术。双塔把问题和文档分别编码成向量再比距离——因为文档向量能提前算好，所以快，但问题和文档互相看不见，精度一般。交叉编码把两者拼在一起送进模型，注意力能逐词对齐，所以准，但每一对都要现场推理一次，慢。

所以分工就很清楚了：用双塔快速从百万里捞出几十个候选（召回），再用交叉编码从这几十个里精挑出三五个（精排）。

颜色含义： 用户 模型 / 计算 工具 / 处理 产出 / 存储 数据 / 静态 风险 / 限制

1. 完整链路：一次提问到底经过什么（HQ-29）

改写问题
把口语问题改写成适合检索的说法，顺带补全多轮对话里的指代（"那标准呢" → "差旅费报销标准是什么"）。
→
两路并行召回
关键词那一路去 ES 捞 50 条，语义那一路去向量库捞 50 条。两路必须并行发，串行等于白花一倍时间。
→
融合
把两路结果合成一份排名。用的是 RRF（只看名次，不看分数），原因见第 3 节。
→
过滤去重
按权限、生效日期、文档类型过滤，去掉重复内容。权限必须在这一步就过滤掉，不能留给模型判断。
→
精排 + 生成
交叉编码器从候选里挑出最相关的 3~5 条，拼进提示词交给模型回答。

这张图在说什么：召回求"不漏"，精排求"精准"。两步的 K 值完全不同——召回要多（50~100），送进模型的要少（3~5）。

2. 查询优化：用户的问题不是好查询（HQ-27、HQ-31）

用户提问有两个特点：短（几个词）、口语（"打包吗"）。而知识库里写的是正式表述（"不提供外带打包服务"）。用词对不上，自然召不回。

手段做什么例子
查询改写 把口语问题改写成适合检索的正式表达，并对齐知识库用词 "报销咋整" → "差旅费报销流程、报销标准、所需材料"
多查询 一个问题生成 3~5 个不同说法，分别检索后合并去重 "怎么报差旅费" / "差旅报销标准" / "出差费用怎么申请"
子查询 复合问题拆成几个小问题分别查 "A 和 B 有什么区别" → 分别查 A、查 B
HyDE 先让模型假想一个答案，用这个假答案去检索 下面单独讲，这是最反直觉的一种
指代消解 把多轮对话里的"它""那个"补全成完整问题 上文在聊报销，用户问"那标准呢" → "差旅费报销标准是什么"
HyDE 的直觉（容易讲不清，重点看）

用户问"能打包吗"，知识库里写的是"员工餐厅不提供外带打包服务"。问题很短、文档也是一句话，两边措辞对不上，向量距离可能不近。

但如果先让模型编一个像模像样的答案（"员工餐厅一般不提供外带打包服务，需要堂食……"），这个假答案的措辞就和真文档接近多了，用它去检索就准得多。

核心思路：用"答案的措辞"去匹配"答案"，而不是用"问题的措辞"去匹配"答案"。假答案只是用来找路，不会出现在最终回答里。

代价与选择：不要全上

查询优化每一步都要调一次模型，延迟和成本都会上升。按需组合：

  • 单轮问答、问题清晰 → 只做改写就够
  • 多轮对话 → 必须加指代消解
  • 召回效果差、专业术语多 → 加多查询 + HyDE
  • 问题明显是复合的 → 加子查询

另外改写结果可以缓存——高频问题直接复用，这是最省事的一个优化。

领域词典 / 同义词表放在两个地方生效：查询改写那一层做同义词扩展（"社保" ↔ "社会保险"），ES 那一层做自定义分词词典（保证"超融合一体机"这种专业词不被切碎）。而且它是要持续维护的——线上发现搜不到的说法，就补进去。

3. 融合：为什么不能把两路分数相加

两路召回后要把结果合成一份排名。最直觉的做法是把分数加起来，但这样是错的：

问题说明
两边分数量纲不同 BM25 的分数可能落在 0~20，向量相似度是 0~1。直接相加，关键词分会单方面碾压，融合就退化成"只看关键词"了
归一化也治不好 某一路出现一个远高于其他结果的分数，归一化后会把整条路的权重带偏
RRF 的聪明之处

RRF（倒数排名融合）干脆不看分数，只看名次：一个文档在每一路里排第几，换算成一个分数再加起来。

名次天然可比，而且对异常分数免疫，几乎没有需要调的超参——这就是它成为标准做法的原因。

4. 精排的代价，以及怎么缓解（HQ-30）

精排准，但慢——每一对「问题 + 候选文档」都要现场跑一次推理，无法像双塔那样预计算。加了精排延迟会上升，缓解手段：

手段说明
缩小候选集100 条 → 30 条。候选少一半以上，延迟线性下降，精度损失通常很小
只精排前 20 条剩下的保持原序。把算力花在最可能有用的部分
结果缓存相同或相似的问题直接命中缓存，高频问题收益极大
用更小的模型精排模型有不同尺寸，小模型快很多，精度损失可以接受
批处理所有候选一次性送进模型，比逐条推理快得多

5. 怎么加速检索：先问瓶颈在哪（JR-6）

上来就背优化手段会显得没做过。检索链路上有四段，慢的通常不是同一处：

查询优化 · 200~800ms
调模型改写/扩展查询。常常是最大的瓶颈——纯等待，而且挡在检索前面。
→
两路召回 · 10~100ms
向量 + 关键词并行召回。这段反而最快，因为走的是索引，不调模型。
→
精排 · 100~500ms
交叉编码逐条打分。用精度换时间，所以要控制候选数量。
→
生成 · 首字 300ms~2s
流式输出，边生成边推。用户感知到的等待主要是"首字时间"。
颜色含义： 要调模型 走索引 产出
慢在哪怎么优化
查询优化改写结果缓存；简单场景用规则代替模型；换更小的模型
召回调 efSearch 权衡；加元数据预过滤（先按部门/年份缩小范围再算向量）；两路并行
精排缩小候选集；批处理；用小模型（见上一节）
生成流式输出，先把首字吐出来，用户体感就快了
通用问题级缓存（相同问题直接返回）；减少无效数据（过期文档下线）
回答模板

"我们会先看监控定位瓶颈：如果是查询优化慢，就用缓存和更小的模型；如果是召回慢，就调 efSearch、加元数据预过滤；如果是精排慢，就缩小候选集、加批处理；如果是生成慢，就上流式先把首字吐出来。"

顺带说一个真实收益会很有说服力："加了查询改写缓存之后，P95 从 X 秒降到 Y 秒。"

6. 答不准时，按什么顺序排查（YF-7）

这一节和第 01 篇第 4 节是同一件事，这里展开成四步。从上游往下游查，不要乱试。

① 数据层：文档解析对了吗？切分合理吗？是不是压根没入库？权限过滤掉了吗？

有问题回到 02 修数据——这一步坏了，后面怎么调都没用
没问题看下一步

② 检索层：该召回的段落，在捞回来的 50 条里出现了吗？

没出现检索问题：改查询优化 / 换向量模型 / 加关键词那一路
出现了看下一步

③ 精排层：精排把正确的那条排到后面去了吗？

是换精排模型，或调整候选集大小
不是看下一步

④ 生成层：证据给对了，模型还是答错？

是提示词组装问题（证据太散、没强调"基于以下内容回答"），或者模型能力不够、噪声太大

7. 怎么证明召回是准的（JR-10）

严肃场景（政策、法律、医疗）必须能回答"你怎么验证的"，否则"我们准确率很高"就是空话。

方法说明
建评测集
黄金标准		 人工标注几百个「问题 → 正确片段」对。这是唯一能客观衡量的基础
算指标 Recall@K：正确片段有没有进前 K（衡量"漏没漏"）
MRR：正确片段排得靠不靠前（衡量"准不准"）
命中率：多少问题至少命中一条正确片段
人工抽检 定期抽样真实问答，人工判断召回内容对不对。严肃场景不能省这一步
线上反馈 点踩率、追问率、引用点击率、平均轮次（一轮解决还是反复追问）
政策文件场景的加分答法

"政策文件这类场景我们除了通用指标，还额外做两件事：

一是按生效日期过滤——同一个问题不同年份答案不同，绝不能让 2019 年的文件回答 2025 年的问题；

二是引用可核对——答案里每条结论都能点回原文那条，用户和审核人员可以自己验证。

另外这类场景不能只依赖用户反馈来发现问题——政策答错是要出事的，所以我们坚持人工抽检。"

8. 讲解骨架（看懂之后再背）

这一段就是答案：按顺序把这几件事讲一遍，讲不下去的地方回上面正文补。再往下的「回忆卡」是自测（先合上材料讲，再展开对照），「动手清单」是怎么落到自己项目里。文中的 X XX X% 不是没写完，是留给你填自己项目数字的槽位——换成真实数字，这段才立得住。

「你们的检索是怎么做的 / 怎么保证召回准确」

【结论】我们的检索是"查询优化 + 混合召回 + 精排"三段式。核心认知是：向量检索解决语义相似，但语义相似不等于能回答问题，所以召回之后必须精排。

【做法】用户问题先做改写和指代消解；然后并行走 ES 关键词和向量两路，各取 Top 50，用 RRF 融合；融合后按权限和生效日期过滤、去重；再用交叉编码器精排到 Top 5 交给模型。两路是并行发的。

【数字】知识库 XX 万段；评测集 XXX 个问题，召回 50 条的命中率 X%，精排后 Top 5 的命中率 Y%；检索全链路 P95 约 X 秒。

【坑】早期只做向量召回，产品型号和条款编号经常搜不到。加了关键词那一路之后这类问题基本消失。另外一开始用"先检索再过滤"做权限，小部门用户经常搜不到东西，改成检索时带条件才解决。

【权衡】精排让准确率明显提升，但延迟增加。我们把候选从 100 缩到 30，并对高频问题做了结果缓存，把延迟压回可接受范围。

为什么用 RRF 而不是加权求和？

因为两路分数量纲不同、不可比：BM25 是 0~20 这个量级，向量相似度是 0~1。直接相加的话关键词分会单方面主导。

归一化能缓解，但对异常值敏感。RRF 只看名次，天然可比、对异常值免疫，而且几乎没有要调的超参。

HyDE 会不会引入幻觉，让检索跑偏？

会，这是它的固有风险——假答案本身可能是错的。但实践中有三层保险：

  • HyDE 只用来生成检索向量，假答案不会出现在最终回答里，不会污染给用户的内容。
  • 它是多路召回中的一路，不是唯一路径——和原始查询的结果一起融合，错了也只是少一路贡献。
  • 事实性要求极高的场景可以不用它，改用多查询或关键词扩展，效果更可控。
topK 设多少合适？

分两段看，很多人会混为一谈：

  • 召回阶段的 K 要大（50~100），目的是"别漏"——宁可多带一些让精排去筛。
  • 送给模型的 K 要小（3~5），目的是"别吵"——塞太多无关内容反而降低答案质量，还费钱。

正确结构是：召回多、精排狠、入提示词少。具体数值要靠评测集调，不同领域差异很大。

没有足够的标注数据，怎么建评测集？
  • 从真实日志里采样：挑高频问题，人工标注正确答案所在片段——几百条就够起步。
  • 用模型造题 + 人工审核：让模型基于文档生成问答对，人工过一遍筛掉错的，效率高很多。
  • 从存量问答记录里挖：已有的客服问答天然就是"问题 → 答案"对，只是要人工关联回文档片段。

关键：评测集要持续扩充。线上每发现一个答错的 case 就补一条进去，它才会真正变成"防线"而不是一次性作业。

回忆卡 1 · 合上材料，用自己的话讲一遍

为什么"语义相似"不等于"能回答问题"？粗排和精排分别用什么技术，为什么？

讲完了，展开对照

向量检索找的是语义相近的段落，但它们未必能回答用户的具体问题——比如两个段落都在讲餐厅，一个是"环境介绍"（相似的），一个是"不提供外带打包"（用户要的）。

粗排用双塔：问题和文档分别编码，文档向量能离线预计算，所以快，但精度一般。精排用交叉编码：两者拼在一起送进模型，能逐词对齐，所以准，但每对都要现场推理。

回忆卡 2 · 合上材料，用自己的话讲一遍

完整讲一遍追问链：RAG 流程 → 怎么加速 → 召回不准怎么办 → 为什么还要精排 → 加了精排变慢怎么办。

讲完了，展开对照
  1. 流程：查询优化 → 两路并行召回 → RRF 融合 → 过滤去重 → 精排 → 生成。
  2. 加速：先定位瓶颈在哪一段（查询优化常是大头），再对症——缓存、并行、预过滤、缩小候选集、流式输出。
  3. 召回不准：先确认"正确片段在不在捞回来的 50 条里"。不在，是检索问题：改查询优化、换向量模型、加关键词那一路。
  4. 为什么要精排：召回的 K 很大是为了"不漏"，里面混着大量不相关的；而且"意思相近"不等于"能回答"，只有交叉编码能分辨。
  5. 变慢怎么办：缩小候选集、只精排前 20 条、结果缓存、换小模型、批处理。
