07 · 多智能体

上一篇讲的 Agent 是"一个 Agent 干所有事"。这一页讲：什么时候该把一个 Agent 拆成几个， 以及拆的代价是什么。后半问才是分水岭——只会说好处的人，一追问就露馅。

读之前

这一页默认你看过 06 · Agent 基础与工具协议（Agent 主循环）和 00 · 先认识这几个词（概念解释）。没看的话先看那两份。

第一遍（5 分钟）只看主图和加粗句。
第二遍（15 分钟）读正文，重点看第 2、3 节（代价和判断标准）。
第三遍（5 分钟）做页尾回忆卡。

0. 先看一个场景

你做了一个 Agent，让它"调研一个竞品并写份分析报告"。它能干，但干得越来越糊：

  • 跑到第 15 轮，它还在改第一版的结论——因为第一版的错误假设还在上下文里，它被自己带偏了
  • 让它"评审自己刚写的东西"，它几乎永远说"还不错，可以再补充一点"
  • 检索、分析、写作三种活混在一个提示词里，写出来的东西既要发散又要收敛，自己跟自己打架

这些毛病的共同点是：所有东西都堆在同一个上下文里。多智能体的核心思路就是——把上下文隔离开。

主图 · 多 Agent 解决的核心问题

不是"分工"，是"让每个 Agent 的上下文干净"

这张图在说什么：左边那种"一个大上下文装所有东西"的 Agent，跑到后面会被自己的历史绑架；右边把上下文拆开，每个 Agent 的判断都更干净。

一句话记住：决定 Agent 表现上限的，不是模型有多强，而是上下文有多干净。

颜色含义： 用户 模型 / 判断 工具 / 执行 产出 / 存储 数据 / 静态 风险 / 限制

1. 从"单 Agent 哪里不行"倒推动机

背定义没用，从问题倒推才是对方想听的：

单 Agent 的问题多 Agent 怎么解决
上下文越来越脏
最核心的动机		 上下文隔离：每个 Agent 只看自己该看的，不被别的环节的过程污染
自己评审自己不客观 评审 Agent 拿到的是"待评内容 + 评审标准"，没有"这是我刚写的"这层包袱
提示词里两套指令打架 一个提示词里同时要求"发散想 10 个方案"和"严格评审"，模型会左右为难。拆开后各自专门优化
串行太慢 互不依赖的子任务（检索、分析）可以并行跑，总耗时取决于最慢的那个
工具集太杂 一个 Agent 配 20 个工具会挑花眼。按角色分配工具集，选择空间小了，选错的概率也降了
「多 Agent 主要解决什么问题」的标准答案

主要解决"上下文污染"和"角色冲突"两个问题，顺带拿到并行能力和交叉验证。

这两点为什么最关键：Agent 的能力上限不取决于模型有多强，而取决于上下文有多干净。一个上下文里混着调研笔记、历史失败方案、"我之前已经决定用 A 方案"的 Agent，越到后面提出的想法越飘——因为它在被自己的历史绑架。

2. 拆的代价：不是免费的

这一节是分水岭。只会说好处的人在背课文，能说清代价的人做过系统。

代价说明
信息会在传递中丢失 Agent 之间传的是自然语言。A 想说的和 B 理解的可能不是一回事——这是最容易出事的一条
状态一致性 多个 Agent 并行干活，各自的中间状态要同步和合并，冲突怎么解决是个真问题
责任边界模糊 结果错了，是检索没找到、分析算错了、还是汇总理解错了？排查链路一下子变长
互相踢皮球 Agent 之间互相转交任务，谁都不收尾。必须设明确的终止条件和轮次上限
延迟和成本上升 每个 Agent 都是一次独立的模型调用，通信本身也要消耗 token
调试难度 单 Agent 是一条日志线，多 Agent 是一张网。可观测性做不好就没法调

3. 判断标准：什么时候该拆

① 这个子任务需要独立的上下文吗？（放一起会互相污染）

需要值得拆 —— 这是拆多 Agent 最核心的理由
不需要看下一个问题

② 它能和别的子任务并行跑吗？

能值得拆 —— 拿到并行收益
不能看下一个问题

③ 它需要不同的工具集 / 权限，或者需要独立评审吗？

需要值得拆
都不需要不要拆 —— 拆了只增加通信成本，是负收益
核心论点（背下来）

"拆不是免费的。多 Agent 有通信成本和状态一致性成本——信息在传递中会丢失，责任边界会模糊，还会互相踢皮球。

我的判断标准是：只有当子任务需要不同的上下文、或者可以并行时才拆。纯粹为了让架构'看起来专业'而拆，是负收益。"

一个很务实的补充

真实项目里两三个 Agent 通常就够（检索 / 执行 / 评审）。那些动辄七八个 Agent 互相讨论的架构，多数演示好看、上线很痛苦。

讲的时候这么说会显得很实在："我们现在只拆了两个——检索和评审，再往下拆的收益已经抵不过通信开销了。"

4. 四种编排方式

模式结构适合
主管制 一个主 Agent 负责拆任务、分派给下属、汇总结果 最常见、最好调试：有明确的负责人，出问题能定位
流水线 A 的输出给 B，B 给 C（调研 → 分析 → 写作 → 评审） 步骤固定、依赖清晰。其实更接近 Workflow
辩论制 多个 Agent 从不同角度给意见，再由一个裁决者综合 需要多视角判断。成本高，慎用
蜂群 Agent 之间自由传递任务，没有中心调度 灵活但极难控制和调试，生产环境很少用

选型建议：从主管制开始。它结构最简单、最容易加日志、最容易定位问题。只有当主管自己明显成为瓶颈（比如它的上下文被撑爆了）才考虑更复杂的拓扑。

动态路由：让模型决定下一步走哪个分支

静态路由是流程图写死的（先 A 再 B 再 C）；动态路由是让模型根据当前情况决定。

实现方式说明
模型分类
最常用		把候选分支和各自的适用条件写进提示词，让模型输出选哪个（以及理由）
函数调用把"选择分支"做成一个函数，参数是分支名和理由，格式由接口层保证
规则 + 模型兜底明确场景走规则（快、稳、便宜），模糊的才交给模型。生产环境最实用的组合

动态路由必须注意的三个坑

坑 1没有兜底分支。模型选不出来、输出格式不对时走哪条路？没有兜底就等于这一步失败整条链路就崩
坑 2不限制跳转次数。Agent 之间互相转交，很容易出现 A 转给 B、B 又转回 A 的死循环
坑 3路由日志没留全。线上出问题第一个要看的就是"为什么走了这个分支"，没日志根本没法调

5. 一个反直觉结论：互相 review 是伪需求

常见做法是"让两个模型互相 review、多轮 loop 改稿"，听起来很高级，实际上不产生收敛：

为什么互相 review 没用

只要让两个模型互相审，它们永远能告诉你"还能怎么改进""还可以从哪个角度优化"。

因为"挑出可以改进的地方"是几乎无成本的任务——任何文本都能找出十条改进建议。但这不等于变得更好了。多轮 loop 的结果往往是：改了十几版，每版都"有道理"，但没有一版真正收敛。

更糟的是，评审者看到了前面的讨论历史，会被带偏（又是上下文污染）。

有效的做法是「独立评审 + 明确标准」

做法说明
上下文隔离评审者只拿到"待评审对象 + 评审维度"，不拿历史讨论、不拿其他候选方案
明确评分维度不是问"这个好不好"，而是问"新颖度够不够、技术上可行吗、跟现有方案的兼容性如何、实现复杂度可控吗"
逐项独立评估每个候选单独评估，而不是把十个候选放一起让模型排名（那样会有顺序偏差和互相影响）
产出结构化结论评分 + 判断理由 + 明确结论（通过 / 修改 / 否决），而不是一段含糊的评价
限定轮次最多一轮修订。不追求"改到完美"，因为不存在完美，只存在"够用"

工程上怎么做到"只回传结论"

手段说明
只回传结论，不回传过程子 Agent 干了 10 轮、读了 20 个文件，但给主 Agent 的只有一段结构化结论 + 出处。过程留在它自己的上下文里
各自独立的上下文不共享同一个对话历史，只有显式的"交接"才传递信息
约定交接格式交接内容固定为：结论、证据、置信度、待解决问题。自由发挥的自然语言交接会丢信息
写操作收敛到主 Agent子 Agent 尽量只读，所有写操作由主 Agent 统一执行，避免冲突

6. 讲解骨架（看懂之后再背）

「什么是多 Agent？为什么需要？什么场景该用？」（一条链，连着答）

【结论】多 Agent 是把一个任务拆给多个有独立角色和上下文的 Agent。它主要解决两个问题：上下文污染和角色冲突，顺带拿到并行能力。

【做法】我们拆了检索和评审两个 Agent。检索 Agent 的上下文里只有查询和结果，不会被后续写作过程污染；评审 Agent 拿到的只有"待评审对象 + 评审维度"，没有历史包袱，判断更客观。两个各配独立的工具集，主 Agent 只负责分派和汇总。

【数字】拆分之后，评审结论的一致性明显提升（同一份内容多次评审的结果更稳定）；检索和评审可以并行，总耗时下降约 X%。

【坑】一开始让两个 Agent 共用一份对话历史，结果评审者被前面的讨论带偏，永远说"还能改进"。改成上下文隔离之后才有收敛。

【权衡】拆不是免费的——通信成本、状态一致性、排查难度都会上升。我的判断标准是：只有当子任务需要不同上下文、或者能并行时才拆。所以我们现在维持在两个，再拆的收益抵不过开销。

单个 Agent 也能分配多个职能，为什么还要多 Agent？

关键差别在上下文，不在职能数量。

单 Agent 即使提示词里写了"你要依次扮演检索员、分析员、评审员"，它跑的仍然是同一份上下文——检索阶段的笔记、分析阶段的失败尝试、它自己刚说过的结论，全都还在。到了评审环节，它是在评价自己刚写的东西，天然倾向于维护原有判断。

多 Agent 的本质是给每个角色一份干净的上下文。这才是拆分的真正价值。

多 Agent 之间怎么通信？用什么格式？
  • 自然语言消息：最灵活，但容易丢信息。
  • 结构化对象（固定字段）：明确、可靠、可校验，推荐用于关键交接。
  • 共享状态 / 黑板模式：所有 Agent 读写同一份状态，灵活但并发冲突要额外处理。

建议：关键交接用结构化格式，中间讨论可以用自然语言。另外每条交接都要带"来源 Agent"和"时间戳"，不然排查问题时对不上。

多 Agent 系统的成本怎么控？
  • 限制 Agent 数量：每一个都是一次独立调用，能合就合。
  • 限制轮次：给每个 Agent 设自己的轮次上限。
  • 分级用模型：简单角色（检索、格式转换）用小模型。
  • 只回传结论：避免大段中间结果在 Agent 之间反复搬运——这是成本失控最常见的原因。
  • 统计每个 Agent 的 token 占比：先知道钱花在谁身上，再优化。

多 Agent 解决的核心问题是什么？拆的代价有哪些？

讲完了，展开对照

核心问题：上下文污染 + 角色冲突（自己评审自己不客观），顺带拿到并行能力。

代价：信息在传递中丢失、状态一致性、责任边界模糊（排查链路变长）、互相踢皮球、延迟和成本上升、调试难度大增。

一句话落点：决定 Agent 上限的不是模型有多强，而是上下文有多干净。

回忆卡 2 · 合上材料，用自己的话讲一遍

什么时候该拆多 Agent？什么时候不该拆？动态路由要注意什么？

讲完了，展开对照

该拆：子任务需要独立上下文 / 能并行 / 需要不同工具集权限 / 需要独立评审。

不该拆：上下文本来就一样；必须串行且强依赖全部细节；工具集重合；只是"想让架构好看"。

动态路由三坑：必须有兜底分支；必须限制跳转次数（否则 Agent 互相踢皮球）；路由日志要留全（否则没法排查）。
