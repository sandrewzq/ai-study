08 · 支付与对账

支付是最不能出错的一类业务：钱扣了但东西没给，用户会投诉甚至投诉到监管。 这一页讲清一件事——为什么"收到回调就发货"是错的。

0. 先看一个场景

用户买了 100 积分的套餐，微信显示已支付成功。但用户回到 App 一看：积分没到账。

查日志发现：微信确实回调了，但那一刻你的服务正在发版重启，回调请求丢了。微信不会无限重试——重试几次失败后就不再发了。

结果就是：钱收了，货没发。这是支付系统最典型的事故，也是 PY-19 那道题问的核心。

主图 · 一笔支付要经过八步

第 6 步之后才是真正容易出事的地方

这张图在说什么：前五步都是"正常流程"，只要代码没错就没问题。真正的难点在第 ⑥ 步之后——回调是外部系统主动推给你的，你控制不了它什么时候来、来几次、是不是真的。

颜色含义： 用户侧 你的后端 校验处理 发货 风险环节

1. 接入流程怎么设计

步骤要点
① 建订单先在自己库里创建订单（状态 = 待支付），生成一个自己的订单号。不要等支付成功才建单——否则回调来了你都不知道对应哪笔业务
② 调下单接口带着订单号、金额、回调地址去调支付渠道的"统一下单"接口，拿到支付凭证（微信叫 prepay_id）
③ 前端唤起后端把支付参数签名后返回给前端，前端唤起微信/支付宝完成支付
④ 等回调用户付完，渠道会异步回调你配置的地址，告诉你"这笔订单支付成功了"
⑤ 发货确认支付成功后，才发虚拟商品 / 加积分 / 改订单状态
为什么要有"自己的订单号"

两个作用：一是幂等的依据（回调里带着它，你能定位到唯一一笔订单）；二是对账的依据（每天拿它和渠道流水比对）。

另外要保存渠道返回的交易号，两个号都要存——排查问题时经常需要拿渠道号去渠道后台查。

2. 回调验签：怎么确认这是真的微信发的

PY-22。回调地址是公网可访问的，任何人只要知道地址就能往里发请求，伪造一条"支付成功"。所以必须验签。

① 拿到原始报文
回调请求里带着业务数据（订单号、金额、交易号）和签名。要用原始报文体验签，不能先反序列化再拼回去——顺序和格式一变签名就不对了。
→
② 用密钥算签名
按渠道规定的算法（通常是 SHA256 / HMAC）和你自己的商户密钥，对原始报文重新算一次签名。
→
③ 比对
把算出来的签名和回调里带的对一下。不一致就直接拒绝，不要往下走。
→
④ 再查一次订单
验签通过还不够。还要反向调渠道接口确认这笔订单真的支付成功了、金额也对得上——双重确认。
验签之外还要校验什么
  • 金额：回调里的金额和你订单里的金额必须一致（防止"1 元订单回调成 100 元"这类篡改）。
  • 订单状态：如果这单已经是"已支付"，说明是重复回调，直接返回成功、不要重复发货。
  • 商户号：确认这笔回调是发给你的，不是发给别人的。

3. 保证到账：不能只靠回调

这是 PY-19，也是这一页最重要的一节。

很多人以为"回调来了就加积分"就够了。不行——回调有三个不可靠的地方：

风险会发生什么对策
回调会丢 你的服务正好在重启、网络抖动、回调地址临时不可用 → 渠道重试几次后放弃 主动查询补偿：定时任务去渠道查"待支付订单"的真实状态
回调会重复 渠道没收到你的响应（虽然你处理了），会再发一次 → 积分加两次 幂等：订单状态机 + 唯一索引，已处理过的直接返回成功
回调会乱序 支付成功和退款回调几乎同时到 → 状态被覆盖 状态机校验：只允许合法流转（待支付 → 已支付），非法流转直接忽略
正确的设计（三层）

第一层 · 实时：回调验签 + 幂等 + 状态机，把绝大多数情况处理掉。

第二层 · 补偿：定时任务主动去渠道查所有超过 N 分钟还在"待支付"的订单，发现渠道那边其实已支付，就补上。这是解决"回调丢了"的关键。

第三层 · 对账：每天拉渠道的对账单，跟本地订单逐笔比对。多出来的（渠道有、本地没有）、少了的（本地有、渠道没有）、金额不一致的，全部进人工处理队列。

一句话：永远不要假设"回调一定会到"。

发货为什么要异步

呼应 PY-20：回调处理里通常只做"更新订单状态"这一件事，然后发一条消息到队列，由消费者去发货。

原因说明
回调必须快速响应渠道对回调的响应时间有要求（超时会重发）。发货可能慢（要调别的接口、要跑任务），不能卡在这里
发货失败要能重试放在队列里可以自动重试；放在回调里就只能返回失败让渠道重发，粒度太粗
解耦支付只负责"记下这笔钱到了"，发货是另一件事

对账具体在对什么

补偿任务解决的是"几分钟内"的问题，对账解决的是"隔了一天之后"的问题——它不追求实时，追求的是最终一笔都不能错。渠道侧通常 T+1 出对账单，所以流程是每天凌晨拉前一天的账单。

对账层次比什么能发现什么
总额本地当天成功收款总额 vs 渠道账单总额最粗的一层。对不上说明有系统性问题，但对上了不代表没问题——见下面的 warn。
笔数两边的成功交易笔数能发现单边多、单边少。比总额敏感一点，但同样会被"一多一少"抵消掉。
逐笔以订单号为键，一笔一笔比对状态和金额这才是真正有效的对账。任何差异都能定位到具体订单，也才有可能自动补单。
为什么不能只对总额

因为差异会互相抵消：渠道多了一笔 100 元（你没记），同时少了一笔 100 元（你记了），总额一减正好为零。账平了，但两笔都是错的。所以对账必须以订单号为键逐笔做。

逐笔比对的结果只有三类，处理方式各不相同：

差异说明怎么处理
渠道有、本地没有用户付了钱，回调丢了、补偿任务也没捞到自动补单——这是"钱收了货没发"的最后一道兜底。补完必须记日志，方便事后核查。
本地有、渠道没有你记了一笔成功，但渠道那边没有这笔交易不能自动改。先冻结这笔订单、进人工队列排查——有可能是本地状态被错误更新了。
金额不一致订单号对得上，但两边金额不同同样不自动处理，直接进人工。这类差异往往是代码 bug 或数据被改过，自动"修正"会把问题掩盖掉。
两个容易被追问的细节

跨天的交易算哪一天？要答得出以渠道账单的日期为准：渠道按它自己记账的时点把交易归到某一天，你的本地订单时间可能落在前一天 23:59，也可能落在后一天 00:01。所以要用"渠道账单里的日期"去捞本地订单，而不是按本地订单的创建时间——否则每个跨天的单子都会被误报成差异。

退款怎么办？退款在账单里是负数流水，通常在单独一段或单独一个文件里。比对时必须一起算进去，否则当天有退款的账永远对不平。

4. 讲解骨架（看懂之后再背）

这一段就是答案：按顺序把这几件事讲一遍，讲不下去的地方回上面正文补。再往下的「回忆卡」是自测（先合上材料讲，再展开对照），「动手清单」是怎么落到自己项目里。文中的 X XX X% 不是没写完，是留给你填自己项目数字的槽位——换成真实数字，这段才立得住。

「如何保证用户支付后积分/虚拟商品一定到账」

【结论】核心认知是：永远不要假设回调一定会到。回调会丢、会重复、也可能被伪造，所以要三层保障。

【实时层】回调进来先验签（用原始报文 + 商户密钥重新算签名比对），再校验金额和商户号，然后反向调渠道接口二次确认这笔订单真的成功了。确认后更新订单状态，并通过队列异步发货。

【幂等】订单走状态机，只允许"待支付 → 已支付"这种合法流转；重复回调直接返回成功、不重复发货。

【补偿层】定时任务扫描超过 N 分钟还是"待支付"的订单，主动去渠道查真实状态，该补的补上——这是解决"回调丢了"的关键。

【对账】每天拉渠道对账单和本地订单逐笔比对，不一致的进人工处理队列。

【数字】加了主动查询之后，"已支付但未到账"的工单从每周 X 单降到基本为零。

为什么要保存"自己的订单号"和"渠道交易号"两个？
  • 自己的订单号：业务侧的唯一标识，用来做幂等、对账、排查。回调里带着它，你能定位到唯一一笔业务。
  • 渠道交易号：渠道侧的标识。当用户投诉或者你要去渠道后台查这笔单时，用的是这个号。

只存一个都会在某个环节卡住——比如想找渠道客服查单，你只有一个自己的订单号，对方查不到。

回调验签为什么必须用"原始报文"？

因为签名是对原始字节算的。如果你先把 JSON 反序列化成对象、再重新拼成字符串去验签，可能会：

  • 字段顺序变了
  • 空格、换行、转义字符变了
  • 数字精度变了（大整数被转成浮点）

任何一个变化都会让签名对不上，导致真实回调被误判为伪造。所以框架层要在反序列化之前先拿到原始 body。

动手清单 · 这些知识怎么在你项目里落地

支付接口个人不太好申请，可以用沙箱环境或者模拟一个支付渠道来练这几件事：

  1. 写一个验签函数：自己造一个"渠道"，用 HMAC 对报文签名；你的回调接口负责验签。故意改一个字节，确认验签失败。
  2. 做一次重复回调测试：同一笔订单的回调连发 3 次，确认订单状态只变了 1 次、积分只加了 1 次。这一条能跑通，讲的时候就是"我做过"。
  3. 模拟回调丢失：把回调接口临时关掉，然后跑你的补偿任务，看它能不能主动查出"其实已支付"并补上积分。
  4. 画一张状态机：待支付 / 已支付 / 已发货 / 已退款，标出哪些流转是合法的。以后所有状态变更都先校验。
  5. 做一次对账脚本：把"渠道流水"和"本地订单"两份数据比对，输出三类差异（只在一方存在的、金额不一致的）。
回忆卡 · 合上材料，用自己的话讲一遍

为什么"收到回调就发货"是错的？正确的做法分哪三层？

讲完了，展开对照

因为回调不可靠：它会丢（你的服务重启、网络抖动，渠道重试几次就放弃了）、会重复（你没及时响应，它再发一次）、还可能被伪造（回调地址是公网可访问的）。

三层保障：

  1. 实时层：验签 + 校验金额 + 反向查渠道二次确认 + 幂等（状态机）。
  2. 补偿层：定时任务主动去渠道查"长时间待支付"的订单，发现已支付就补上——解决回调丢失的关键。
  3. 对账层：每天和渠道流水逐笔比对，差异进人工处理。

一句话：永远不要假设回调一定会到。
