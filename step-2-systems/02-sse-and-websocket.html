02 · SSE 与 WebSocket

0. 先看一个场景

你在用 AI 对话，它的回答一个字一个字地出现，你能看到它"正在想"。但如果你等它全部生成完再一次性显示，体验会差很多——总时长一样，但感觉慢了好几倍。

问题来了：服务器要"持续不断地往外吐字"，浏览器要"持续不断地接"。普通的 HTTP 请求做不到这件事——它是"一问一答，答完就结束"。

所以需要一种能"保持连接、持续传输"的技术。主流有两种：SSE 和 WebSocket。

主图 · 两者最本质的区别

SSE 是单向的，WebSocket 是双向的

这张图在说什么：SSE 只有服务器能往浏览器推，浏览器不能主动发。WebSocket 握手之后是双向的，两边随时都能发。

这个区别直接决定了选型：只是"服务器持续吐字给用户看"，用 SSE 就够；如果用户还要频繁主动发消息（比如协作编辑、游戏），才用 WebSocket。

颜色含义： 浏览器 / 用户侧 服务器侧 工具 / 处理 产出 / 存储 数据 / 静态 风险 / 限制

1. 三种方案对比（FN-6、HQ-19、YF-20）

除了这两个，还有一种最土的办法：轮询（每隔几秒问一次"好了吗"）。三种放一起看：

SSEWebSocket轮询
方向 单向：只有服务器能推 双向：两边都能随时发 单向（靠客户端反复问）
底层 普通 HTTP 长连接 独立协议，需要握手升级 普通 HTTP
数据格式 纯文本（text/event-stream） 文本或二进制 普通响应
自动重连 浏览器自带，不用自己写 要自己实现 不需要
实现成本 低，服务端就是持续写响应 高一些，要管握手、心跳、事件协议 最低，但效果最差
代理 / 网关兼容 基本无痛（就是 HTTP） 有些网关 / 负载均衡要专门配置 无痛
适合 AI 流式输出、任务进度推送、日志实时展示 聊天室、协作编辑、游戏、需要高频双向交互 兜底方案；对实时性要求极低时
一句话选型

只是"服务器持续推数据给前端看" → 用 SSE；需要"频繁双向交互" → 用 WebSocket。

AI 对话场景里绝大多数是前者，所以主流做法是用 SSE——它更简单、天然兼容 HTTP 基础设施、浏览器还自带重连。

2. SSE 的实现细节

SSE 的数据格式非常简单，就是一行一行的纯文本，每条消息以两个换行结束：

data: {"text": "员工"}
data: {"text": "餐厅"}

data: {"text": "不提供"}
data: {"text": "外带打包"}

data: [DONE]

每一行以 data: 开头，浏览器拿到之后触发 onmessage，前端把 text 拼起来实时渲染。这就是"一个字一个字蹦出来"的全部原理。

要点说明
响应头必须带 Content-Type: text/event-stream，并且关闭缓冲（否则会被攒起来一次性发，就不"流"了）
前端接收用 EventSource，监听 onmessage；也可以用 fetch + 读 ReadableStream（后者更灵活，比如要带自定义请求头）
结束标记约定一个 [DONE] 之类的标记，前端收到就知道结束了
常见坑Nginx 默认会缓冲响应，必须显式关掉（X-Accel-Buffering: no）；否则现象就是"卡住很久然后一次性全出来"

3. WebSocket 的前端流程（SH-10、SH-11、SH-12）

前端接 WebSocket 的四步（对应 SH-10 ~ SH-12）：

建立连接
用 new WebSocket(url) 发起，走一次 HTTP 握手升级协议。要监听 onopen（成功）、onerror（出错）、onclose（断开）三个事件。
→
监听消息
用 onmessage 收消息。约定用 JSON：{ type, data, id }——type 区分事件类型，data 是内容。
→
分发处理
按 type 分发到不同处理函数（比如 token 追加到回答、progress 更新进度条、error 提示用户）。
→
心跳与重连
定时发心跳包保活；断开后按退避策略重连。这两件事 WebSocket 都要自己写，SSE 不用。
"和后端约定事件"具体约什么

这是 SH-12 想问的。实际要约定这几样：

  • 消息类型枚举：token（流式片段）、progress（进度）、done（结束）、error（错误）、ping/pong（心跳）
  • 每种类型的字段结构：比如 token 要带 seq（序号，用于断线续传去重）
  • 结束与错误语义：怎么表示"正常结束"、怎么带错误码
  • 版本号：协议变了怎么兼容旧客户端

4. 怎么选：三个问题

① 客户端需要频繁主动发消息给服务器吗？

需要用 WebSocket（协作编辑、聊天室、游戏）
不需要看下一个问题

② 需要传二进制数据（文件、音视频）吗？

需要用 WebSocket（SSE 只支持文本）
不需要看下一个问题

③ 是"服务器持续推数据给前端展示"这类场景吗？（AI 流式输出、进度、日志）

是用 SSE：更简单、天然兼容 HTTP、浏览器自带重连

补充一句实话：很多团队选 WebSocket 是因为"听起来更高级"，实际上 AI 对话场景用 SSE 更省事——少写重连、少踩网关配置的坑。

5. 讲解骨架（看懂之后再背）

这一段就是答案：按顺序把这几件事讲一遍，讲不下去的地方回上面正文补。再往下的「回忆卡」是自测（先合上材料讲，再展开对照），「动手清单」是怎么落到自己项目里。

「SSE 和 WebSocket 有什么区别，分别用在什么场景」

【结论】最本质的区别是方向：SSE 是服务器单向推送，WebSocket 握手之后是双向的。

【SSE】底层就是普通 HTTP 长连接，服务端持续往响应里写文本流，格式是简单的 data: 行。它的好处是浏览器自带断线重连、天然兼容各种网关、实现成本低。缺点是只能服务器推，而且只能传文本。

【WebSocket】需要一次 HTTP 握手升级成独立协议，之后两边都能随时发消息，支持二进制。灵活但心跳、重连、事件协议都要自己实现，部分网关还要专门配置。

【怎么选】只是"服务器推数据给前端看"（AI 流式输出、任务进度、日志）→ 用 SSE；需要频繁双向交互或传二进制（协作编辑、聊天室）→ 用 WebSocket。

【我们的选择】我们 AI 对话用的是 SSE。因为需求就是单向推 token，SSE 少写一堆重连逻辑，而且通过 Nginx 只要关掉缓冲就能跑。唯一要注意的是代理的缓冲问题——一开始没关，现象是"卡很久然后一次性全出来"。

SSE 断线了怎么办？

浏览器自带的 EventSource 会自动重连——这是 SSE 相对 WebSocket 的一大优势，你什么代码都不用写。它会带上 Last-Event-ID 请求头，服务端如果支持，可以据此把断线期间漏掉的消息补上。

但要注意：自动重连只是"重新连上"，不等于"接着上次继续"。要做到"接着上次继续"，需要服务端支持断点续传（见下一篇）。

如果用 fetch + 流式读取而不是 EventSource（因为要带自定义请求头），那就得自己实现重连和退避。

为什么前端有时用 fetch 而不用 EventSource？

因为 EventSource 有几个限制：

  • 不能自定义请求头——没法带 Authorization，只能靠 Cookie 或把 token 放 URL 里（不安全）。
  • 只能发 GET 请求——没法 POST 一大段消息体。
  • 不能主动中断后的自定义处理不够灵活。

所以很多项目用 fetch 拿到 ReadableStream 自己逐块解析 SSE 格式——协议还是那个协议，只是换了个读取方式。

SSE 支持多少并发连接？会不会把服务器拖垮？

每个 SSE 连接占用一个长连接，不像普通请求那样用完就释放。所以要注意：

  • 连接数上限：浏览器对同域名 HTTP/1.1 连接数有限制（通常 6 个），开多个标签页会互相挤占；HTTP/2 下多路复用能缓解。
  • 服务端资源：每个连接占一个线程/协程，要用异步框架（Node.js、Go、Python async）才撑得住。
  • 必须设超时：否则断开的连接会一直挂着占资源。
动手清单 · 这些知识怎么在你项目里落地
  1. 用 SSE 把流式输出接起来：后端持续写 data: 行，前端用 EventSource 或 fetch + 流式读取逐块渲染。跑通"一个字一个字蹦出来"的效果。
  2. 故意踩一次缓冲的坑：先不关 Nginx 缓冲跑一遍，观察"卡住很久然后一次性全出来"的现象，再关掉对比。这个体验差异你要能讲出来。
  3. 量一下首字延迟：记录"从发请求到第一个字出现"的时间。这个数字讲的时候很有用（"我们的首字延迟是 X 毫秒"）。
  4. 试试 WebSocket 版本（可选）：用同一套业务逻辑再实现一个 WebSocket 版，对比代码量——你会直观感受到"重连、心跳都要自己写"有多麻烦。这个对比能答出很真实的选型理由。
  5. 录一段口述：讲清"为什么我们选 SSE 不选 WebSocket"，带上实现成本和踩坑经历。
