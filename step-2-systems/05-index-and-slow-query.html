05 · 索引与慢查询

AI 应用最后都会落到数据库上：知识库元数据、会话记录、任务状态、用量统计。数据一多就慢，慢了就要查索引。 这一页是 D 域的地基，也是后端问得最实的一块。

0. 先看一个场景

你的知识库有 200 万条切片记录。上线三个月后，用户反馈"搜东西越来越慢"。

查了一下：一条按 doc_id 查切片的语句，从 3 毫秒变成了 3 秒。

你的第一反应可能是"加机器"。但真正的原因通常是：查询没走索引，数据库在逐行扫描 200 万条记录。加索引之后，同一条语句回到 3 毫秒——没有加任何硬件。

主图 · 最常被问的那道题

联合索引的「最左匹配」：只能从最左边连续用起

这张图在说什么：联合索引像一本先按 a 排序、a 相同再按 b、再按 c 的电话簿。你要查"所有 b=2 的人"，就相当于在一本按姓氏排的电话簿里找"所有名字叫小明的人"——没法用排序，只能一页页翻。

这就是 YF-17 那道题的完整答案：必须从最左列开始、且连续，中间断了后面的就用不上。

颜色含义： 索引键 能用上 用不上 全表扫描

1. 索引为什么快：三条要知道的原理（YF-17）

概念一句话解释
B+ 树 索引是一棵排好序的多叉树。查一个值不用逐行找，从根往下走几层就定位到了——100 万行大约只要 3~4 次磁盘读取。这也是为什么索引列能做范围查询（> BETWEEN）。
回表 索引里通常只存了索引列 + 主键。如果查询要的字段不在索引里，还得拿着主键回主表再查一次——这叫回表。回表是慢查询的常见原因。
覆盖索引 如果查询要的字段全都在索引里，就不用回表了。
例：索引 (doc_id, chunk_id) 能满足 SELECT chunk_id WHERE doc_id=?——不用回表，快很多。
能加分的说法

"我们有个列表接口很慢，查下来是回表太多。后来把常用的几个字段加进联合索引做成覆盖索引，直接在索引里就取到了，延迟从 X 毫秒降到 Y 毫秒。"

能说出"回表"和"覆盖索引"，比只说"加索引"高一个档次。

2. 索引失效的常见情况

加索引不等于用得上。下面是实际会踩的坑：

写法为什么失效怎么改
WHERE name LIKE '%张%' 前面带通配符，没法用排序定位起点 改成 LIKE '张%'（前缀匹配可以用索引）；真要做全文模糊搜索，用 ES
WHERE YEAR(created_at) = 2026 对索引列做了函数运算，索引值跟表达式对不上 改成 created_at >= '2026-01-01' AND created_at < '2027-01-01'
WHERE status = 1（status 只有 0/1） 区分度太低。优化器一算：反正是要扫一半的表，不如直接全表扫 这种列单独加索引没意义，要和别的列组成联合索引
WHERE phone = 13800000000（phone 是字符串） 类型不匹配，数据库要做隐式转换 传对类型：phone = '13800000000'

3. 慢查询怎么排查：一套固定动作（HQ-12）

对方爱问"你平时做过哪些 SQL 优化"（HQ-12）——他要的不是你背了哪些优化点，而是你有没有一套排查流程。

① 先找到慢的是哪条 SQL

慢查询日志打开慢查询日志，设一个阈值（比如 1 秒），它会自动记录所有超过阈值的语句
监控面板云数据库一般自带"慢 SQL 排行"，直接看 Top 10

② 用 EXPLAIN 看它到底怎么执行的

type = ALL全表扫描，大概率没用上索引
type = ref / range / const用上索引了，看下一步
rows 很大预估要扫的行数太多，说明索引选择性差
Extra 里有 filesort排序没走索引，额外做了一次文件排序

③ 对症下药

没走索引改查询写法（见上一节），或者加/调整索引
回表太多做覆盖索引，把要查的字段加进索引
数据量太大加缓存、归档历史数据、或者考虑分表
一个常被忽略的前提

在动手加索引之前，先问一句："这条查询真的需要每次都查数据库吗？"

很多"慢查询"其实是不该查——热点数据加一层缓存，或者把结果缓存几秒，比优化 SQL 见效快得多。能说出这一层，说明你不是只会加索引。

4. 大表的问题：百万级之后慢插入（TK-10）

这是 TK-10。数据过了百万之后，不只是查询慢，写入也会慢。原因和优化：

现象原因优化
插入越来越慢 每插一条都要更新所有索引；索引越多越慢 批量插入（一条语句插多行）；去掉用不上的索引
批量导入特别慢 每批都在等磁盘刷盘 导入期间临时关掉自动提交、导入完再重建索引
表越来越大，查询也慢 单表几千万行之后，索引层数变多、缓存命中率下降 归档：把历史数据挪到另一张表 / 另一套库；实在不行再分表
删除历史数据也很慢 大事务 + 大量索引更新 分批删（每次几千行），别一条 DELETE 删几百万
顺序很重要

优化的优先级是：改查询 → 加索引 → 加缓存 → 归档 → 分表。

分表是最后手段——它带来跨表查询、分布式事务、扩容等一堆新问题。上来就说"分库分表"是新手最容易犯的错。

5. 实战题：MySQL IO 爆红怎么排查（TK-9）

这是 TK-9，题目给了一个很具体的场景：

题目场景

三张表关联查询，每小时同步一次，从一个库查、往另一个库插，插入时报错，同时 MySQL 的 IO 爆高。

这种题的正确答法是先问清楚、再给排查路径，而不是直接猜答案：

① 先确认：IO 是"读爆"还是"写爆"？

看监控读 IOPS 高 → 大概率在扫表；写 IOPS 高 → 在写大量数据或刷日志

② 如果是读爆：为什么在扫表？

查询没走索引三表关联最容易出现：关联字段没索引 → 每行都去扫一遍被关联的表（嵌套循环的放大效应）
没有增量条件"每小时同步一次"如果每次都全量查，数据涨了 IO 自然涨 → 应该按更新时间增量拉
一次拉太多一次性查出几十万行 → 应该分页 / 分批

③ 如果是写爆：为什么写这么多？

逐条插入几十万条一条条插 → 改成批量插入
大事务一个事务里插几十万行，回滚日志和锁都撑不住 → 拆成小批次提交
索引太多目标表索引多，每条插入都要更新所有索引 → 同步期间可以先禁用非唯一索引，导完再建

④ 插入报错怎么定位？

唯一键冲突重复同步导致主键/唯一索引冲突 → 改成 INSERT ... ON DUPLICATE KEY UPDATE（幂等写入）
字段超长 / 类型不符源库和目标库表结构不一致 → 对比 schema
锁等待超时目标表被别的事务占着 → 看 SHOW PROCESSLIST 找阻塞源
这题的加分点

"我会先确认是读爆还是写爆，这决定了排查方向完全不同。然后从最可能的一条开始验证——三表关联没索引是最常见的，因为嵌套循环会把开销放大好几倍。"

先分类、再定向验证——这个思路比背一堆可能原因有用得多。

6. 剩下几道零散的题（YF-15、HQ-10、HQ-11、HQ-13）

题答案要点
MySQL 5.6 和 8.0 有什么区别（YF-15） 8.0 的主要变化：默认字符集改成 utf8mb4（5.6 默认 latin1 / 5.7 是 utf8，存 emoji 会出问题）；窗口函数和 CTE（复杂统计不用写一堆子查询了）；JSON 字段支持更好；去掉了查询缓存（因为命中率低还容易成为瓶颈）；索引支持降序索引和隐藏索引。
抓 ORM 生成的 SQL（HQ-10） ORM 把 SQL 藏起来了，慢查询排查第一步是把它打印出来：开 ORM 的 SQL 日志开关；用数据库的慢查询日志反查（更快，因为不依赖应用日志）；或者用 APM 工具看调用链。
经典坑：ORM 的"懒加载"会生成 N+1 查询——循环里每条记录都单独查一次关联表。要用预加载一次性查出来。
PostgreSQL 物化视图（HQ-11） 物化视图 = 把查询结果真的存成一张表，而不是每次实时算。适合"统计口径复杂、但不需要实时"的场景（报表、看板）。
代价是要手动刷新（或定时刷新），数据有延迟。和普通视图的区别：普通视图只是存了 SQL，每次查都重新执行；物化视图存的是结果，查得快但要刷新。
分库分表 / 读写分离（HQ-13） 被问到就说清什么时候才需要：单表过了几千万行、并且归档和索引都优化过了，才考虑分表。读写分离则是读多写少时把读流量分到从库，但要接受主从延迟（刚写的数据可能读不到），所以"写完立刻读"的场景要走主库。

7. 讲解骨架（看懂之后再背）

这一段就是答案：按顺序把这几件事讲一遍，讲不下去的地方回上面正文补。再往下的「回忆卡」是自测（先合上材料讲，再展开对照），「动手清单」是怎么落到自己项目里。文中的 X XX X% 不是没写完，是留给你填自己项目数字的槽位——换成真实数字，这段才立得住。

「日常做过哪些 MySQL 慢查询 / 索引 / SQL 优化」

【结论】我有一套固定流程：先定位是哪条 SQL，再用 EXPLAIN 看它怎么执行的，最后对症下药。不会凭感觉加索引。

【定位】开慢查询日志 + 看数据库自带的慢 SQL 排行，先拿到 Top 几的语句。

【分析】用 EXPLAIN 看三件事：type 是不是 ALL（全表扫描）、rows 预估行数、Extra 有没有 filesort。

【优化】按优先级来：先改查询写法（避免函数运算、前导通配符、类型不匹配），再考虑加索引或做覆盖索引减少回表，然后加缓存，最后才是归档和分表。

【数字】最有代表性的一次：XX 接口的查询从 3 秒降到 30 毫秒，原因是关联字段没索引导致嵌套循环放大；加索引后 EXPLAIN 的 type 从 ALL 变成 ref。

【权衡】索引不是越多越好——每个索引都会拖慢写入。所以我们定期梳理，把用不上的索引删掉。分表是最后手段，因为它会带来跨表查询和扩容的新问题。

为什么不建议用 UUID 做主键？

核心原因是插入性能：

  • 自增主键：新数据总在索引末尾，是顺序写入，页分裂少。
  • UUID：随机分布，新数据插在中间，会频繁触发页分裂和数据移动，写入变慢、索引变大。

如果业务上必须用全局唯一 ID，可以用有序的 UUID（比如时间戳前缀的 UUID v7）或者雪花算法，兼顾唯一性和有序性。

EXPLAIN 里哪个字段最重要？

type 最直观。从好到坏的常见取值：

const（主键/唯一索引等值查）> eq_ref（关联查询用主键）> ref（普通索引等值查）> range（范围查）> index（扫整个索引）> ALL（全表扫描，要警惕）。

但别只看 type：rows 大不大、Extra 有没有 Using filesort / Using temporary 同样重要。

索引是不是越多越好？

不是。索引是用写入性能换查询性能。

  • 每个索引都占空间。
  • 每次写入（增删改）都要更新所有相关索引，索引越多写越慢。
  • 索引太多，优化器选择也会变慢，甚至选错索引。

实践：优先做联合索引覆盖多个查询（注意最左匹配），定期清理从没被用到的索引。

动手清单 · 这些知识怎么在你项目里落地
  1. 给你的知识库表加索引并实测：造 100 万条切片记录，先不加索引跑一次按 doc_id 查的语句，记下耗时；加索引再跑一次，对比。这个前后数字讲的时候非常有用。
  2. 跑一次 EXPLAIN：对着上面那条查询执行 EXPLAIN，看 type 从 ALL 变成什么。截图存下来当答题卡素材。
  3. 故意写一个索引失效的查询：比如 WHERE DATE(created_at) = '2026-09-14'，看 EXPLAIN 的 type，再改成范围查询对比。
  4. 做一次批量插入对比：逐条插入 1 万行 vs 一条语句批量插入，记录耗时差异。
  5. 开一次慢查询日志：把阈值设成 0.1 秒，跑一会你的应用，看看有哪些语句被抓出来。
回忆卡 1 · 合上材料，用自己的话讲一遍

联合索引 (a, b, c) 上，下面几个查询哪些能用上索引？为什么？
a=1 / a=1 AND b=2 / b=2 / a=1 AND c=3

讲完了，展开对照
  • a=1 ✅ 用上 a
  • a=1 AND b=2 ✅ 用上 a、b
  • b=2 ❌ 完全用不上——跳过了最左列 a，索引是"先按 a 排序"的，只查 b 没法定位
  • a=1 AND c=3 ⚠️ 只能用上 a——中间的 b 断了，c 就用不上

一句话：从最左列开始，连续才能用；断了一列，后面的全失效。

回忆卡 2 · 合上材料，用自己的话讲一遍

发现一条查询很慢，你的排查步骤是什么？

讲完了，展开对照
  1. 先确认它该不该查数据库——热点数据能不能加缓存。
  2. 定位：慢查询日志 / 慢 SQL 排行，拿到具体的语句。
  3. EXPLAIN：看 type（是不是 ALL）、rows（预估行数）、Extra（有没有 filesort）。
  4. 对症：没走索引就改写法或加索引；回表多就做覆盖索引；数据量太大就归档或分表。

优化优先级：改查询 → 加索引 → 加缓存 → 归档 → 分表。分表是最后手段。
