10 · NestJS 与 ORM

这一页是按方向选读内容：只有目标公司用 NestJS + TypeORM 才需要细看（对应的题号都是 HQ 开头的）。 其他方向扫一眼概念即可。

0. 先看一个场景

你接手一个项目，120 个接口。产品说："给所有接口都加上操作日志，记录谁在什么时候调了什么、耗时多久。"

笨办法是：每个接口里都复制一段记日志的代码——120 个地方，漏一个就少一个，以后改格式要改 120 遍。

NestJS 的答案是：用拦截器在一处统一处理。而拦截器只是它请求管线里的一站——这一页的主图就是这条管线。

主图 · NestJS 的请求管线

一个请求要经过七站，每一站都能做一类统一的事

这张图在说什么：这条管线的价值是"横切关注点"只写一次。日志、鉴权、参数校验、异常处理，这些每个接口都要做的事，各自有专门的站点负责，业务代码里就不用重复写了。

记住每站的原话：中间件管日志鉴权，守卫管权限，拦截器管切面，管道管参数，控制器管业务，异常过滤器管兜底。

颜色含义： 基础 校验 / 权限 切面 业务 异常兜底

1. 怎么给上百个接口统一加日志

这就是 HQ-7。答题的关键是说出"用框架的切面机制，而不是挨个改"。

做法说明适合什么
全局拦截器
首选		 注册一个全局拦截器，用 next.handle() 前后包住请求，在 tap 里记录耗时、用户、入参、结果 绝大多数场景。一处代码覆盖所有接口
中间件 更早执行，也拿得到 req/res 日志要记录"还没进业务就失败"的请求
装饰器 + 拦截器 写一个 @Log('操作名') 装饰器，配合拦截器读取元数据 需要区分业务语义时（"这是'删除用户'操作，不是'查询'"）
答题时的加分点
  • 说清"在哪一层"：用拦截器而不是管道或控制器——因为拦截器能同时拿到入参和返回值，还能算耗时。
  • 说清怎么区分操作类型：光有 URL 不够（POST /users 是"创建"还是"登录"？），所以配一个装饰器标注操作名。
  • 说清"日志写哪里"：同步写数据库会拖慢接口，通常先写日志队列异步落库（呼应 07）。
  • 说清"别记敏感信息"：密码、token、身份证号要脱敏，否则日志本身就是泄露源。

2. 管道（Pipe）是什么

HQ-8。一句话：管道是"进入业务逻辑之前的守门员"，负责转换和校验参数。

① 请求到达
URL 参数、查询参数、请求体的原始值被解析出来。这时它们都还是字符串或未校验的对象。
→
② 管道处理
转换（"123" → 123，字符串转成数字/日期/枚举）+ 校验（必填、长度、格式）。
→
③ 交给控制器
控制器拿到的已经是干净的、类型正确的数据，业务代码里不用再写一堆 if (!xxx) throw。
内置管道作用
ValidationPipe最常用。配合 DTO 类 + 装饰器（@IsString() @IsInt()）自动校验，不通过直接返回 400
ParseIntPipe把路径参数转成整数，转不了就报错
ParseUUIDPipe校验是不是合法的 UUID
DefaultValuePipe给缺省的参数补默认值
为什么用管道而不是在控制器里 if 判断

因为校验规则能跟 DTO 定义绑在一起，一处定义、全局生效，而且错误格式统一。

对比一下：不用管道的话，每个接口开头都有一堆 if (typeof body.age !== 'number') throw new BadRequestException(...)——重复、容易漏、错误格式还不一致。

3. 依赖注入：Provider 是单例还是每次新建

HQ-5 问的这个问题很具体，答案是：默认是单例（整个应用启动时创建一次，所有请求共用）。

作用域什么时候创建什么时候用
单例（默认）应用启动时创建一次，全局共用绝大多数场景：Service、工具类、数据库连接池
请求级每个请求创建一个新实例实例里存了"当前请求"相关的状态（比如当前登录用户）
瞬态每次注入都创建新的很少用，比如需要互相隔离的工具实例
这里有个陷阱，说出来很加分

单例 Service 里不能存请求相关的状态。

比如你在 Service 里写 this.currentUser = user，那 A 用户请求刚设置完，B 用户的请求就把它覆盖了——这就是经典的并发串数据 bug，而且很难复现。

正确做法：需要请求上下文时，把它当参数传进去，或者用框架的请求上下文机制，而不是存在 Service 的成员变量上。

单例模式的优点（HQ-6）

优点说明
省资源不用每个请求都 new 一个对象。对连接池、HTTP 客户端、缓存这类重量级对象尤其重要
状态可共享需要全局共享的状态（比如内存缓存的配置）天然只有一份
可控的初始化时机应用启动时就建好，能提早发现配置错误

代价：单例之间如果有可变状态，就会有并发问题；也不好做隔离测试。所以单例最适合"无状态的服务"——这也是为什么 Service 层应该写成无状态的。

4. TypeORM 和 Prisma 怎么选

HQ-2 / HQ-3。两者都是 Node 生态里常用的数据库工具，但设计理念完全不同：

TypeORMPrisma
核心理念 面向对象：用类和装饰器定义实体，实体之间可以有关系 Schema 驱动：先写一份 schema 文件，用命令生成类型安全的客户端
类型安全 一般，容易出现类型和实际表结构不一致 很强，生成的客户端查询方法都有类型提示
上手成本 要理解实体、关系、仓库、查询构造器等一套概念 学一个 schema 语法 + 客户端 API 就行，上手更快
复杂查询 更灵活，QueryBuilder 能拼出很复杂的 SQL 复杂查询有时要写原生 SQL，灵活性弱一些
和 NestJS 的配合 官方一等公民，@nestjs/typeorm 集成得很顺 需要额外封装，没有官方集成那么自然
适合 已经在用 NestJS、关系复杂、需要大量自定义查询 追求类型安全和开发体验、表结构相对规整的新项目
被问"调研过优缺点吗"怎么答

"我们选 TypeORM 主要是因为项目已经在用 NestJS，官方集成最顺，而且我们的查询比较复杂（多表关联 + 聚合），QueryBuilder 更灵活。

Prisma 的类型安全确实更好，写起来也更舒服，如果重做新项目我会认真考虑它。当时没选它的顾虑是：复杂查询要退回原生 SQL，而且它对 NestJS 的依赖注入体系没有官方支持，要多写一层封装。"

关键是要说出"我们基于什么约束做的选择"，而不是哪个更好。

5. TypeORM 的两种运行模式

HQ-9。其实问的是"你的实体和表结构怎么保持同步"：

模式怎么工作适合
实体模式
Entity / 装饰器		 表结构由实体类 + 装饰器定义（@Entity @Column），代码即 schema 开发阶段、快速迭代。用迁移（migration）把变更同步到数据库
Schema 同步模式 开启 synchronize，启动时自动对比实体和表结构，自动改表 只用于本地开发——生产环境开这个等于让框架随便改你的表结构，非常危险
这题真正想验证的

对方问这个，是想确认你知不知道 synchronize 不能上生产。

正确的做法是用迁移文件：每次改表结构生成一个迁移脚本，经过评审后在部署时按顺序执行。这样表变更是可追溯、可回滚的——synchronize: true 在开发环境爽，在生产环境是事故源头（它可能直接删列）。

6. 讲解骨架（看懂之后再背）

「怎么给几十上百个接口统一加操作日志」

【结论】用框架的切面机制在一处统一处理，而不是每个接口里复制一段——那样漏一个就少一个，改格式还要改上百遍。

【做法】注册一个全局拦截器，它在控制器前后各执行一次，能同时拿到入参、返回值和耗时。为了区分业务语义（POST /users 到底是"创建"还是"登录"），再配一个装饰器标注操作名，拦截器读取这个元数据。

【写入】日志不直接同步写库（会拖慢接口），而是丢进队列异步落库。

【安全】记录前对密码、token、身份证号做脱敏——日志本身也可能是泄露源。

【权衡】拦截器覆盖所有接口很方便，但也意味着所有请求都会多一层开销。所以我们对高频的健康检查接口做了排除。

NestJS 的模块、控制器、服务是什么关系？
  • 模块（Module）：组织单元，把相关的控制器和服务打包在一起，并声明"我要用别人的什么、我允许别人用什么"。
  • 控制器（Controller）：负责接口层——定义路由、解析参数、返回响应，不写业务逻辑。
  • 服务（Service）：负责业务逻辑，通过依赖注入被控制器使用。

这个划分对应 09 讲的"应用层 / 领域层"——Controller 是应用层，Service 是领域层。

ORM 的 N+1 查询问题是什么？

用 ORM 的"懒加载"时很容易踩到：查 10 条订单，然后循环里每条订单再去查它的用户——本来 1 次查询能搞定，结果发了 11 次（1 次查订单 + 10 次查用户）。

为什么慢：每次查询都有网络往返开销，10 次就是 10 倍的延迟。

怎么解决：用预加载（relations 或 join）一次性把关联数据查出来。这也是排查 ORM 慢查询时第一个要看的地方（呼应 05 的 HQ-10）。

为什么 Service 应该写成无状态的？

因为 Provider 默认是单例——所有请求共用同一个实例。如果 Service 里存了"当前请求"的状态：

  • A 请求设置了 this.user = alice，还没执行完；
  • B 请求进来设置了 this.user = bob；
  • A 请求后面读到的是 bob → 串数据了。

这种 bug 偶发、难复现、后果可能很严重（比如 A 用户看到了 B 用户的数据）。所以需要请求上下文时，当参数传进去，不要存在成员变量上。

动手清单 · 这些知识怎么在你项目里落地
  1. 搭一个最小 NestJS demo：一个控制器 + 一个服务 + 一个模块，跑起来。不用做复杂功能，先把"模块/控制器/服务"的关系敲实。
  2. 写一个全局拦截器记日志：记录 URL、方法、耗时、用户。跑几个请求看输出。
  3. 加一个 ValidationPipe + DTO：给一个接口加参数校验，故意传错参数，看返回的错误格式。
  4. 写一个全局异常过滤器：让所有错误都返回统一格式（{ code, message }），而不是框架默认的一大坨。
  5. 验证单例陷阱：在 Service 里存一个成员变量，并发发两个请求，看会不会串。亲手复现一次，这个知识点就再也忘不掉了。
  6. 用迁移改一次表结构：体会一下 synchronize: true 和写迁移文件的区别。
回忆卡 1 · 合上材料，用自己的话讲一遍

NestJS 的请求管线有哪几站？每站负责什么？

讲完了，展开对照

中间件（日志、鉴权）→ 守卫（权限判断）→ 拦截器·前置（切面逻辑）→ 管道（参数转换与校验）→ 控制器（业务处理）→ 拦截器·后置 → 响应。

任何一站抛出的异常，都由异常过滤器统一转成规范错误响应。

这条管线的价值是：日志、鉴权、校验、异常处理这些"每个接口都要做"的事，各自只写一次。

回忆卡 2 · 合上材料，用自己的话讲一遍

Provider 默认是单例还是每请求新建？这带来什么好处和陷阱？

讲完了，展开对照

默认是单例——应用启动时创建一次，所有请求共用。

好处：省资源（连接池、HTTP 客户端这类重量级对象不用反复创建）、状态可共享、初始化时机可控。

陷阱：单例 Service 里不能存请求相关的状态。存了就会串数据——A 用户设置完还没执行完，B 用户就把它覆盖了。这种 bug 偶发难查，所以 Service 应该写成无状态的，需要请求上下文时当参数传进去。
