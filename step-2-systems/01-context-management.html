01 · 上下文治理

Agent 跑到十几轮之后开始犯糊涂，你以为是模型不行——其实是上下文脏了。 这一页讲怎么管住它。这是 C 域最重要的一份，也是做项目时必须动手实现的第一块。

JR-11JR-12JR-14
读之前

这一页要用「上下文」「上下文窗口」「token」这些概念。看着眼生的话，先看 00 · 先认识这几个词 的第一组。

第一遍（5 分钟）只看主图和加粗句。
第二遍（15 分钟）读五种手段，对照自己的项目想"我该上哪几种"。
第三遍做末尾的动手清单。

0. 先看一个场景

你的 Agent 跑了 15 轮，开始犯一些很蠢的错误：反复改一个已经改对的地方、把早就否掉的方案又提出来、明明文件里写着答案却说"找不到"。

你换了个更强的模型——没用，还是这样。

真实原因：上下文里已经堆满了它自己的历史。前 14 轮的工具返回、失败的尝试、被推翻的结论，全都在。它每轮都要读一遍这些，然后被自己带偏。

这一页的论点（也是讲解的落点）

"AI 一直修不好一个 bug，不一定是它没有这个能力，而是它的上下文已经被彻底带偏了。"

最直接的验证方法：开一个新对话，把关键信息重新说一遍，它两分钟就解决了。

主图 · 上下文是怎么被撑爆的

轮次越多，"当前任务"占比越小

蓝色部分是"这一轮真正需要看的信息"：

第 1 轮 —— 上下文很干净

当前任务占 36%，模型看得见重点。

第 8 轮 —— 前面几轮的工具返回开始堆积

被稀释到 12%，开始被无关内容干扰。

第 20 轮 —— 当前任务几乎被淹没

只剩 4%。失败的尝试、已经作废的结论全都还在，模型被自己的历史绑架。

这张图在说什么：上下文不是"越多越好"。每多塞一段无关内容，真正有用的信息就被稀释一分。

颜色含义： 当前任务 / 模型 历史堆积 危险区

1. 五种治理手段，按优先级排

核心原则：最好的压缩是不需要压缩。一开始就别让脏东西进主上下文，比事后补救有效得多。

优先级手段怎么做适合什么
① 最优先 隔离 脏活（装环境、下载数据、跑测试、批量搜索）交给子 Agent，只把结论回传主线程 凡是过程又长又乱、结论很短的任务
② 外部化 大结果写到文件或数据库，上下文里只留路径和摘要，需要时按需读取 工具返回大 JSON、长文档、日志
③ 摘要 把早期对话滚动总结成一段话（"之前确认了 X，尝试过 Y 失败，原因是 Z"） 长对话。注意关键约束不能只靠摘要
④ 裁剪 工具结果只保留需要的字段/行区间；读文件只读相关部分 所有工具调用，应该做成默认行为
⑤ 最后手段 截断 只保留最近 N 轮 快速止血。容易把早期的关键约束一起扔掉
讲的时候按这个顺序讲

"优先级是隔离 > 外部化 > 摘要 > 截断。理由很简单：最好的压缩是不需要压缩——一开始就别让脏东西进主上下文。等到塞满了再摘要，信息已经损失过一轮；而截断最粗暴，容易把关键前提一起扔掉。"

2. 追问：压缩质量不行怎么办

这是个很尖锐的追问（JR-12），因为它直指一个事实：摘要质量本身就受模型能力限制——用小模型做摘要，关键信息会丢。

专业且诚实的答法

"压缩质量确实受模型能力限制，所以我们的做法是不把压缩当成唯一依赖：

  • 关键信息结构化保存——约束条件、已达成的结论、失败的教训，这些放在独立的结构化字段里（不靠模型摘要），每轮都随上下文带上。
  • 原始内容落盘——被压缩掉的内容不销毁，需要时可以回溯查证。
  • 压缩用更强的模型，并且压缩结果做一次校验（比如让它回答几个关键问题，看信息有没有丢）。
  • 但最根本的还是前面那条：与其压缩，不如一开始就别让脏东西进主上下文。"
这里的"结构化保存"很容易被追问

对方可能接着问："具体存什么？" 准备好一个具体答案，比如：

维护一个固定结构的任务状态对象：目标、已确认的事实、已排除的方案及原因、待解决问题。每轮都把这个对象重新拼进上下文，而不是指望模型从漫长的历史里自己想起来。

3. claude code 是怎么做的

先明确对方想听什么

问这个（JR-14）不是让你背源码。答"我逐行读过源码"却讲不出设计取舍，反而扣分。他要听的是：你理解它为什么这么设计。

它围绕上下文做的四条设计取舍——这些原则不依赖具体实现，自己写一个 agent loop 也能验证：

原则做法为什么
检索优于全量 不把整个代码库塞进上下文，先搜索定位，只带相关片段 装不下整个仓库；全塞进去噪声大、还贵
工具结果要裁剪 读文件只读需要的行区间，命令输出做截断 避免"读了一个 5000 行文件"直接占满上下文
子任务隔离 搜索、探索类工作交给子 Agent，只回传结论 探索过程又长又乱，不该污染主线
提示词可缓存 稳定的系统提示和工具定义放最前面并缓存 降本提速，也减少上下文抖动
这题的落点

"它的所有设计最终都指向同一件事——管住每一个 session 的上下文。因为决定 Agent 表现的往往不是模型上限，而是上下文质量。所以它宁可多调几次工具去精确定位，也不愿意把大块内容直接塞进上下文。"

4. 讲解骨架（看懂之后再背）

「你们上下文压缩的策略是什么」（含追问）

【结论】我们的核心原则是"最好的压缩是不需要压缩"——优先从源头上不让脏东西进上下文。

【做法】四层：① 隔离：装环境、下数据、跑测试这些脏活交给子 Agent，主线只拿结论；② 外部化：工具返回的大结果落盘，上下文里只留路径和摘要；③ 摘要：长对话滚动总结，但关键约束（目标、已确认的结论、失败的教训）用结构化对象保存，不依赖模型摘要；④ 截断：作为最后手段，只保留最近 N 轮。

【数字】改造之后单次任务的 token 消耗下降约 X%，任务成功率提升 X%。

【追问应对】压缩质量确实受模型能力限制。所以关键信息不靠摘要、原始内容可回溯、压缩用更强的模型并做校验。但根本解法还是前面那条——把需要压缩的量降下来。

怎么知道上下文"脏了"？有没有可观测的信号？

几个可以监控的信号：

  • 上下文长度曲线：随着轮次增长而任务没有收敛，就是危险信号。
  • 重复行为：连续几轮调用同样的工具、同样的参数。
  • 结论反复：把之前已经否掉的方案又提出来。
  • "找不到"变多：明明信息在上下文里，它却说不存在。

实践中最有效的一招是把每一轮的完整上下文存下来，出问题时离线重放——你能直接看到它当时"眼里"是什么。

多轮对话场景，上下文怎么组织？

常见的结构（从稳定到易变）：

  1. 系统提示 + 工具定义（最稳定，放最前面，方便命中提示词缓存）
  2. 结构化任务状态（目标、已确认事实、已排除方案、待解决问题）
  3. 历史对话摘要（滚动更新）
  4. 最近几轮原文（保留细节）
  5. 本轮检索到的资料 + 用户当前问题（放最后，注意力最集中）

关键点：顺序就是优先级。稳定的放前面（省缓存），最相关的放最后（注意力高），历史摘要在中间。

动手清单 · 这些知识怎么在你项目里落地

这一块是步骤 2 的核心，光看不算完成。给自己排一个下午，把下面几件事做出来：

  1. 加一个"任务状态对象"：定义固定结构（目标 / 已确认事实 / 已排除方案 / 待解决问题），每轮重新拼进上下文。这是投入产出比最高的一件事。
  2. 给工具返回值加裁剪：挑一个返回内容最多的工具，改成"只返回需要的字段 + 摘要"。对比改造前后同一任务的 token 消耗。
  3. 做一次隔离实验：把某个又长又乱的子任务（比如批量检索）拆成子 Agent，只回传结论。看主线程的上下文长度变化。
  4. 把每轮的完整上下文存下来：出问题时能离线重放。这是调试 Agent 最快的手段。
  5. 录一段口述：用五段式讲一遍"我怎么管上下文的"，必须带上第 2 步测出来的 token 变化数字。
回忆卡 · 合上材料，用自己的话讲一遍

五种上下文治理手段分别是什么？为什么"隔离"排第一、"截断"排最后？

讲完了，展开对照

五种：隔离（脏活丢子 Agent，只回传结论）→ 外部化（大结果落盘，只留路径和摘要）→ 摘要（滚动压缩）→ 裁剪（工具结果只留需要的部分）→ 截断（只保留最近 N 轮）。

顺序的理由：最好的压缩是不需要压缩。隔离和外部化是在源头控制，让脏东西压根不进来；摘要是事后补救，信息已经损失过一轮；截断最粗暴，容易把早期的关键约束一起扔掉。
