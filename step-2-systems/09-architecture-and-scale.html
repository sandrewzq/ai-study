09 · 架构分层与高并发

前面几页讲的都是"某个点怎么做对"，这一页讲整体怎么搭：代码分几层、什么时候该拆微服务、 以及系统扛不住时用什么手段保命。

HJ-8HJ-10PY-9KJ-10
读之前

这一页偏"设计题"，没有标准答案。重点不是背出某个架构，而是能说清每个选择解决什么问题、代价是什么。

第一遍（5 分钟）看主图，记住分层的顺序。
第二遍（12 分钟）读"稳定性四件套"那一节。
第三遍做末尾的动手清单——把你的项目画成一张架构图。

0. 先看一个场景

对方问："你们这个系统的后端分几层？"（HJ-8）

很多人会答"三层：Controller、Service、DAO"。这不算错，但太笼统——对方想听的是每一层为什么这么分、不这么分会出什么问题。

主图 · 典型的后端分层

每一层只干一件事，出错时才好定位

这张图在说什么：分层的价值是把变化隔离开——换数据库只动数据层，改业务规则只动领域层，加限流只动接入层。

反过来，如果 Service 层里直接写 SQL、Controller 里写业务判断，那就变成"三层只是三个文件夹"，分层等于没分。

颜色含义： 客户端 接入 应用 / 编排 领域 / 业务 数据 / 存储

1. 每层该干什么、不该干什么

层该干不该干（常见错误）
接入层 鉴权、限流、路由、协议转换（HTTP → 内部调用） 写业务判断；直接查数据库
应用层 编排一次业务用例的步骤、决定事务边界、组装返回数据 写核心业务规则（那是领域层的事）；拼 SQL
领域层 业务规则、状态流转校验、领域计算 关心 HTTP 状态码、依赖具体的数据库表结构
数据层 封装对数据库/缓存/队列的访问 写业务判断（"如果状态是 X 就不能改"这种规则应该在上层）

判断分层分得好不好，有个简单标准：能不能在不改业务代码的前提下换掉数据库？能，说明隔离做到了；不能，说明 SQL 泄漏到了上层。

2. 微服务：什么时候该拆

PY-9 问"有没有做过微服务、数据中台"。这题最容易踩的坑是把微服务说得越好越显得专业——恰恰相反，能说清"我们为什么没拆"反而更可信。

该拆的信号不该拆的情况
不同模块的扩容需求差别很大（AI 推理要 GPU，管理后台几乎不用） 团队只有几个人，还没到需要独立部署的规模
不同模块的发布节奏差别很大，互相拖累 模块之间调用极其频繁，拆了就是无数跨网络调用
需要故障隔离（一个模块挂了不能拖垮全部） 还没搞清业务边界就拆——边界错了，拆完还要合回去
团队规模大到沟通成本超过协作收益 没有配套的监控、日志、链路追踪——拆完没法排查问题
讲解落点

"我们没有一上来就拆微服务。因为团队只有 X 个人，业务边界也还在变。先做模块化——代码上按领域分模块、约定不互相越界访问，等某一块的扩容或发布真的成为瓶颈了，再把它抽出来独立部署。

微服务解决的是组织和扩容问题，不是代码质量问题。没有这些问题的团队拆了，只会多出一堆分布式事务和排查困难。"

3. 稳定性四件套：限流、熔断、缓存、队列

HJ-10 问的就是这个。四个手段解决的是不同的问题，别混在一起说：

手段解决什么问题怎么做代价
缓存 热点数据反复查库，浪费资源 Redis 缓存查询结果；本地缓存放变化更少的数据 要处理一致性（见 06）
限流 流量突增把系统打垮 网关按用户/IP/全局限流；超出直接返回"稍后再试" 可能误伤正常用户，要配白名单
熔断 下游挂了，把上游也拖死（雪崩） 统计下游失败率，超过阈值就"熔断"——一段时间内直接不调用，快速失败；过一会再试探恢复 熔断期间功能降级，要设计降级后的表现
队列 瞬时高峰 vs 处理能力不匹配 请求入队，消费者按自己的能力匀速处理（削峰） 有延迟；队列本身要保证不丢（见 07）
限流和熔断的区别（最容易被问）

限流是"我扛不住，别来了"——保护自己，主动拒绝多余流量。

熔断是"下游坏了，我别等了"——保护自己不被下游拖死，快速失败而不是傻等超时。

一句话：限流管入口，熔断管出口。

举个真实的连锁反应：模型 API 变慢 → 你的请求线程全被占住等着 → 线程池耗尽 → 连"查看历史记录"这种不依赖模型的接口也响应不了 → 整个应用不可用。熔断就是为了在第一步就切断这个链条：发现模型接口失败率过高，直接返回"服务繁忙"，把线程留给其他功能。

4. 追问：express 的底层原理

KJ-10 问"express 的底层原理，如果让你设计实现怎么做"。这题考的是你能不能把一个框架拆解成最小模型。

express 的本质是一个中间件数组 + 一个"下一个"函数：

① 请求进来
创建 req 和 res 两个对象。express 把它们包装得比原生更顺手（比如 res.json()）。
→
② 依次执行中间件
框架内部维护一个函数数组。每个中间件收到 (req, res, next)，处理完调用 next() 就交给下一个。
→
③ 路由匹配
把 URL 路径和注册的路由做匹配（express 用 path-to-regexp 把 /user/:id 转成正则）。匹配上了才执行对应的处理函数。
→
④ 结束响应
某个中间件调用了 res.send() / res.json()，响应就结束了，后面的中间件不再执行。
"如果让你设计"怎么答

说清三个核心机制就够了：

  • 中间件数组 + next 推进：这是整个框架的骨架。本质是责任链模式。
  • 洋葱模型：中间件可以在 next() 之前和之后都做事，形成"进去一圈、出来一圈"的效果（所以请求日志能算出总耗时）。
  • 错误处理靠参数个数区分：(err, req, res, next) 四个参数的中间件就是错误处理器——这是 express 里很巧妙的一个设计。

再加一句局限：它是回调式的，异步错误捕获不友好（async 函数里抛错不会自动进错误中间件，要手动 try/catch 或包一层）。这也是 Koa / NestJS 出现的原因之一。

5. 讲解骨架（看懂之后再背）

「传统业务系统的后端分几层」

【结论】我们分四层：接入层、应用层、领域层、数据层。分层的目的是把变化隔离——换数据库只动数据层，改业务规则只动领域层。

【各层职责】接入层做鉴权、限流、路由，不碰业务；应用层负责编排一次业务用例的步骤、决定事务边界；领域层放业务规则和状态流转；数据层封装对数据库/缓存的访问。

【怎么判断分得好】一个简单标准：能不能不改业务代码就换掉数据库。能，说明隔离做到了。

【权衡】分层也有成本——多一层就多一层转换代码。所以小项目不必严格四层，但"业务规则不能写在数据访问层"这条底线要守住，否则以后换存储就要重写业务。

什么是"数据中台"？我们需不需要？

数据中台是把各业务线的数据统一采集、清洗、建模、对外提供的一套能力，解决"每个业务各自建一套数据、口径不一致"的问题。

什么时候需要：业务线多、数据源杂、有多个团队都在做重复的数据加工。

什么时候不需要：只有一两个业务、数据量不大——这时候硬做中台就是为了架构而架构，投入大、见效慢。务实地说："我们数据量还没到那个规模，所以先用数仓 + 定时任务满足报表需求。"

接口变慢了，怎么判断是哪里慢？

靠链路追踪：给每个请求生成一个 traceId，贯穿所有调用，记录每一段的耗时。这样一眼就能看出是数据库慢、还是模型调用慢、还是网络慢。

没有链路追踪的话，退而求其次：在代码里打点记录关键步骤的耗时（比如"检索 200ms、精排 150ms、模型 1200ms"），先定位到段，再深入那一层排查。

动手清单 · 这些知识怎么在你项目里落地
  1. 把你的项目画成一张架构图：照主图那四层，标出你的每个模块属于哪一层。这张图讲的时候可以直接画给对方看。
  2. 找出一次"分层被破坏"的地方：比如有没有在接口处理函数里直接写 SQL、或者把业务判断写在数据访问层。改掉它。
  3. 给模型调用加超时和熔断：模型接口是最不稳定的一环。设置超时时间，连续失败 N 次就熔断一段时间，返回降级话术。这是 AI 应用最该做的一件事。
  4. 给关键接口加限流：比如每分钟每用户最多 10 次问答，超了返回"请求过于频繁"。
  5. 量三个数字：单个问答请求里，检索、精排、模型生成各占多少毫秒。这三个数字能答掉一大堆"你怎么优化性能"的问题。
