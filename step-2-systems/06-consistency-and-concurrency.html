06 · 数据一致性与并发

"两个人同时买最后一件库存会怎样"——这个问题背后是并发下的数据一致性。 它是 D 域最能区分水平的一块：只会背 ACID 的人答不出超卖怎么防，做过的人能画出时序图。

这一页假设你知道数据库的"事务"是什么（一组要么全成功、要么全失败的操作）。不知道的话先看第 1 节。

第一遍（5 分钟）只看主图，理解超卖是怎么发生的。

0. 先看一个场景

秒杀活动：100 件商品。活动结束后一统计，卖出去 137 件。

代码逻辑看起来完全正确：

1. 查库存：SELECT stock FROM goods WHERE id = 1;   -- 假设查到 1
2. 判断：if (stock > 0) { ... }                    -- 1 > 0，通过
3. 扣减：UPDATE goods SET stock = stock - 1 WHERE id = 1;

单个人执行这套逻辑没问题。问题是很多人同时在执行。

主图 · 超卖是怎么发生的

两个请求都读到了"库存 1"

这张图在说什么：问题出在"读"和"写"之间有空隙。两个请求都在这个空隙里读到了同一个值，然后各自认为自己可以扣。

这类问题的通用名字叫"竞态条件"。解决思路只有一条：让"读—判断—写"这三步不能被别的请求插进来，或者让判断和扣减合并成一步原子操作。

颜色含义： 冲突点 正常步骤 索引 / 计算 正确结果

1. 事务：先把概念说清

HQ-23 问"什么是数据库事务"，答案是 ACID 四个特性。但只背四个字母没用，要能说出它解决什么问题。

特性什么意思不满足会怎样
A 原子性 事务里的操作要么全成功、要么全失败 转账扣了钱但没加钱，钱凭空消失
C 一致性 事务前后，数据的约束关系不被破坏 转账后总金额对不上
I 隔离性 并发事务之间互不干扰，像串行执行一样 两个人同时买最后一件 → 超卖
D 持久性 提交后的数据不会因为宕机丢失 用户付了钱，重启后订单没了

怎么判断一个场景"必须用事务"（HQ-24）——看两个条件，同时满足就该用：

判断标准
  1. 一次业务操作要写多张表（或同一张表的多行），且这些写入要么都成功、要么都别生效。
  2. 中间失败会导致数据对不上（钱少了、库存扣了但订单没生成）。

例子：下单 = 扣库存 + 建订单 + 减余额。这三步必须在一个事务里，任何一步失败都要回滚。
反例：只是往日志表插一条记录，失败了也无所谓——不需要事务。

2. 并发扣减的四种解法

这是 D 域的核心。按从简单到复杂排，回答时说清各自的代价：

方案怎么做优点代价
① 悲观锁 SELECT ... FOR UPDATE 把这一行锁住，别人得等 实现简单，绝对安全 并发差：所有请求排队，秒杀场景直接被打爆；容易死锁
② 乐观锁
推荐		 不加锁，把判断写进更新语句：
UPDATE goods SET stock=stock-1 WHERE id=1 AND stock>0；
看影响行数是不是 1，是 0 就说明没抢到		 不用加锁，靠数据库的行锁保证原子性，并发好得多 失败要重试或直接告诉用户"已售罄"；高冲突时重试多
③ Redis + Lua 库存预热到 Redis，用 Lua 脚本做"判断 + 扣减"（Redis 单线程执行，天然原子）；扣成功再异步落库 性能最高，能扛住秒杀流量 多了一套组件；要处理 Redis 和数据库的一致性问题（见第 4 节）
④ 队列串行化 请求先入队，消费者单线程逐个处理扣减 彻底没有并发冲突，逻辑最简单 有延迟；队列本身要保证不丢（见下一篇）
讲的时候怎么选（这段话很加分）

"日常的低并发场景用乐观锁就够了——把条件写进 UPDATE 语句，不用加锁，简单又安全。

秒杀这种瞬时高并发才需要Redis 预扣减 + Lua，因为数据库扛不住那么大的写入量。但引入 Redis 之后就多了一致性问题，要用消息队列把扣减结果异步同步到数据库，并做对账兜底。

核心判断依据是并发量级，不是哪个方案更高级。"

3. 秒杀系统怎么设计

PY-12 是道大题，按漏斗的思路答——每一层都挡掉大部分流量：

这张图在说什么：每一层都只让一小部分流量通过，所以真正打到数据库的请求从"几十万"变成"一百"。注意框的宽度只是表达"逐层收窄"这个趋势，不是精确比例。

答题时按这个顺序说，条理自然就出来了：前端挡掉脚本 → 网关限掉超量 → 缓存做库存判断 → 队列削峰 → 数据库只兜底。少任何一层，压力都会往后传。

颜色含义： 入口流量 逐层拦截 最终落库
环节关键点
限流按用户维度限（一个用户只能抢一次）、按 IP 限、全局限。超出的直接返回"已抢完"，不要让它进到后面
削峰把瞬时的高并发变成队列里的平缓消费。这也是 PY-20 问的"支付为什么用异步队列"的同一个思路
库存判断前置先在 Redis 里判断和扣减（原子），通过了才继续。避免大量无效请求打到数据库
超卖防护Redis 扣减用 Lua 保证原子；数据库扣减用乐观锁（WHERE stock >= 1）作为最后一道防线
幂等同一个用户重复提交要只算一次——用唯一索引或分布式锁（见 PY-15）
对账兜底活动结束后核对 Redis 和数据库的库存，不一致要能修

Redis 分布式锁（PY-15）

要点说明
加锁SET lock_key 唯一值 NX PX 30000——NX 保证只有一个人能设成功，PX 设过期时间防止死锁
为什么要"唯一值"解锁时要确认"这把锁是我加的"。否则可能删掉别人的锁（比如自己超时了，锁被下一个人拿到，你才回来删）
解锁要用 Lua"判断是不是自己的锁 + 删除"两步必须原子，否则中间可能被别人插进来
为什么不用 Lua 做扣减锁的粒度大（锁整个操作），Lua 脚本能把"判断 + 扣减"做成一个原子操作，性能更好。能用 Lua 就不用锁

4. 缓存和数据库的一致性

YC-1。核心问题是：数据改了，缓存怎么办？

策略怎么做问题
先更新库，再删缓存
推荐		 改数据库 → 删掉缓存（下次读时自然回源重建） 理论上仍有极短的窗口不一致（并发读正好在删之前），但概率极低
先删缓存，再更新库 先让缓存失效，再改库 更容易出问题：删完缓存、还没改完库，另一个请求读进来把旧值又写回缓存了
更新库 + 更新缓存 两边都写 两次写入之间会被读到中间态；如果缓存值需要复杂计算，还浪费算力
延迟双删 删缓存 → 改库 → 隔一小段时间再删一次 能覆盖上面那个窗口，但引入"延迟"这个不确定因素
讲解落点

"我们用的是先更新数据库、再删缓存。因为删除比更新安全——就算删失败了，最坏也就是下次读回源，不会留下错数据。

而且要接受一个前提：缓存和数据库的强一致是做不到的，除非加分布式锁（代价太大）。所以工程上的目标是最终一致，再配合过期时间兜底——就算某次没删成功，缓存也会在 TTL 到期后自动失效。"

5. 追问：不用 Redis，只用 MySQL 怎么保证安全

PY-17。这题考的是你能不能在最简单的条件下降级解决问题，而不是只会堆组件。

手段说明
乐观锁扣减 UPDATE ... SET stock = stock - 1 WHERE id = ? AND stock >= 1，靠数据库的行锁保证原子性。这是最核心的一招
唯一索引幂等 订单表对 (user_id, activity_id) 建唯一索引，一个人重复提交直接报冲突，天然去重
事务包裹 扣库存 + 建订单放一个事务，失败一起回滚
限制入口流量 网关层限流，让数据库的并发在它扛得住的范围内
接受性能上限 诚实地说：纯 MySQL 方案能保证正确性，但扛不住太高的并发。如果业务量真的很大，就必须引入缓存或队列
这题真正考什么

不是"没有 Redis 我会不会做"，而是"你能不能在受限条件下说清边界"。

好的回答会包括："用乐观锁 + 唯一索引可以保证不出错，但在几千 QPS 以上数据库会先成为瓶颈。所以这个方案适合中小流量；如果是秒杀量级，还是得上缓存层。"——既给了方案，也说了方案的上限。

6. 讲解骨架（看懂之后再背）

「高并发下怎么避免超卖」

【结论】超卖的本质是"读—判断—写"之间有空隙，两个请求都读到了同一个值。所以思路是让判断和扣减变成一步原子操作。

【方案】按并发量级选：日常场景用乐观锁——把条件写进 UPDATE 语句（WHERE stock >= 1），看影响行数判断是否成功，不用加锁；秒杀量级用 Redis + Lua 预扣减，因为数据库扛不住那么大的写入。

【兜底】数据库层的乐观锁始终保留，作为最后一道防线；订单表加唯一索引做幂等，防止同一用户重复下单；活动结束后对账。

【数字】改造前压测时 100 件会卖出 137 件；改成乐观锁后压测 5000 QPS 无超卖；引入 Redis 后单机 QPS 从 X 提到 Y。

【权衡】乐观锁在高冲突场景下失败率高，要么重试要么直接提示售罄；Redis 方案性能好但多了一套组件，还要处理缓存和数据库的一致性，所以我们用队列异步落库并对账兜底。

乐观锁和悲观锁到底怎么选？

看冲突概率：

  • 冲突少（读多写少、不同用户操作不同数据）→ 乐观锁。加锁本身有开销，冲突少的时候锁纯属浪费。
  • 冲突多（同一个热点数据被频繁改）→ 乐观锁会不停失败重试，反而更慢，这时悲观锁或队列串行更合适。

一句话：乐观锁假设"一般不会冲突"，悲观锁假设"一定会冲突"。

Redis 和数据库的数据不一致，业务上怎么兜底？
  • 过期时间：缓存设 TTL，就算某次没删成功，到点也会失效。
  • 延迟双删：写库前后各删一次，覆盖并发窗口。
  • 消息队列：把"删缓存"做成一个消息，失败可以重试。
  • 定时对账：定时比对关键数据（比如库存），发现不一致就修正并告警。

核心认知：不要追求强一致，要追求"不一致能被发现并修复"。

什么是死锁？怎么避免？

两个事务各自锁了一部分资源，又在等对方释放，谁也不让——就卡死了。

避免手段：

  • 固定加锁顺序：所有事务都按同样的顺序访问资源（比如都按主键升序），最有效。
  • 缩短事务：事务里别做网络调用、别处理大批数据。
  • 降低锁粒度：能用行锁就别用表锁。
  • 设超时：万一还是死锁，让数据库自动检测并回滚其中一个，应用层捕获后重试。
动手清单 · 这些知识怎么在你项目里落地
  1. 写一个会超卖的脚本：拿一张测试表，开 100 个并发去扣同一行库存，用"先查再改"的写法跑一遍，确认真的超卖。（这是理解这个问题最快的方式）
  2. 改成乐观锁再跑一遍：把判断写进 UPDATE 语句，同样的并发下确认不超卖。记录两次的结果差异。
  3. 给你的项目加唯一索引幂等：比如任务表对 (task_type, biz_id) 建唯一索引，防止重复提交创建两个任务。这在 AI 应用里非常常用——用户连点两次就重复调用模型了。
  4. 用 Redis + Lua 实现一次库存扣减：把"判断 + 扣减"写成一个 Lua 脚本，理解为什么它天然原子。
  5. 给你的缓存加上 TTL 和删除时机：确认"先更新库、再删缓存"的顺序，并统计一下缓存命中率。

超卖是怎么发生的？四种解法分别是什么，代价是什么？

讲完了，展开对照

原因：两个请求都读到了"库存 1"，各自的判断都通过，于是同一件库存卖了两次。问题出在"读"和"写"之间的空隙。

四种解法：① 悲观锁（FOR UPDATE，安全但并发差）；② 乐观锁（把 stock >= 1 写进 UPDATE，不用加锁，推荐）；③ Redis + Lua（性能最高，但要处理一致性）；④ 队列串行化（彻底无并发，但有延迟）。

选择依据是并发量级，不是哪个更高级。

回忆卡 2 · 合上材料，用自己的话讲一遍

缓存和数据库怎么保持一致？为什么是"先更新库、再删缓存"而不是反过来？

讲完了，展开对照

顺序是"先更新数据库，再删缓存"。

为什么不能反过来：如果先删缓存再改库，在"删完、还没改完"的空隙里，另一个请求读进来发现缓存没了，就去数据库读到旧值，然后把它写回了缓存——缓存里就留下了一个错误的旧值。

更关键的前提：缓存和数据库的强一致做不到，工程目标是最终一致。所以还要配 TTL 兜底、对账修正。
