04 · 断线续传与任务状态

上一篇解决"断了能重连"，这一页解决"重连之后能接着看"——用户刷新页面、关了窗口再打开， 之前的回答不能白丢。这是流式功能里最容易被忽略、也最能体现工程水平的一块。

YC-10HQ-18HQ-20HQ-21HQ-22
读之前

这一页默认你读过 02 和 03。这一页是它们的落点：把"连接"和"业务状态"解耦。

第一遍（5 分钟）看主图，理解"用序号对账"这件事。
第二遍（15 分钟）读四节正文。
第三遍做末尾的动手清单。

0. 先看一个场景

用户问了个问题，AI 正在一个字一个字地回答，刚出来三分之一——用户不小心刷新了页面。

  • 初级做法：页面一刷新，内容全没了，用户得重新问一遍。（很常见）
  • 好一点：前端把已收到的部分存在本地，刷新后先显示出来，但后面的内容接不上了。
  • 正确做法：生成这件事在服务端继续跑，前端刷新后连回来，从断掉的地方接着收。

区别在于一个认知：生成任务是服务端的事，前端只是一个"显示器"。显示器拔了，片子还在放。

主图 · 断线续传靠什么对账

给每条消息编号，重连时报"我收到第几条了"

这张图在说什么：断线续传的本质是用序号对账。前端记住收到哪了，重连时报给服务端，服务端把后面的补上。

要做到这一点，服务端必须把已经生成的内容暂存起来（或者重新执行一遍并快速跳过已发部分）。这就是"任务状态"要独立于连接存在的原因。

颜色含义： 已收到 未收到 / 待补发 断点

1. 断线续传怎么实现

要点做法
任务与连接解耦 生成任务由 task_id 标识，存在服务端（内存或 Redis）。连接断了任务照跑，连接只是"订阅"这个任务的输出
给消息编号 每条输出带一个递增的 seq
重连时上报位置 用 SSE 的话可以直接用浏览器自带的 Last-Event-ID 请求头；用 WebSocket 就在重连握手里带上 { taskId, lastSeq }
服务端补发 如果任务还在跑 → 把 seq > lastSeq 的已生成内容补发，然后继续推；如果任务已经结束 → 一次性把完整结果返回
保留多久 生成结果要存一段时间（比如 30 分钟），否则用户隔太久回来就补不了了。这是个要主动说的取舍
一句话本质

"把'连接'和'任务'解耦：连接是可以断的，任务是不断的。"

想清楚这一点，续传、进度查询、多端同步这些需求就都有统一的解法了——前端不管连不连得上，都能通过 task_id 查到任务状态和已有结果。

2. 前端怎么感知后端任务状态

这是 HQ-18。长任务（视频解析、批量向量化）随时可能中断、终止、完成，前端要知道现在处于什么状态。三种方案：

方案怎么做适合
轮询状态接口 前端定时调 GET /task/{id}，返回 status + progress 最简单、最稳，对实时性要求不高的任务
长连接推送 通过 SSE / WebSocket 主动推状态变更事件 实时性要求高，且已经有长连接通道
混合
推荐		 长连接推状态；页面加载时先查一次接口拿当前状态（因为长连接只能收到"之后"的变化） 生产环境的标准做法

状态要设计成明确的状态机，别用一堆布尔值：

这张图在说什么：只有"成功"是一个终态之外的正常出口——失败和取消都是从"进行中"岔出去的旁路。设计状态机时重点就在这两个旁路：失败要能重试，取消要能清理资源，不能只画一条成功路径。

颜色含义： 未开始 / 已取消 进行中 成功终态 失败旁路

前端按状态渲染：pending/running 显示进度条、succeeded 显示结果、failed 显示错误和重试按钮、cancelled 显示已取消。每个状态都要有对应的界面，不能只做成功路径。

3. 边收边渲染怎么做

这是 HQ-21。后端把内容一块一块推过来，前端不能等全部收完再渲染——那就失去流式的意义了。但"边收边渲染"有几个具体的麻烦：

麻烦解法
Markdown 被切断 收到的内容可能停在 **加粗 中间。做法是容错渲染：未闭合的标记按普通文本先显示，等闭合了再变成加粗
表格渲染错乱 表格要等表头和分隔行都到了才能变成表格。在此之前先按纯文本显示
代码块没闭合 收到 ``` 但还没收到结束标记时，按"已开始的代码块"渲染
频繁重渲染卡顿 不要每个字符都触发一次全量重渲染。按帧合并更新（比如每 50ms 刷一次），或者只更新最后一个文本节点
自动滚动打断用户 用户往上翻看历史时不要强制滚到底部；只有当他本来就在底部时才自动跟随
最后一行的体验细节，讲出来很加分

"用户往上翻的时候如果还强制滚到底，他会很烦躁。我们的做法是判断当前是否在底部——在底部才自动跟随，否则显示一个'回到最新'的按钮。"

4. 协议设计：AGUI 这类方案在解决什么

先解释 AGUI：它指的是一类"用结构化事件驱动前端渲染"的协议——后端推的不是纯文本，而是带类型的事件，前端根据类型渲染成不同组件（文字、表单、卡片、按钮）。

为什么要这么做？因为纯文本只能表达"一段话"，表达不了"一个可交互的界面"。

纯文本流的问题结构化事件怎么解决
要让用户填个表，只能把字段写成文字，用户得自己复制 推一个 form 事件，前端直接渲染成可填的表单
要让用户确认一个操作，只能写"请回复是或否" 推一个 confirm 事件，前端渲染成按钮
流式渲染时格式容易乱 每个事件是独立完整的结构，天然不会出现"半个表单"

整体流程（HQ-20）：

后端识别
判断出这一步需要用户填东西，而不是继续生成文字。
→
推送带类型的事件
推一个标明类型的事件，而不是纯文本：
{ "type": "form", "id": "f1", "fields": [...] }
→
前端按类型分发
看到 form 就渲染成表单组件，而不是当文字打出来。id 用于定位和增量更新。
→
回传进入下一轮
用户填完提交，前端把数据回传，后端接着往下走。

底层 API 的设计逻辑（HQ-22），被问到时可以这么答：

设计要点为什么
事件带类型和 id类型决定渲染方式，id 用于定位和更新（同一个组件可以增量更新）
增量 + 全量两种更新文字用增量（追加），组件用全量（替换），各取所需
事件可排序、可去重带 seq，断线续传和去重都靠它
文本作为最基础的事件绝大多数场景就是文本，复杂组件是少数；不要让简单场景为复杂协议买单
可降级客户端不认识某个事件类型时，要有兜底渲染（比如显示成文本），不能白屏

5. 讲解骨架（看懂之后再背）

「SSE 断线续传你们做过吗？用户关掉窗口又打开怎么继续」

【结论】核心思路是把"连接"和"生成任务"解耦——连接可以断，任务在服务端不断。

【做法】生成任务由 task_id 标识存在服务端；每条输出带递增的 seq；前端记住最后收到的序号，重连时上报（SSE 直接用 Last-Event-ID 请求头）；服务端把 seq 之后的内容补发，然后继续推。如果任务已经结束，就一次性返回完整结果。生成结果在服务端保留一段时间（我们设的是 30 分钟）。

【前端配合】页面加载时先调一次任务状态接口拿当前状态和已有内容，再用长连接接收后续增量——因为长连接只能收到"连接之后"的变化。

【坑】我们最早把内容和连接绑在一起，用户刷新就全丢了。改成"任务独立存储 + 序号对账"之后才解决。

【权衡】保留时长是有取舍的：留太久占内存，留太短用户回来就补不上了。我们按业务场景设的 30 分钟，超时就提示"该回答已过期，请重新提问"。

任务状态和生成结果存在哪？
  • 单机 + 短任务：放进程内存里最简单，但进程重启就没了。
  • 多实例 / 要持久：放 Redis，设过期时间；重启后还能查到。
  • 要长期归档：落数据库，Redis 只做热数据的缓存。

判断依据：任务会不会跨实例、能不能接受重启丢失、要保留多久。讲的时候说出这个判断依据比直接报一个技术名词更有说服力。

多个页面同时打开同一个任务，怎么处理？

因为任务和连接已经解耦了，所以天然支持：多个连接订阅同一个 task_id，各自记录自己的 lastSeq，服务端按各自的进度补发。

要注意的是写入端只能有一个——不能让多个连接都去触发"继续生成"，否则会重复调用模型。这需要在服务端对任务加锁或做幂等控制。

动手清单 · 这些知识怎么在你项目里落地
  1. 把生成任务从连接里剥出来：给它一个 task_id，结果存到 Redis。前端只用 task_id 订阅——这一步是后面所有功能的基础。
  2. 给输出加 seq：每条消息带递增序号，前端记录最后收到的。
  3. 做一次真实的刷新测试：提问 → 回答到一半 → F5 刷新 → 看能不能接着往下收。这一条能跑通，讲的时候就是"我做过"。
  4. 加一个任务状态接口：GET /task/{id} 返回状态机 + 进度 + 已有内容，前端页面加载时先调它。
  5. 把状态机的每个状态都渲染出来：pending / running / succeeded / failed / cancelled，每个都要有对应的界面，尤其别只做成功路径。
  6. 处理"用户往上翻"的体验：判断是否在底部，只在底部时自动滚动。

断线续传靠什么实现？为什么说"要把连接和任务解耦"？

讲完了，展开对照

靠序号对账：每条输出带递增的 seq；前端记住最后收到的序号，重连时上报；服务端把之后的内容补发。

解耦的意义：连接是可以断的，任务是不断的。生成任务由 task_id 标识存在服务端，连接只是"订阅"它的输出。想清楚这一点，续传、进度查询、多端同步就都有统一解法了。

回忆卡 2 · 合上材料，用自己的话讲一遍

前端怎么感知长任务的状态？边收边渲染有哪些坑？

讲完了，展开对照

感知状态：长连接推变更 + 页面加载时先查一次接口（因为长连接只能收到"之后"的变化）。状态设计成明确的状态机（pending/running/succeeded/failed/cancelled），每个状态都要有对应的界面。

边收边渲染的坑：Markdown 被切断（容错渲染，未闭合的标记先当普通文本）、表格和代码块没闭合、每个字符都重渲染导致卡顿（按帧合并更新）、用户往上翻时被强制滚到底（判断是否在底部再决定是否跟随）。
