05 · 技术栈自评

「你对 XX 了解到什么程度」——这是整个 J 域最实用的一页。 因为它问得最频繁，而且答错的代价最直接：说高了当场翻车，说低了被低估。

YU-11YU-22YF-12YF-16YF-25YU-6
读之前

这一页需要你先在事实表里把技术栈分好三档。没分的话先回去分——这页讲的都是基于那个分级的表达方式。术语不熟先看 00 · 先认识这几个词。

第一遍（5 分钟）只看主图，把三档的判断标准记下来。
第二遍（15 分钟）读第 1、2 节——"不会怎么答"是最关键的一节。
第三遍做页尾回忆卡，把你在事实表里列的技术一个个套档。

0. 先看一个场景

对方问：「你对 Java 了解到什么程度？」

你其实没怎么用过 Java，但自己的技术清单里写着"了解后端"。这时候怎么办？

三种答法，差别很大
  • 「Java 我了解一些，基本的语法都会。」
    ——接下来对方就会问 JVM、GC、并发包。你会在第二个问题就崩。而且崩了之后，前面说过的所有话都会被重新审视。
  • 「Java 我不会。」
    ——太干，浪费了一次展示的机会。而且会让对方觉得你只会自己那一块。
  • 「Java 我没有在项目里用过，但后端这套东西我是通的——我现在的主力是 Node 那套，关系库、缓存、队列这些都实际做过。语法层面的东西换一门语言很快，难的是工程上的判断，这部分是通的。」
    ——诚实、有边界、还说明了可迁移性。

这一页要解决的就是：怎么在不吹牛的前提下，把自己的能力说清楚。

主图 · 三档，每档都有一个"能做什么"和"不能做什么"

关键是说出边界，不是说出等级

这张图在说什么：三档的关键不在名字，而在每一档都能说出"能做什么"和"不能做什么"。说出边界，对方才有判断依据；只给一个模糊的等级词，他只能靠自己猜。

底下那三句是应对"完全不会"的：先干脆承认，再说清你懂的相关部分，最后说明可迁移性。整个过程不卑不亢，而且信息量比"我不会"大得多。

颜色含义： 可以说 第二档 第三档 别说 应对不会的三步

1. 为什么"熟悉""精通"这类词不能用

因为这些词没有公认的标准。你说"熟悉 Redis"，对方不知道你说的是"会用基本命令"还是"能设计集群方案"——他只能自己去试，而试的方式通常是往深了问。

模糊的词对方会怎么理解换成什么
"精通 XX" 往最难的地方问——原理、源码、边界情况。绝大多数人说"精通"都撑不住这个标准。 说"能主导这块的方案"，然后举一个你做过的决定。
"熟悉 XX" 没有参照系，对方只能靠追问来定位你的水平。 说"能独立完成日常开发，复杂场景需要查资料"——把边界自己画出来。
"了解 XX" 从最基础的开始问，浪费时间；或者干脆跳过你。 说"知道它的原理和适用场景，但没有在项目里独立用过"——明确到这一层。
"用过 XX" 追问"用它做过什么、遇到什么问题"。这是最容易被戳破的一个。 要么说清具体项目里做了什么，要么降到"了解"那一档。
一个能通用的句式

把"我熟悉 XX"换成这个结构：

「XX 我在项目里用过（说明范围）——能独立完成 A 和 B（说能做什么）；但 C 那种情况我还没处理过，一般会查资料或者找有经验的同事确认（说不能做什么）。」

这个句式的价值在于：你把边界主动画出来了，对方就不需要靠追问来试探。而且一旦你说了"能做什么"，他更可能顺着你熟的地方问——这等于你在引导话题。

2. 「完全不会」怎么答（YF-12、YU-22）

被问到不会的东西是常态——关键是别慌，也别硬撑。用主图里那三句话：

① 先承认，而且要快
"Java 我没有在项目里用过。"——短促、明确。最忌讳的是绕：说"了解一些""学过一点"，等于邀请对方继续问，然后你在第三个问题上崩掉。
→
② 说清你懂的相关部分
"但后端这套东西我是通的——我现在主力是 Node 那套，关系库设计、缓存、队列、并发这些都在项目里实际做过。"把话题从"语言"拉回"能力"。
→
③ 说明可迁移性
"语法层面换一门语言很快——真正的难点是工程判断，比如什么时候该加缓存、事务边界怎么划，这部分是通的。"
有一个例外：别说"我学得很快"

第 ③ 句里不要出现"我学习能力强，很快就能上手"——这句话太常见，而且没法验证，说出来反而像是在找补。

正确做法是用可迁移的"具体能力"替代"学习速度"：

  • ❌ "我学得很快，给我时间就能上手。"
  • ✅ "语法层面的东西换一门语言很快；真正难的是工程上的判断——比如并发怎么写、事务边界怎么划，这部分在哪个语言里都是通的，我做过。"

后者没有承诺"我很快能学会"，而是指出"真正难的部分我已经有了"——这更有说服力。

对方追问：「那你数据库能力大概在什么水平？」（YF-16）

数据库这类技术深度是分层的，所以答的时候要指出你在哪一层，而不是给一个笼统的水平：

层次能做到什么
第一层：会写能写查询、联表、聚合。这是最基本的，说这一层等于没加分。
第二层：会设计能根据业务设计表结构、定字段类型、想清楚关系。这一层开始有价值。
第三层：会优化能看执行计划、加对索引、定位慢查询（见步骤 2 的索引与慢查询）。这一层是大多数方向真正要的。
第四层：懂原理知道存储引擎怎么组织数据、事务隔离是怎么实现的。这一层通常只有专门做数据库的人需要。

答法示范：「我在设计和优化这两层。表结构和索引设计是我自己做的；慢查询也实际排查过几次，做过一次索引优化把接口从几秒降到几十毫秒。再往下的存储引擎原理我了解大概，但没有深入研究过——那是专门做数据库的人的事。」

这个答法同时做到了三件事：定位清楚、有具体例子、主动划了上界。

对方追问：「你做 AI 相关是工作落地，还是业余学习？」（YF-25）

这题不能含糊——因为它是在核实你前面讲的项目到底是不是真的。三种情况分别答：

  • 如果是工作落地：说清在什么场景、解决了谁的什么问题、有没有真的被用起来。光说"公司要求做的"不够，要说清"做出了什么、谁在用"。
  • 如果是业余做的：不要心虚。说清做了什么、做到什么程度、为什么要做。"业余做的东西能跑起来"本身就是很强的信号——说明你是真的有兴趣，不是被推着走。
  • 如果两边都有：这是最好的答案。分开说清各做了什么，以及工作里的东西怎么反哺到自己的探索上。

无论哪种，都要落到具体的产出上："我业余也搭过一个本地知识库，跑了两万份文档，主要是想验证一下不同切分策略对召回的影响。"——这种细节编不出来。

3. 「你是怎么转型学过来的」（YU-6）

这题问的是学习方法，而不是结果。所以别只说"我现在能写后端了"，要说清你怎么从不会到会的。

说哪一段内容
① 起点 当时是什么情况——为什么需要转、你原来的基础是什么。有起点才有"跨越"的对比。
② 路径 先学了什么、后学了什么、怎么验证。关键是说清"验证方式"——这决定了你是真会还是看过。
③ 卡在哪 哪个概念最难理解、哪次踩坑最深刻。这一段最能证明你是真的走过这条路。
④ 现在到什么程度 和你的技术栈分级保持一致。别忘了说边界。
套出来的样子

【起点】「一开始是因为项目需要，前端只有我一个人，后端没人接，只能自己顶上。当时我对后端基本是空白——会发请求，但不知道怎么设计表、怎么保证数据不出问题。」

【路径】「我的顺序是先跑通再补原理。第一步是用最简单的框架把接口和数据库接起来，先让功能能用；然后才开始补基础——关系库设计、事务、缓存这几块。验证方式是强迫自己真的用：每学一块，就在项目里替换掉原来的临时方案。」

【卡在哪】「最难理解的是并发和一致性。因为前端基本是单线程思维，我一开始完全无法理解'两个人同时操作会怎样'。后来是做缓存的时候真的踩了一次——数据和缓存对不上，排查了很久才定位。那次之后我才真正建立起来这个概念。」

【现在到什么程度】「现在是能独立完成日常开发，表结构和索引设计是我做的，慢查询也排查过。但复杂的并发场景还是要查资料或者找人确认，这个我也写在自己的短板上。」

这题的加分点

"先跑通再补原理"这个顺序，本身就是一个可以讲的判断——但要说清它什么时候成立、什么时候不成立：

「我的顺序是先跑通再补原理。这么做的理由是：有了一个能跑的东西，学原理的时候才有具体的问题可以对照，不然抽象的概念记不住。

但这个顺序有前提——只能用在出错代价低的地方。如果一开始就要碰支付、碰账务这种不能出错的部分，那必须先搞懂再动手。我当时做的第一版是内部工具，所以敢先跑起来。」

最后那句"有前提"是关键——它把"我的方法"变成了"我知道这个方法什么时候适用"。

4. 讲解骨架（看懂之后再背）

「你对 XX 了解到什么程度 / 后端接触多深 / Java 会吗 / 数据库什么水平」

【统一原则】我一般不说"精通""熟悉"这类词，因为它们没有标准。我会说清"能做什么、什么还不行"，这样对方能自己判断。

【主力方向】前端和全栈这条线我是能主导方案的——选型、拆模块、定接口这些我自己能定。AI 应用的工程落地也是我做主的，从链路设计到效果调优。

【后端】后端我能独立完成日常开发——接口设计、表结构、缓存、队列这些都在项目里实际做过，慢查询也排查过几次，做过一次索引优化把接口从几秒降到几十毫秒。但复杂的并发和一致性问题还要查资料或者找人确认，这个我心里有数。

【Java 这类没用过的】Java 我没有在项目里用过。但后端这套东西我是通的——关系库设计、缓存、队列、事务这些在 Node 那套里都实际做过。语法层面换一门语言很快，真正难的是工程判断，比如什么时候该加缓存、事务边界怎么划，这部分在哪个语言里都是通的。

【数据库的分层】我会说自己在哪一层：设计和优化这两层——表结构和索引是我做的；再往下的存储引擎原理我了解大概，没深入研究过，那是专门做数据库的人的事。

【AI 是工作还是业余】两边都有。工作上是真的落地了一个内部系统，有两万多份文档，还有人在用；业余自己也搭过一个小的，主要是想验证不同切分策略对召回的影响。

【怎么转过来的】我的顺序是先跑通再补原理。前端只有我一个人、后端没人接，所以先用最简单的框架把链路接起来，再回头补关系库设计、事务、缓存。验证方式是强迫自己在项目里替换掉临时方案。最难的是并发——前端是单线程思维，我一开始完全理解不了"两个人同时操作会怎样"，直到做缓存时真踩了一次，数据和缓存对不上，排查了很久才建立起这个概念。

【权衡】"先跑通再补原理"这个顺序有前提——只能用在出错代价低的地方。如果一开始就碰支付、账务这种不能出错的部分，必须先搞懂再动手。我当时做的第一版是内部工具，所以敢先跑起来。

回忆卡 1 · 合上材料，用自己的话讲一遍

被问到一个你完全没用过的技术，说出你的三段答法。

讲完了，展开对照
  1. 干脆承认："我没有在项目里用过。"——短促明确，不要用"了解一些"来绕。
  2. 说清你懂的相关部分：举同类技术里的实际经验，把话题从"这门语言"拉回"这类能力"。
  3. 说明可迁移性：指出真正难的部分（工程判断）你已经有了，而不是承诺"我学得很快"。

最后自检一句：你有没有说出"我学习能力强"？说了就删掉——那句话没有信息量，而且会让前面两句的可信度下降。

要记住的底线：承认不会不丢分，硬撑然后被戳破才丢分。而且第二三句一说，对方往往会顺着你熟的部分继续问——相当于你把话题引导到了自己的主场。

回忆卡 2 · 合上材料，用自己的话讲一遍

为什么"熟悉 XX"和"精通 XX"这两个词不能用？换成什么？

讲完了，展开对照

因为它们没有公认的标准。

你说"熟悉 Redis"，对方无法判断你指的是"会用几个基本命令"还是"能设计集群方案"。他只能自己去试——而试的方式通常是往深了问，问到你不会为止。这时候"熟悉"这个词就成了把柄。

替换结构：能做什么 + 不能做什么。

「Redis 我在项目里用过——能独立做缓存设计和常见问题排查（能做什么）；但集群和持久化的细节我还没处理过，一般会查资料或找人确认（不能做什么）。」

这个结构有个额外好处：你把边界主动画出来之后，对方更可能顺着你说了"能"的那部分问——等于你在引导话题走向自己的主场。
