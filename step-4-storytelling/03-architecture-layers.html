03 · 架构分层与技术选型

「介绍一下你的架构」是一道开放题，没有标准答案——但有一种答法一定不扣分： 按职责分层讲，每层说清它负责什么、为什么这么切。

JR-1YC-3PY-8YC-5
读之前

这一页假设你手上有步骤 2做出来的项目，能说清它由哪些部分组成。还没做出来的话，这一页只能当模板看。术语不熟先看 00 · 先认识这几个词。

第一遍（5 分钟）只看主图，记住那五层分别负责什么。
第二遍（15 分钟）读第 2、3 节，把你自己项目的层画一遍。
第三遍做页尾回忆卡，用数据流把分层串起来讲一次。

0. 先看一个场景

对方问：「介绍一下你这个项目的架构。」

你开始说：「前端用 Vue3，后端用 NestJS，数据库 PostgreSQL，缓存 Redis，向量库用的 Milvus，部署在云主机上，前面挂了 Nginx……」

说完了。对方点点头，问：「那这些是怎么串起来的？」

——这说明你刚才报的是技术清单，不是架构。

技术清单和架构的区别

技术清单回答的是"用了什么"，架构回答的是"东西怎么组织、数据怎么流转、为什么这么切"。

同样这些组件，你可以说成清单，也可以说成架构——区别只在于你有没有讲"它们之间的关系"和"你为什么这么安排"。

主图 · 一个 AI 应用通常这么分层

每一层只回答一个问题

这张图在说什么：AI 应用的分层和普通 Web 应用大体一样，只是中间多了一层「AI 能力层」——改写、检索、精排、生成这些"智能"的部分都在这儿。

讲的时候守住两条：每层先说职责再说技术，以及说清层与层之间谁调谁。有这两条，听起来就是架构；没有，就是清单。

颜色含义： 通用层 AI 应用特有 存储与支撑 讲解要求

1. 「分成哪些层」（YC-3、JR-1）

照着上面五层讲就行，但重点要放在第 ③ 层——那是 AI 应用和普通 Web 应用真正不一样的地方，也是对方最想听的。

层职责怎么讲得不空
接入层 收请求、鉴权、限流、把结果推回去。 可以一句话带过，但流式推送要提一句——这是 AI 应用的接入层和普通网页不同的地方。
应用层 判断这次请求该走哪条链路、管会话、管权限。 讲一个具体判断：什么样的问题走简单检索，什么样的问题要进 Agent 流程。有这一句就说明你真的分过流。
AI 能力层 查询改写、检索、精排、上下文组装、模型调用、结果校验。 这一层要讲细：按顺序说清每一步做什么、哪一步最关键。大多数追问都会落在这里。
数据层 文档和切片、向量、会话记录、任务状态、用量统计。 关键是说清"为什么分开存"：文档和会话记录适合关系库；向量要用专门的库；热点会话状态放缓存（见步骤 2 的一致性与并发）。
基础支撑 异步队列、定时任务、日志、监控、告警。 重点讲哪件事是异步的——文档解析和向量化通常都放队列里跑。
这题的加分点

讲完分层，主动补一句"哪一层最重、哪一层我改得最多"：

「实际投入最多的是 AI 能力层——接入层和数据层都是标准做法，但检索这一步的每个参数都要按语料调。我们后来大部分优化都发生在这一层。」

这句话把"我知道有哪些层"变成了"我知道重心在哪"。

2. 「数据怎么流转」（YC-5）

拆模块和技术选型都能背，唯独数据流转背不出来——因为它必须是你项目里的真实路径。所以这一问是最能分辨真假的地方。

① 请求进来
接入层收下，做鉴权，拿到用户身份和会话标识，转给应用层。
→
② 应用层判断
读会话历史（从缓存里拿），判断这次要不要改写、要不要走 Agent。这一步决定后面走哪条分支。
→
③ 检索
改写后的查询同时走向量检索和关键词检索，两路结果合并去重，再送精排模型打分。
→
④ 组装与生成
取精排后的前几段，和系统提示、历史对话拼成上下文，调模型。流式返回，边生成边推给前端。
→
⑤ 落库与统计
这一轮的对话、引用的资料、消耗的用量都记下来。离线任务再拿这些数据去算命中率和成本。
讲数据流转的一个技巧

用一个具体的问题走完全程，比抽象地讲"数据从 A 到 B"好得多。

「比如用户问'报销单丢了怎么办'。这句话先被改写补全成'差旅报销单丢失后的补办流程'；然后向量检索命中了两份制度文档、关键词检索命中了另一份；三份合并后精排，前两名送进上下文；模型基于这两份生成回答，同时把文档出处一起返回，前端显示成可点的引用。」

带具体问题的数据流，和只报组件名的数据流，可信度差一个量级。

3. 「怎么拆模块、怎么选型」（YC-5）

这两问通常在数据流之后出现。拆模块有可讲的原则，选型有可讲的顺序，都不要答成"看情况"。

拆模块的原则什么意思在你项目里的例子
按变化频率拆 改得频繁的和几乎不动的分开，避免动一处波及一片。 检索策略经常调，就单独成模块；鉴权基本不动，不用拆那么细。
按职责边界拆 一个模块只干一类事，边界清晰才好测试和替换。 向量检索和关键词检索各成一块，背后可以换不同实现。
按复用度拆 多处要用的抽出来，只有一处用的先别急着抽。 模型调用被封成统一的一层，因为好几个地方都要用；但某个页面专用的逻辑没必要抽。

技术选型的顺序：先定"约束"，再定"关键选型"，最后才是外围

① 先摸约束团队会什么、规模多大、能不能上云、有没有合规要求。约束不定，选型就是空谈。
② 定关键选型AI 应用里最关键的通常是模型怎么用（直接调 API 还是私有化）和向量库选哪个。这两个定了，其他都跟着定。
③ 再定外围关系库、缓存、队列这些都有成熟方案，按团队习惯选就行，不用纠结。
④ 别颠倒顺序最怕的是先挑了个时髦的技术，再倒过来找理由。这种选型一被追问就崩。
对方追问：「为什么向量不放在关系库里？很多数据库现在也支持向量。」

这是个很实际的问题，答好了很加分。别答"因为向量库更专业"，那是同义反复。从访问模式讲：

  • 两者的查询模式不同：关系库是"按条件精确找行"，向量检索是"按相似度找最近的若干条"。后者需要专门的索引结构和计算方式。
  • 扩展方式不同：向量检索吃内存和算力，关系库吃磁盘和连接数，混在一起扩容很别扭。
  • 但要承认合并也有道理：数据量不大的时候，用同一个库确实省运维成本。我们的量级需要独立扩展，所以分开了。

最后那句"我们的量级需要……所以分开了"是关键——把通用道理落回你的实际情况，而不是当成绝对真理。

对方追问：「数据库和后端架构是什么？」（PY-8）

这题问得比"介绍一下架构"更具体，所以要落到表结构和部署形态上：

  • 有哪些主要的表：文档、切片、会话、消息、用量记录。说出主要字段和关系，比如切片表外键指向文档表。
  • 哪些数据不放关系库：向量放专门的库，热点会话状态放缓存，原始文件放对象存储。说清每一类的去向和理由。
  • 部署形态：几台机器、数据库是自建还是托管、有没有读写分离。量级不大就直说，别硬撑。
  • 一个实际的坑：比如"切片表数据涨到几百万行之后，按文档标识查变慢了，加了联合索引才好"（见步骤 2 的索引与慢查询）。

4. 讲解骨架（看懂之后再背）

「介绍一下你的架构 / 分成哪些层」

【结论】我一般按职责分成五层讲：接入、应用、AI 能力、数据、基础支撑。和普通 Web 应用比，多出来的是中间的 AI 能力层，那也是我投入最多的一层。

【接入层】页面和接口网关，负责鉴权、限流，以及把流式结果推给前端——这是 AI 应用和普通网页不太一样的地方。

【应用层】判断这次请求该走哪条链路。简单的直接走检索生成，需要多步的才进 Agent 流程；同时管会话历史和权限。

【AI 能力层】查询改写 → 混合检索（向量加关键词）→ 合并去重 → 精排 → 组装上下文 → 调模型 → 流式返回。大部分优化都发生在这一层，因为检索的参数要按语料调。

【数据层】文档和会话记录放关系库，向量放专门的向量库，热点会话状态放缓存，原始文件放对象存储。分开的理由是访问模式不同——精确查找和相似度检索是两种完全不同的查询，扩展方式也不一样。

【数据怎么流】用户提问 → 应用层读会话、判断分支 → 改写后两路检索 → 合并精排 → 取前几段拼进上下文 → 模型流式生成 → 前端渲染并显示引用 → 这一轮的数据落库、离线算命中率和成本。

【选型原则】先摸约束（团队、规模、合规），再定关键选型（模型怎么用、向量库选哪个），外围技术按团队习惯选。关键是别颠倒顺序——先挑时髦技术再找理由，一追问就崩。

【权衡】这套分层在规模不大的时候其实有点重。如果只有几百份文档、几个人的团队，完全可以把向量和关系数据放同一个库，省一半运维成本。分层是为了应对变化，用不上的时候就是过度设计。

回忆卡 1 · 合上材料，用自己的话讲一遍

用一次完整的问答，把你的架构串起来讲一遍（从用户点下发送开始）。

讲完了，展开对照

检查你的讲述里有没有这几样：

  1. 一个具体的问题，而不是抽象的"数据"——比如"报销单丢了怎么办"。
  2. 每一跳都说清"谁调谁、传了什么"——这是架构和清单的分界线。
  3. 检索那一步要讲细：两路检索怎么合并、精排取前几段。
  4. 至少一处"为什么这么设计"——比如为什么向量单独存。
  5. 结尾落到落库和统计——说明数据不只是流过去，还留下来了。

如果讲的时候卡在某一步，那一步就是你项目里最不熟的部分——回去把它弄明白。

回忆卡 2 · 合上材料，用自己的话讲一遍

「你搭框架的整体思路是什么？」——说出你的回答（这是 下一份要展开的题）。

讲完了，展开对照

核心是别一上来讲技术，先讲你怎么摸清需求：

  1. 先问约束：谁用、多少人用、有没有合规要求、团队会什么。这一步决定后面所有选择的空间。
  2. 再划边界：哪些是核心必须自己做的，哪些用现成的就行。AI 应用里框架和检索组件大多是现成的，真正要自己做的是数据准备和效果调优。
  3. 然后定关键选型：模型怎么用、数据怎么存。
  4. 最后搭骨架并跑通一条最小链路：先让"提问 → 检索 → 回答"能走通，再往上加功能。

收尾一句：「我的习惯是先跑通最小闭环，再谈扩展——不然容易在还没验证效果的时候就陷入架构细节。」
