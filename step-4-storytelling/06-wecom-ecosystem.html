06 · 企微生态专题

这一组题很"专"——没做过这个生态的人几乎答不上来，做过的人能讲一堆坑。 所以它反而是证明你真做过项目的好机会。这一页把六道题串成一条线：身份从哪来、怎么同步、怎么用。

TK-1TK-2TK-4TK-5TK-6TK-7
读之前

需要知道"网页授权""回调"这类词的大概意思。没做过企微也没关系，这一页会把流程讲清；但如果你做过，一定要把当年的坑翻出来——那才是这组题的分数所在。术语不熟先看 00 · 先认识这几个词。

第一遍（5 分钟）只看主图，记住那条"身份流转"的主线。
第二遍（15 分钟）读第 1、2 节，把流程和身份标识分清楚。
第三遍做页尾回忆卡，重点看那道"域名限制"的题——它最能拉开差距。

0. 先看一个场景

对方问：「你们那个 H5 页面，用户是怎么登录的？」

如果你没做过，很容易答成：「就是用户点了之后跳转授权，然后拿到用户信息。」

做过的人会这么答：

做过的人的回答

「用户在企微里打开页面时，我们先静默授权——这种模式用户无感，但只能拿到身份标识、拿不到详细信息。如果业务需要头像昵称，就得再走一次手动授权，那一次会弹确认框，所以我们会尽量把需要用到的信息一次性授权完，避免反复打断。

拿到授权码之后，服务端去换用户身份，然后建立我们自己的会话——后面的业务都用自己的会话，不再每次都去换，不然每次请求都要多一个来回。

这里有个坑：授权是绑定在可信域名上的，我们的页面域名必须在配置里，否则直接报错。而且那个配置项数量有限，多个业务域名就很麻烦。」

差别在哪？不在知识量，在细节和坑。这一页就是把这些细节补上。

主图 · 这六道题其实是一条线

身份从哪来 → 怎么对上 → 怎么用

这张图在说什么：这六道题串起来是一条完整的身份主线——用户进来时怎么认出来、身份怎么和你的业务数据对上、对上之后怎么用来做分群和统计。

最容易卡住的两个地方我都标出来了：域名数量限制和身份标识用错体系。这两个都是"没做过就想不到、做过就很难忘"的坑。

1. 登录流程与三个身份标识（TK-1、TK-5）

先讲登录，再讲身份——因为这两个问题其实是连着的。

环节做什么要注意什么
静默授权 用户打开页面时自动跳一次授权，用户没有感知，但只能拿到身份标识，拿不到头像昵称这类信息。 适合"只判断你是谁"的场景。它不会打断用户，所以能用就用它。
手动授权 会弹出确认页面，用户点了同意才能拿到更完整的信息。 会打断用户，所以要合并需求——把需要的信息一次性授权完，别来回弹好几次。
换取身份 授权后拿到一个临时的码，由服务端拿去换用户身份。这个码只能用一次，而且有效期很短。 必须服务端换，因为这需要密钥。把密钥放在前端是最典型的安全事故。
建自己的会话 换到身份之后，签发你自己的登录凭证，后续请求都用它。 这一步很关键：不做的话每次请求都要重新走一遍授权流程，多一个来回还容易超时。
三个"唯一 ID"不是一回事 —— 这题最容易答错（TK-5）

这个生态里有好几个"标识"，最要命的是它们在什么范围内唯一：

  • 平台内的用户标识：在这个企业范围内唯一。这是你业务主键唯一应该用的东西。
  • 平台内的外部联系人标识：指企业外部的人（客户），和上面的不是一套，不能混用。
  • 微信侧的标识：同一个用户在不同应用下拿到的值不一样——换一个应用，同一个人就变成另一个值了。

所以最典型的坑是：拿微信侧的标识当业务主键。后果是——同一个用户从不同入口进来，在你的库里成了两个人；或者你换了应用配置，所有人的绑定关系全部失效。

正确做法：用企业范围内的用户标识做业务主键，微信侧的标识只作为辅助字段存着。如果确实需要跨体系对应，那就老老实实做一张映射表。

2. 域名数量限制怎么绕（TK-2）

这是这一组里最能拉开差距的一题——它是个纯工程问题，没做过的人根本想不到会有这个限制。

问题是什么：平台对"可信域名"的配置项数量有限制（历史上是 2 个），但业务上可能有十几个不同的页面域名。域名不在列表里，授权直接报错。

四种绕法，按推荐程度排

① 统一到一个域名，用路径区分最干净的做法。所有业务挂在同一个主域名下，用子路径区分不同系统。这样只需要占一个配置项。代价是要统一部署和路由，历史项目改造量大。
② 主域名做授权中转把授权域名配成一个固定的中转页：用户在这里完成授权，服务端换到身份、建好会话，再跳转回真正的业务域名。业务域名不需要在配置里，因为它不参与授权。这是历史项目最常用的办法。
③ 网关统一入口所有域名都通过一个网关转发，对外看起来只有一个域名。本质是方案①的加强版，适合有一定基础设施的团队。
④ 申请更多配置项可以走官方渠道申请，但不一定批、周期也不可控。不能把项目计划押在这上面，只能作为备选。
这题的加分点

说清"中转方案"里一个容易被忽略的细节，可信度立刻不一样：

「中转方案要注意：授权完成之后的跳转，不能把会话凭证直接放在地址栏里——那样会被日志、浏览器历史、Referer 带出去。我们的做法是中转页先种好会话，再跳到业务域名，凭证走 Cookie 而不是明文参数。如果确实要传一次性的码，也要保证用完立即失效、且只能换一次。」

3. ID 同步与标签（TK-6、TK-4）

问题怎么答
ID 同步怎么做（TK-6） 靠回调，不是靠轮询。人员入职离职、部门调整这些变更，平台会主动推一个事件通知给你，你收到之后更新本地的用户表。
三个必须处理的点：① 回调是加密的，要按官方方式验签解密，不能裸收；② 回调会重复推送，处理逻辑必须幂等（同一事件处理两次结果一样）；③ 可能丢，所以要有一个定期全量对账的补偿机制——只靠回调迟早会对不上。
用户打标签（TK-4） 平台的标签体系一般分企业统一维护的和个人自己打的，两类的可见范围不同，对接时要分清楚。
做法：把标签同步到本地，和你的用户表关联起来——这样就能按标签做分群（比如"只看某个部门的资料""给某类客户推不同的内容"）。
注意：标签是会变的，所以同步也要走回调 + 定期对账，和上面那题是同一套机制。
埋点怎么做（TK-7） 先定要回答什么问题，再定埋什么——这是最容易被跳过的一步。常见的四类：曝光（看了哪些）、点击（点了什么）、停留（看了多久）、转化（走完了哪条路径、在哪一步流失）。
实现上的三个要点：① 批量上报，别每个事件发一次请求；② 页面关闭时用专门的方式兜底上报，否则最后一批数据会丢；③ 带上前面的用户标识，否则埋点和用户对不上，数据没法用。
埋点这题最容易答空

大部分人的答案是"我们接了统计工具，埋了 PV/UV"——这等于没答。

好的答法要落到"埋了这些数据之后你做了什么"：

「我们埋的主要是问答链路的分步数据：用户问了什么、检索命中了哪些、最后有没有点开引用、有没有反馈"没用"。这些数据直接进了那个未命中问题列表，我们每隔一段时间看一次，发现某类问题反复搜不到，就去补对应的资料。」

最后那句才是重点——埋点的价值不在数据本身，在你用它改了什么。

对方追问：「回调你们怎么保证不丢、不重复？」

这题在验证你有没有真正处理过线上问题。三层都要说到：

  • 防重复：用事件里的唯一标识做幂等键，处理前先查有没有处理过。重复推送是常态，不是异常。
  • 防丢：回调可能因为网络或者发布而丢失，所以要有定期全量对账——按天拉一次完整数据，和本地比一遍，把差异补上。只靠回调的系统迟早会对不上。
  • 处理要快、要能重试：收到回调先落库就立刻返回成功，真正的业务处理丢到队列里异步做——否则处理慢了对方会重推，反而制造重复。

收尾：「这三条的顺序也重要：先落库再返回、异步处理、定期对账。我一开始是先处理再返回，结果处理稍慢就被重推，日志里全是重复记录。」

对方追问：「你刚才说的这些，是你做的还是别人做的？」

这题很直接，而且必须诚实——因为追问下去就会验证。三种答法：

  • 如果是你做的：说清你负责的边界（比如"授权和 ID 同步是我做的，标签那块是同事负责的对接"）。
  • 如果是你参与的：说清你具体做了哪一部分，别含糊成"我们一起做的"。
  • 如果只是了解：直接说——"这块是同事负责的，我了解整体流程和几个主要的坑，但具体实现细节是他做的。"

最后一种答法不丢分。对方问这个是想确认边界，不是要你全包。硬撑自己全做了，一追问实现细节就崩，那才是真丢分。

4. 讲解骨架（看懂之后再背）

「企微 H5 登录 / 唯一 ID / 域名限制 / 回调同步 / 埋点」

【登录流程】用户打开页面先走静默授权——用户无感，但只拿得到身份标识。需要头像昵称这类信息时才走手动授权，那次会弹确认框，所以我们会把要用的信息一次性授权完，避免反复打断。服务端拿授权码换取身份之后，签发我们自己的会话，后续请求不再重复换取。

【唯一 ID】这里有个容易搞错的点：平台里的用户标识和微信侧的标识不是一回事。微信侧的标识在同一个用户、不同应用下是不同的值，拿它当业务主键，会导致同一个人数据对不上、或者换配置后绑定全失效。所以业务主键用企业范围内的用户标识，另一个只作辅助字段。

【域名限制】可信域名的配置项数量有限，但业务域名往往很多。我们的做法是主域名做授权中转：用户在固定的中转页完成授权，服务端建好会话后跳回业务域名——业务域名不参与授权，就不需要配置。注意凭证不能明文放地址栏，走 Cookie。

【ID 同步】靠回调推给你，不轮询。三个必须处理的点：回调解密验签、处理逻辑幂等、定期全量对账兜底。另外收到回调先落库就返回，真正的处理丢队列异步做——不然处理慢了会被重推，制造重复。

【标签】平台的标签分企业维护的和个人自建的，可见范围不同。我们把标签同步到本地和用户表关联，用于分群——比如按部门决定能看到哪些资料。标签会变，所以同步同样走回调加对账。

【埋点】我们埋的是问答链路的分步数据：问了什么、命中了哪些、有没有点开引用、有没有反馈没用。这些数据进了未命中问题列表，我们照着它去补资料。实现上是批量上报，页面关闭时走专门的兜底上报方式，每条都带上用户标识。

【权衡】这一套里最麻烦的其实是域名的统一治理——技术上不难，但要协调多个历史项目改造，商务和沟通成本比写代码高。所以我的经验是：能在一开始就统一域名，就别拖到后面去绕。

回忆卡 1 · 合上材料，用自己的话讲一遍

为什么"拿微信侧的标识当业务主键"是个严重的错误？

讲完了，展开对照

因为它的唯一性范围不对。

微信侧的标识是"某个用户 + 某个应用"这个组合下的值——同一个人，换一个应用就变成另一个值了。而你的业务主键需要的是"这个人在我的系统里是谁"，这个身份不应该随应用配置而变。

后果具体有两个：

  • 同一个人变成两条记录：他从不同入口进来，拿到的标识不同，你的系统认不出是同一个人——数据统计、权限、历史记录全乱。
  • 换个配置就全断：应用配置一变，所有标识都变了，之前的绑定关系全部失效。

正确做法：业务主键用企业范围内的用户标识（它在你的企业里是稳定的），微信侧的标识只作为辅助字段存着。如果确实需要跨体系对应，就单独做一张映射表，把两套标识关联起来。

回忆卡 2 · 合上材料，用自己的话讲一遍

「可信域名只能配两个，但你有十几个业务域名」——你的解法是什么？为什么这么选？

讲完了，展开对照

推荐的答法是主域名做授权中转：

  1. 授权域名配一个固定的中转页，它在可信列表里。
  2. 用户在任何业务页面被引导到这个中转页完成授权。
  3. 服务端拿到身份、建好会话并种下凭证。
  4. 中转页跳回真正的业务域名——业务域名不参与授权，所以不需要配。

为什么选它：它对现有项目的改造最小，业务代码基本不用动，只加一个中转页。

更彻底的方案是把所有业务统一到一个域名下、用路径区分——技术上更干净，但要改造所有历史项目，沟通和迁移成本高。

加分细节：跳转时凭证走 Cookie，不要明文放地址栏——地址栏会被日志、浏览器历史、Referer 带出去。
