01 · 项目整体怎么讲

「介绍一下你的项目」是每一轮都会问、而且决定后面聊什么的一道题。 这一页给你三档详略的标准版本——30 秒、2 分钟、深挖，按对方的兴趣切换。

ML-1YF-1YU-16FN-5
读之前

这一页假设你手上有步骤 2做出来的项目和步骤 3测出来的数字。没数字的话这一页只能看个结构，用不上。术语不熟先看 00 · 先认识这几个词。

第一遍（5 分钟）只看主图，理解三层详略分别用在哪。
第二遍（15 分钟）读第 1、2 节，然后照着写出你自己的 30 秒版本。
第三遍做页尾回忆卡，对着录音讲一遍 2 分钟版本。

0. 先看一个场景

对方坐下来说：「先简单介绍一下你这个项目吧。」

这句话有两种理解，而大多数人选错了：

「简单介绍」不是让你讲简单，是让你讲短

很多人听到"简单介绍"，就开始铺垫背景：我们公司是做什么的、这个业务怎么来的、当时有个什么契机……讲了两分钟还没到正题。

对方的真实意思是：用最短的话让我知道这是个什么东西，然后我会挑感兴趣的地方追问。

所以这道题的正确姿势是准备好三档长度，根据对方的反应切换——而不是准备一个固定长度的稿子。

主图 · 同一个项目，三档详略

看你讲完之后，对方往哪追问

这张图在说什么：同一个项目要准备三档长度。30 秒版本用来"让对方知道这是个什么"，2 分钟版本用来"把链路交代清楚"，深挖版本才是你真正得分的地方——但前提是前两档讲得干脆，对方才愿意往下问。

关键那句：顺序是「问题 → 方案 → 结果」，不是「技术 → 技术 → 技术」。一上来报技术栈，对方既记不住也没有追问的抓手。

颜色含义： 最短版本 标准版本 追问才展开 常见错误 原则

1. 30 秒版本：四句话

这四句话的顺序不能换，因为它对应的是听的人心里的四个问题。

第几句说什么它在回答对方心里的什么问题
第一句 这是个给谁用的什么系统。 "这东西的定位是什么？"——先归类，对方才能调用已有的认知框架去理解你后面说的东西。
第二句 它解决什么问题（没有它之前是怎么样的）。 "为什么需要它？"——这一句决定后面所有技术选择的合理性。没有痛点，你讲什么架构都是自嗨。
第三句 你负责哪一块。 "你在里面干了什么？"——很多人讲了半天系统，却没说清自己的角色。
第四句 一个数字（规模、效果、或者工期）。 "这东西是真的吗？"——数字是"真做过"的第一个证据，也是对方决定往哪追问的线索。
套出来的样子（用你自己的填）

「这是一个给公司内部研发团队用的技术资料问答系统。以前大家查规范只能靠翻文件或者问人，新人上手要一两个月。我负责从检索链路到前端交互的全栈实现，目前库里有两万多份文档，常用问题的检索命中率在八成以上。」

四句话，二十多秒。对方立刻知道该往哪追问了——是问检索怎么做的，还是问命中率怎么测的。

为什么第四句是"一个数字"而不是"一堆数字"

因为 30 秒版本的目标是给对方一个追问的抓手，不是展示数据。

说一个最有代表性的就够（通常是效果类或规模类的）。一口气报五个数字，对方一个也记不住，还会觉得你在背稿。

2. 2 分钟版本：怎么把链路讲顺

对方说了"展开讲讲"，你要在这两分钟里把整条链路走一遍。这里最容易犯的错是按技术分层讲（前端什么、后端什么、数据库什么）——听着像技术清单。

更好的方式是按数据流讲：一个请求进来，依次经过了什么。

① 用户做了什么
从一个具体动作切入，而不是从"系统由什么组成"切入。比如"用户输入一个问题"。有了具体动作，后面的每一步都自然。
→
② 问题经过了哪几步
改写 → 检索 → 精排 → 组装上下文 → 调模型 → 流式返回。每一步一句话说清做了什么，先不展开为什么。
→
③ 数据存在哪
文档切片、向量、会话记录、任务状态分别在哪。这一步顺带就把"用了什么数据库"交代了。
→
④ 一句话收技术栈
走完链路之后再说"所以技术上是这些"，这时候技术栈是"对前面链路的总结"，而不是"开场白"。
把"用到哪些技术"讲得不流水账（YF-1）

这题的正确答法是每个技术都挂在一个理由上：

❌ "前端 Vue3，后端 NestJS，数据库 PostgreSQL，缓存 Redis，向量库 Milvus。"

✅ "后端用 NestJS，因为它自带依赖注入和模块划分，我们好几个人分模块开发不容易冲突；数据库用 PostgreSQL，主要看中它支持 JSON 字段和全文检索，一些非结构化数据不用再单独找存储；向量库选的是支持混合检索的那一类，因为我们后来发现纯向量召回效果不够。"

每个选择都带一个"因为"——这就是"用过"和"列过"的差别。

3. 「印象最深的项目」怎么选（FN-5）

这题的关键在选材，不在表达。选错了，后面怎么讲都平淡。

应该选哪个项目？

别选"最大的"最大的项目往往你只参与了很小一块，一追问细节就说不下去
别选"最成功的"一路顺风的项目没有故事，讲出来就是流水账
要选"你解决过难题的"判断标准很简单：这个项目里有没有一件事，是你最初不知道怎么办、后来搞定了的？有，就选它
最好还能覆盖多个域如果这个项目同时能讲架构、能讲优化、能讲踩坑，那它一个人就能撑起整场

讲的时候按什么顺序？

先给结论"我印象最深的是 XX 项目，因为它让我第一次真正理解了 YY。"——一句话定调，对方知道你接下来要讲什么
再讲难在哪说清当时的约束和难点。难点要具体，不能是"时间紧任务重"这种空话
然后讲你怎么做的试过什么、为什么最后选了这条
最后讲收获不是"学到了很多"这种废话，而是具体的认知改变——"我以前以为 A，做完发现其实是 B"
这题的加分点

最后那句"收获"是拉开差距的地方。对比一下：

❌ "这个项目让我对 AI 应用有了更深的理解。"——等于没说。

✅ "我以前觉得 RAG 效果不好就换个更强的模型，做完这个项目才发现，大部分问题其实出在切分和精排上——检索回来的东西不对，模型再强也白搭。"

后者具体、可验证、还带一点反直觉，一听就是真做过。

对方追问：「你在这个项目里具体负责什么？」

这题几乎必问，而且很多人会答砸——要么说得太大（"整个系统都是我做的"），要么说得太虚（"我负责前端部分"）。

好的答法是说清"范围 + 深度"：

  • 范围：参与了哪些模块，哪些是别人做的。坦率说清分工反而更可信——没有人会独立做出一个完整系统。
  • 深度：你负责的那块，你做到什么程度。是"按设计稿实现"，还是"方案也是我定的"。
  • 最难的那部分：明确指出哪一块是你攻下来的。这一句是重点。

例：「检索链路和前端是我做的，后端的基础设施是同事搭的。其中混合检索的排序策略是我自己调的——一开始只用向量召回，长尾问题效果很差，后来加了关键词检索和重排才稳定下来。」

对方追问：「如果重来一次，你会怎么改？」

这是一道专门测反思能力的题，答不好会显得你没复盘过。别答"我觉得挺好的"，也别说一堆无关痛痒的小改动。

好的答法：指出一个当初的决策、说明当时的理由、再讲现在会怎么选。

「当时我为了快，把上下文治理直接做成了"超长就截断"。这么做上线是快了，但多轮对话到后面质量明显下滑。如果重来，我会一开始就把摘要做进去——虽然开发慢几天，但能省掉后来重构的功夫。」

注意这句里的三层：当初的决策 → 当时的取舍理由 → 现在的判断。第三层才是对方要的。

对方追问：「这个项目有多少人做？做了多久？」

这题看着是问事实，其实在验证前面讲的东西是不是你做的。答的时候把数字和分工对上：

  • 人力和时长要对得上工作量：一个人两周做出一个"两万份文档的知识库系统"是可信的（因为有现成框架）；但说"两个人两周从零做了一个完整的多 Agent 平台"就会让人起疑。
  • 阶段要能拆：调研、开发、联调、上线各占多久。能拆说明你真的经历过全过程。
  • 和自己前面报的数字对得上：这一条最重要，见下一份。

4. 讲解骨架（看懂之后再背）

「介绍一下你的项目」

【30 秒版】这是一个给内部研发团队用的技术资料问答系统。以前查规范只能翻文件或问人，新人上手要一两个月。我负责检索链路和前端的实现。目前库里两万多份文档，常用问题的命中率八成以上。

【展开：问题】核心痛点是资料散、版本多、找不到。而且这类问题有长尾——同一个意思有好几种问法，纯关键词搜索经常搜不到。

【展开：方案】所以做成了 RAG。一个请求进来依次是：查询改写 → 向量加关键词的混合检索 → 重排 → 组装上下文 → 调模型 → 流式返回。前端负责流式渲染和断线续传。

【技术选型】后端用 NestJS，因为它自带模块划分和依赖注入，多人分模块开发不容易冲突；数据库用 PostgreSQL，看中它同时支持 JSON 字段和全文检索，非结构化数据不用再单独找存储；向量库选支持混合检索的，因为纯向量召回在长尾问题上不够。

【最深的坑】上线后发现有些问题答不准，一开始以为是模型不行，换了更强的模型提升有限。后来把检索结果打出来看，发现真正的问题是切片把表格切碎了——表格被切开之后语义就断了。改成按结构切、表格整体保留，效果才上去。

【权衡】这套方案适合资料相对稳定、问题偏事实型的场景。如果是需要大量推理的任务，光靠检索补充上下文不够，得考虑别的方式。而且混合检索的排序权重是要按语料调的，换一套资料就得重新调一轮。

回忆卡 1 · 合上材料，用自己的话讲一遍

用 30 秒介绍你自己的项目——四句话，按顺序说出。

讲完了，展开对照

检查你的四句话是不是这四类：

  1. 给谁用 + 是什么：一句话定位，让对方能归类。
  2. 解决什么问题：说清"没有它之前是怎么样的"，这是后面所有技术选择的依据。
  3. 你负责哪块：明确自己的范围，别说"整个系统"。
  4. 一个数字：规模或效果，选最有代表性的那一个。

如果卡住了，通常是两个原因：要么第二句说不清（说明你没想清楚为什么做这个系统），要么第四句没有（说明数字还没测，回步骤 3 的用量口径补）。

讲完记一下实际秒数。超过 40 秒就说明某一句太啰嗦了。

回忆卡 2 · 合上材料，用自己的话讲一遍

对方问"你这个项目用到哪些技术"，你怎么答才不像背清单？

讲完了，展开对照

核心原则：每个技术都挂在一个理由上，而且按链路顺序说，不按分层罗列。

  1. 先说链路：一个请求进来经过哪几步。这样技术栈就是"链路的自然结果"，而不是孤立的清单。
  2. 再逐个补"因为"：为什么选它、当时还考虑过什么、为什么没选。
  3. 最后说一个"换过的"：如果某个技术中途换过，讲清为什么换——这比任何"因为"都更能证明你真的用过。

对比："我们用了 Redis" vs "一开始我们把会话状态放在数据库里，但每轮对话都要读写一次太慢，后来挪到 Redis 了"——后者一听就是踩过坑的人说的。
